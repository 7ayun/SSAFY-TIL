## 학습 목표

* AI 오케스트레이션이 필요한 이유를 단일 LLM 구조의 한계와 비교해 설명할 수 있다
* LangFlow의 플로우·컴포넌트 개념을 이해하고 기본 채팅 플로우를 직접 구성할 수 있다
* 메모리 컴포넌트를 연결해 대화 기록을 유지하는 구조와 토큰 소비 원리를 설명할 수 있다
* Agent 컴포넌트에 도구(Tool Mode)를 부착해 자율 실행 흐름을 구성할 수 있다
* 오케스트레이터 + 하위 에이전트의 비선형 구조를 설계하고 LangFlow Export로 팀 공유 설계도를 만들 수 있다

## 1. AI 오케스트레이션이란

### 1-1. 정의

AI 오케스트레이션은 **AI가 AI를 지휘하는 구조**다. 하나의 상위 오케스트레이터가 사용자의 입력을 분석해 상황에 맞는 하위 에이전트를 호출하고, 각 에이전트의 결과물을 받아 다음 에이전트에게 전달하거나 최종 답변으로 합성(Synthesizing)하는 실행 흐름 제어 시스템이다.

단순히 더 좋은 답을 만들기 위한 기술이 아니라, **정확한 실행 순서와 역할 분리를 통해 예측 가능한 서비스를 구성**하는 아키텍처 개념이다. 내부 LLM 자체가 바뀌는 것은 아니며, Next Token Prediction 원리는 그대로 유지된다.

> **강사님 강조**: AI를 도구로 보는 것이 아니라 작업 시스템의 구성 요소로 설계해야 한다. 그래야 규모가 커져도 통제 가능한 서비스를 만들 수 있다.

### 1-2. 오케스트레이터가 필요한 이유

에이전트가 사용할 수 있는 도구(Tool)가 많아질수록, 즉 MCP·노션·슬랙·달력 등 외부 연동이 늘어날수록 실행 경로가 복잡해지고 어디서 멈출지 예측하기 어려워진다. 에이전트 내부 LLM이 판단하긴 하지만 여전히 확률 기반이기 때문에 상위 통제 레이어가 없으면 반복 루프나 의도치 않은 동작이 발생한다.

| 구조 | 특징 | 한계 |
|------|------|------|
| 단일 LLM | 입력 → 모델 → 출력 | 역할 혼합, 컨텍스트 누전 |
| 단일 에이전트 + 도구 | 도구 자율 선택 | 도구 증가 시 경로 예측 불가 |
| 오케스트레이터 + 멀티 에이전트 | 역할 분리 + 실행 흐름 통제 | 설계 복잡도 증가 |

## 2. LangFlow 개요

### 2-1. LangFlow란

LangFlow는 **LangChain 기반의 오픈소스 노코드(No-Code) / 로우코드(Low-Code) AI 에이전트 설계 도구**다. GUI 기반 캔버스에서 컴포넌트를 드래그 앤 드롭으로 연결해 AI 파이프라인 설계도(Flow)를 만들 수 있다. 로컬 실행 시 `localhost:7860`에서 접속한다.

> **강사님 강조**: LangFlow는 배포 도구가 아니라 설계와 검증 도구다. 플로우가 정상 동작하는 것을 확인한 뒤 LangChain 코드로 옮겨 실제 서비스에 통합하는 방식으로 사용한다.

### 2-2. 핵심 개념

```
Flow     : 하나의 작업을 수행하기 위해 컴포넌트들을 연결한 설계도 단위
Component: 기능별로 나누어진 블록 (입력, 모델, 프롬프트, 출력, 도구 등)
Playground: 만들어진 Flow를 코드 구현 없이 바로 테스트할 수 있는 UI (Streamlit 기반)
Export   : Flow를 JSON 파일로 내보내 팀원 공유 및 재사용 가능
```

### 2-3. 설정 — 모델 프로바이더 및 글로벌 변수

우측 상단 로켓 아이콘 → Settings에서 두 가지를 설정한다.

- **Model Providers**: 사용할 API 키 등록 및 검증 (`Validate API Key`)
- **Global Variables**: 검증된 API 키가 자동 등록되며, 모든 플로우에서 공통으로 참조 가능

> **강사님 주의**: 실습 환경에서 공유 API 키를 사용하는 경우 인원을 조로 나누어 동시 요청 수를 제한한다. 모든 인원이 동시에 요청을 보내면 IP 차단이나 요청 한도 초과가 발생할 수 있다. 사용 모델은 GPT-4o mini(구 GPT-5 nano)로 한정한다.

## 3. 실습 1 — Basic Prompting 플로우

### 3-1. 기본 구조

```
[Chat Input] → [Language Model] ← [Prompt Template]
                     ↓
               [Chat Output]
```

컴포넌트 연결 순서:
1. `New Flow` → `Basic Prompting` 템플릿 선택
2. Language Model 컴포넌트에서 사용 모델 지정 (GPT-4o mini)
3. Prompt Template에 시스템 지시 작성 (예: "말 끝에 항상 `~양` 붙여서 답변해. 최대 세 줄까지만.")
4. Playground에서 채팅 테스트

### 3-2. 단일 요청-응답 구조의 한계

Basic Prompting 플로우의 Language Model 컴포넌트는 **싱글턴(Single-turn) 방식**으로 동작한다. 이전 대화 내역을 저장하거나 주입하지 않아 "내 이름이 뭐야?"라고 물으면 이름을 기억하지 못한다. 대화 기억 기능을 위해서는 별도의 **메모리 컴포넌트**를 부착해야 한다.

## 4. 실습 2 — 메모리 컴포넌트 추가

### 4-1. Message History 연결 구조

```
[Chat Input] → [Language Model A]
                  ↓ (output: Language Model 타입으로 변경)
[Prompt Template] → [Language Model B] ← [Message History]
                          ↓
                    [Chat Output]
```

- Language Model A: 사용자 입력을 받아 Language Model 타입 출력으로 반환
- Language Model B: A의 출력 + Message History + Prompt Template을 합쳐 최종 답변 생성
- 실제로 모델을 두 개 쓰는 것이 아니라 **입력 경로를 구분한 GUI 설계 방식**이다 (Receiving Input)

> **강사님 팁**: LangChain 코드로 직접 구현할 경우 훨씬 간결하다. 사용자 입력과 시스템 응답을 리스트에 누적하여 모델에게 전달하는 방식으로 동일한 기능을 구현할 수 있다.

### 4-2. 메모리 누적과 토큰 소비

대화 내역이 쌓일수록 모델에게 전달되는 데이터량이 선형으로 증가하며, 이는 토큰 소비와 비용 증가로 이어진다. 실제 서비스에서는 적절한 시점에 **대화 요약(Compression)** 을 수행해 히스토리를 압축하는 전략이 필요하다. Message History 컴포넌트의 `max_token` 설정으로 유지할 기록 범위를 제한할 수 있다.

## 5. 실습 3 — API 도구 추가 (Wikipedia)

### 5-1. Language Model + API Request 구조

```
[Chat Input] → [Language Model] ← [Prompt Template]
                     ↓
              [API Request]
                     ↓
              [Smart Transform] ← [Prompt Template 2]
                     ↓
              [Chat Output]
```

- **Language Model**: 사용자 질문에서 키워드 1개 추출 → Wikipedia API URL 형식으로 반환
- **API Request**: 반환된 URL로 GET 요청 → JSON 응답 수신
- **Smart Transform**: JSON에서 `extract`(요약)와 `page`(출처 URL) 값을 추출해 한글 답변 생성

> **강사님 주의**: 이 구조는 RAG(Retrieval-Augmented Generation)가 아니다. 외부 API를 호출해 얻은 데이터를 LLM이 가공하는 구조일 뿐이다. RAG는 벡터 DB와 임베딩을 사용하는 별도 구조다. 혼동하지 않도록 한다.

### 5-2. 프롬프트 변수 문법

LangChain에서 프롬프트 내 동적 값 삽입 시 중괄호 형식을 사용한다:

```
# 프롬프트 내 변수 삽입 예시
사용자 입력: {user_input}
이전 검색 결과의 extract 키값 데이터를 참고하여 답변을 생성하라.
page 키값으로 출처를 제시하라. 답변은 최대 4줄, 한글로 작성.
```

`{user_input}` 처럼 중괄호로 감싼 부분이 **프롬프트 변수(Template Variable)** 로 동작하며, 이전 컴포넌트의 출력값이 해당 위치에 자동으로 주입된다.

## 6. 실습 4 — Agent 컴포넌트

### 6-1. Language Model vs. Agent 컴포넌트 차이

| 항목 | Language Model | Agent |
|------|----------------|-------|
| 동작 방식 | 입력 → 모델 → 출력 (단일) | Think → Act → Observe → 반복 |
| 메모리 기본 탑재 | 없음 (별도 연결 필요) | 있음 (기본 대화 기억) |
| 도구 사용 | 불가 | 가능 (Tool Mode 컴포넌트 연결) |
| 인스트럭션 위치 | 하단 (System Message) | 상단 (Agent Instructions) |

### 6-2. Tool Mode — 도구 부착 방법

API Request 컴포넌트 상단의 **Tool Mode** 를 활성화하면, 해당 컴포넌트가 에이전트가 호출 가능한 도구로 변환된다. 에이전트는 사용자 입력을 Reasoning한 뒤, 필요하다고 판단되면 연결된 도구를 자율적으로 호출한다.

```
[Chat Input] → [Agent] ← [Agent Instructions (Prompt)]
                 ↑
         [API Request (Tool Mode)]
                 ↓
          [Chat Output]
```

에이전트 인스트럭션에 Wikipedia API URL 형식을 명시하지 않아도, 에이전트가 스스로 적절한 엔드포인트를 추론하고 사용한다.

> **강사님 강조**: Agent는 대화를 기억한다고 해서 완전한 메모리가 탑재된 것이 아니다. LangChain으로 직접 구현할 때는 체크포인트(Checkpoint)를 사용해 메모리를 명시적으로 주입해야 한다. LangFlow Agent 컴포넌트가 기본 제공하는 메모리는 LangFlow 내부 기능이다.

## 7. 실습 5 — AI 오케스트레이션 설계

### 7-1. 오케스트레이터 + 하위 에이전트 구조

```
사용자 입력
    ↓
[오케스트레이터 (Agent + Orchestrator Prompt)]
    ├── 취미 언급 감지 → [못난이 에이전트 Tool] (부정 답변 생성)
    ├── 정보 질문 감지 → [Wikipedia API 에이전트 Tool] (검색 후 답변)
    ├── 계획 요청 감지 → [Planner 에이전트 Tool]
    ├── 코드 생성 요청 → [Generator 에이전트 Tool]
    └── 검증 요청 감지 → [Reviewer 에이전트 Tool]
                               ↓
                    [Python Interpreter Tool] (코드 실행 결과 반환)
    ↓
[Chat Output]
```

### 7-2. Run Flow — 플로우를 도구로 재사용

LangFlow의 **Flow Control → Run Flow** 컴포넌트를 사용하면, 이전에 만든 플로우(설계도) 전체를 하나의 도구로 불러올 수 있다. Tool Mode로 전환 후 오케스트레이터 에이전트에 연결하면, 오케스트레이터가 조건에 따라 해당 플로우를 통째로 실행한다.

> **강사님 팁**: 이름과 설명을 명확하게 작성해야 한다. 오케스트레이터가 어떤 도구를 호출할지 판단할 때 해당 플로우의 이름과 설명을 참조하기 때문에 도구의 이름·설명 = 프롬프트 엔지니어링이다.

### 7-3. 비선형 구조와 조건 분기

플래너 → 제너레이터 → 리뷰어는 선형처럼 보이지만, 오케스트레이터를 중심으로 구성하면 **비선형 구조**가 된다. 사용자의 입력에 따라 어떤 에이전트를 먼저 호출할지, 한 에이전트의 결과를 다른 에이전트에게 전달할지를 오케스트레이터가 실시간으로 판단한다. 조건 분기가 올바르게 작동하는지 확인하기 위해 억지로 대비되는 조건을 설정해 테스트하는 방법이 효과적이다 (예: 취미 질문 → 부정 에이전트 / 정보 질문 → Wikipedia 에이전트).

## 8. LangFlow의 한계와 활용 범위

### 8-1. LangFlow로 할 수 있는 것과 없는 것

| 가능 | 불가 |
|------|------|
| 컴포넌트 연결 및 파이프라인 설계 | 코드 저장 및 서버 실행 |
| Playground에서 즉시 동작 검증 | API 직접 배포 (제한적 지원) |
| JSON Export로 팀 설계도 공유 | 프로덕션 수준 서비스 직접 운영 |
| 다양한 LLM API 교체 테스트 | LangFlow 전용 구조를 그대로 코드 이식 |

### 8-2. 프로젝트 활용 방법

LangFlow는 1학기 최종 프로젝트에서 **팀 공유 설계도**로 활용하는 것이 최적의 사용 방법이다. 플로우를 JSON으로 익스포트한 뒤 팀원에게 배분해 "너는 이 컴포넌트를 코드로 구현해"라고 역할 분담할 수 있다. 추후 GMS(Galaxy Model Suite) 환경이 제공되면 OpenAI, Claude, Google 등 다양한 LLM API를 플로우 단위로 교체 테스트하고, 최적 모델을 선택해 프로젝트에 통합할 수 있다.

> **강사님 강조**: 단순 LLM 챗봇에서 그치지 않고, 각 LLM의 특성을 살린 기능 조합으로 서비스를 구성하면 포트폴리오 가치가 높아진다. LangFlow로 설계도를 먼저 만들고, 동작 확인 후 코드로 옮기는 순서를 지키면 개발 효율이 올라간다.

## 정리

| 구분 | 핵심 포인트 |
|------|-------------|
| AI 오케스트레이션 정의 | AI가 AI를 지휘, 상위 오케스트레이터가 하위 에이전트 실행 흐름 통제 |
| 오케스트레이터 필요성 | 도구 증가 → 실행 경로 복잡 → 통제 레이어 없으면 예측 불가 |
| LangFlow | LangChain 기반 노코드 설계 도구, localhost:7860, JSON Export |
| Flow / Component | 플로우 = 설계도, 컴포넌트 = 기능 단위 블록 |
| 메모리 컴포넌트 | Message History 별도 연결 필요, 누적 시 토큰 소비 증가 → 압축 필요 |
| Tool Mode | 컴포넌트를 에이전트가 호출 가능한 도구로 전환 |
| Run Flow | 기존 플로우 전체를 하나의 도구로 재사용 |
| 프롬프트 변수 | {variable_name} 형식으로 동적 값 주입 |
| 비선형 구조 | 오케스트레이터 중심 조건 분기 → 상황별 에이전트 선택 호출 |
| LangFlow 한계 | 설계·검증 도구 / 배포·운영은 LangChain 코드로 직접 구현 |
