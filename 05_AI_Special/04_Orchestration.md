## 1. 오케스트레이션과 오케스트레이터

### 1-1. 오케스트레이션이란

다수의 AI 모델과 시스템을 조정·관리하며 데이터 흐름(파이프라인)을 제어하는 행위다. 에이전트의 기능이 강력해질수록 도구 호출 루프와 실행 경로가 복잡해지므로, 이를 통제하는 상위 구조가 필수적이다.

### 1-2. 오케스트레이터(지휘자)

오케스트라의 지휘자처럼, 사용자의 요청에 따라 적절한 에이전트를 호출하고 실행 순서를 결정하는 **상위 에이전트**다. 다수의 하위 에이전트와 양방향으로 데이터·상태를 공유하며 최종 결과물을 산출한다.

```
사용자 요청 → 오케스트레이터(지휘자)
                ├→ 에이전트 A (위키피디아 검색)
                ├→ 에이전트 B (코드 생성)
                └→ 에이전트 C (데이터 분석)
                        ↓
              결과 종합 → 사용자에게 반환
```

## 2. 랭플로우(Langflow)의 이해

### 2-1. 랭플로우란

랭체인(LangChain) 기반의 오픈소스 GUI 설계 도구다. 코드 작성 없이 시각적으로 에이전트 아키텍처를 설계하고, 플레이그라운드에서 즉시 테스트할 수 있다.

### 2-2. 주요 구성 요소

**플로우(Flow)** 는 하나의 작업을 수행하기 위해 여러 컴포넌트를 연결한 전체 흐름이다.

**컴포넌트(Component)** 는 에이전트, 프롬프트, 모델, 입력/출력 등 기능 단위별 블록이다.

### 2-3. 활용 위치

랭플로우는 실제 배포용 서버 환경이 아니라 **설계 검증 및 팀원 간 협업용 설계도(Blueprint)** 로 활용하는 것이 적절하다. Export 기능으로 JSON 형태의 설계도를 팀원과 공유하면 개발 병목을 줄일 수 있다.

> **강사님 주의**: 랭플로우는 실제 배포 환경이 아닌 설계 검증용 도구다. 프로토타이핑과 팀 협업에 활용하고, 실서비스는 별도로 구현해야 한다.

---

## 3. 에이전트 통제 및 세분화 전략

### 3-1. 역할 분리와 비선형 구조

단일 대화창의 맥락 혼선을 방지하기 위해 플래너, 제너레이터, 리뷰어를 독립적 실행 단위로 분리한다. 상위 오케스트레이터가 사용자 입력의 성격에 따라 **비선형적으로** 적절한 에이전트를 선택하여 호출한다.

### 3-2. 메모리 관리

랭귀지 모델은 기본적으로 단일 요청-응답 구조이므로 이전 대화를 기억하지 못한다. 대화 맥락을 유지하려면 **Message History 컴포넌트**를 별도로 부착해야 한다.

> **강사님 강조**: 에이전트 컴포넌트 자체에 자동 메모리 기능이 내장된 것이 아니다. 대화 기록을 유지하려면 반드시 별도의 히스토리 컴포넌트를 연결해야 한다.

---

## 4. 랭플로우 설계 실습

### 4-1. 기본 구조 — 모델과 메모리 연결

```
Chat Input → Message History → Language Model (GPT-4o mini) → Chat Output
```

Chat Input으로 사용자 텍스트를 수신하고, Message History가 이전 대화 로그를 관리하며, Language Model이 입력값과 히스토리를 합산하여 응답을 생성한다.

### 4-2. 도구 활용 — API 에이전트 설계

에이전트가 특정 정보를 검색해야 할 때 외부 도구를 호출하는 구조다. 프롬프트로 키워드 추출을 지시하고, API Request 컴포넌트를 Tool Mode로 활성화하여 에이전트에 연결한다. JSON 응답에서 핵심 정보를 추출하는 Smart Transform 컴포넌트를 후단에 배치한다.

### 4-3. 오케스트레이터 라우팅 프롬프트

```markdown
# 오케스트레이터 시스템 프롬프트

## 규칙 1. 역할 수행
- 사용자 입력에 직접 대답하지 않고 적절한 도구(에이전트)만 호출
- 취미 관련 이야기: '못난이 에이전트(부정 답변)' 호출
- 지식 검색 질문: '위키피디아 에이전트' 호출

## 규칙 2. 결과 처리
- 하위 에이전트가 생성한 답변을 변형 없이 그대로 사용자에게 전달
```

오케스트레이터는 스스로 답변하지 않고, 입력의 성격을 판단하여 적절한 하위 에이전트를 호출한 뒤 그 결과를 전달하는 역할만 수행한다.

> **강사님 팁**: 동일 IP에서 대량의 API 요청이 발생하면(예: 실습 환경에서 동시 접속) 봇 차단 및 403 오류가 발생할 수 있다. 실습 시 요청 간격을 두는 것이 좋다.

## 정리

| 구분 | 핵심 포인트 |
|------|-------------|
| 오케스트레이션 | 다수의 AI 모델·시스템을 조정·관리하며 데이터 흐름을 제어하는 행위 |
| 오케스트레이터 | 사용자 요청에 따라 적절한 에이전트를 호출·지휘하는 상위 에이전트 |
| 랭플로우 | LangChain 기반 GUI 설계 도구, 설계 검증·프로토타이핑용 (배포용 아님) |
| 플로우 / 컴포넌트 | 플로우 = 전체 흐름, 컴포넌트 = 기능 단위 블록 (에이전트·프롬프트·모델 등) |
| 메모리 관리 | LLM은 기본적으로 대화를 기억하지 못함, Message History 컴포넌트 별도 부착 필수 |
| 비선형 라우팅 | 오케스트레이터가 입력 성격에 따라 에이전트를 비선형적으로 선택·호출 |
