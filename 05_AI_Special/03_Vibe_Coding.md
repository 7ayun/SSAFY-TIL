# AI 강의 Ⅰ Day2 : 바이브 코딩 요약 및 구현 가이드

## 1. 바이브 코딩(Vibe Coding)의 명암과 올바른 접근법

바이브 코딩은 자연어를 통해 직관적이고 빠르게 프로그래밍하는 최신 개발 트렌드입니다. 하지만 단순히 AI에게 모든 것을 맡기는 것은 매우 위험합니다.

* **위험한 습관 3가지:**
  1. 코드 변경 사항을 확인하지 않고 무작정 `Keep`을 누르는 행위
  2. 요청하지 않은 수정 사항이 포함되어 있어도 무시하는 행위
  3. 코드를 실행(테스트)해 보지 않고 "잘 됐겠지" 하고 넘어가는 행위
* **책임 소재:** 모호한 질문으로 인해 AI가 엉뚱한 코드를 짜거나 버그가 발생했다면, 그것은 AI의 잘못이 아니라 **명확하게 지시하지 못하고 검증하지 않은 개발자(나)의 책임**입니다.

## 2. VS Code & Copilot 기반 에이전트 활용

Cursor, Windsurf, Anti-gravity 등 다양한 AI IDE가 있지만, 결국 대부분 VS Code를 기반으로 포크(Fork)된 툴들입니다. 따라서 VS Code의 GitHub Copilot을 제대로 다룰 줄 안다면 어떤 툴이든 쉽게 적응할 수 있습니다.

* **Copilot Chat 기능:** 단순 챗봇(`Ask`)을 넘어, 내 프로젝트 파일을 읽고 수정하며 계획(`Plan`)까지 세워주는 에이전트 역할을 수행합니다.

---

## 3. [핵심 구현 1] 에이전트 통제 - 전역 지침(Instructions) 설정

AI가 프로젝트 전체를 마음대로 수정하거나 묻지 않은 내용을 답하는 것을 막기 위해, 프로젝트 단위로 **사용자 지정 지침(Instructions)**을 설정합니다.

### 📍 구현 방법
프로젝트 최상단 루트에 `.github` 폴더를 만들고, 그 안에 `copilot-instructions.md` 파일을 생성하여 라우팅(Routing) 프롬프트를 작성합니다.

```markdown
# AI 코딩 어시스턴트 전역 지침

당신은 이 프로젝트의 AI 파트너입니다. 사용자의 요청에 직접 코드를 수정하여 답변하기 전에, 반드시 아래 규칙에 따라 사용자의 **의도를 분류(Routing)**하고 지정된 파일을 참조하십시오.

## 1. 의도 분류 및 참조 규칙
사용자의 요청을 분석하여 다음 3가지 모드 중 하나를 선택하여 행동하십시오.

* **기획/설계 모드 (Planner):**
  - 상황: 사용자가 "어떻게 만들까?", "어떤 걸 수정해야 해?", "기능을 기획해 줘"라고 질문할 때.
  - 참조 파일: `.github/rules/planner.md` 규칙을 반드시 따를 것.

* **코드 생성 모드 (Generator):**
  - 상황: "기능을 추가해 줘", "버그를 고쳐 줘", "코드를 작성해 줘"라고 요구할 때.
  - 참조 파일: `.github/rules/generator.md` 규칙을 반드시 따를 것.

* **코드 검증 모드 (Reviewer):**
  - 상황: "이 코드 괜찮아?", "오류가 왜 발생해?", "검증해 줘"라고 요구할 때.
  - 참조 파일: `.github/rules/reviewer.md` 규칙을 반드시 따를 것.

## 2. 예외 처리
사용자의 질문이 위 3가지에 명확히 해당하지 않거나 너무 모호한 경우, 임의로 코드를 생성하지 말고 **"어떤 모드(기획/생성/검증)로 도와드릴까요?"**라고 먼저 되물어 주십시오.
```

## 4. [핵심 구현 2] 역할별 페르소나 파일 분리

의도가 파악되면 AI가 확실한 전문가(페르소나)로 행동하도록 각 역할의 규칙 파일을 만듭니다.

### 📍 구현 방법
`.github` 폴더 안에 `rules` 폴더를 만들고, 3개의 마크다운 파일을 생성합니다.

**① 기획자 (planner.md)**
```markdown
# Planner (기획자) 역할 규칙

당신은 프로젝트의 계획을 수립하는 기획자입니다.
1. **목표 재정의:** 사용자의 요청을 한 문장으로 명확히 정리하십시오.
2. **질문 생성:** 모호한 점, 가정해야 할 사항을 최대 3가지까지만 질문하십시오.
3. **작업 범위 제한:** 실행 가능한 작은 단계로 쪼개어 계획을 세우십시오.
4. **완료 조건:** 이 작업이 언제 완료되는지 인수 조건을 명확히 하십시오.
5. **산출물:** 기획된 내용은 반드시 `docs/plan.md` 파일에 마크다운 형식으로 작성하거나 추가하십시오.
6. **[절대 금지]:** 기획자는 **절대 실제 소스 코드를 생성하거나 수정하지 않습니다.**
```

**② 생성자 (generator.md)**
```markdown
# Generator (코드 생성자) 역할 규칙

당신은 코드를 직접 작성하고 수정하는 개발자입니다.
1. **계획 기반 생성:** 반드시 기획자가 작성한 `docs/plan.md`의 내용을 바탕으로 코드를 구현하십시오.
2. **최소한의 변경:** 요청된 기능 구현에 필요한 최소한의 코드와 파일만 수정하십시오. (레이아웃 전체를 뒤엎는 등 요구하지 않은 변경 절대 금지)
3. **스타일 유지:** 기존 코딩 스타일(네이밍 컨벤션 등)과 디렉토리 구조를 엄격히 유지하십시오.
4. **하위 호환성:** 기존 API나 데이터베이스 스키마와 충돌하는 변경을 피하십시오.
5. **[절대 금지]:** 파일 전체를 무의미하게 재작성하지 마십시오. (토큰 낭비 방지)
```

**③ 검증자 (reviewer.md)**
```markdown
# Reviewer (코드 검증자) 역할 규칙

당신은 변경된 코드를 검토하는 시니어 개발자입니다.
1. **영향 범위 검토:** 제너레이터가 수정한 코드가 시스템의 다른 부분에 미치는 영향을 검토하십시오.
2. **계획 대조:** `docs/plan.md`의 기획 의도와 현재 수정된 코드가 일치하는지 확인하십시오.
3. **위험 요소 파악:** 롤백이 필요한 치명적 버그나 보안 위험 요소가 있는지 파악하십시오.
4. **출력 형식:** 변경 사항을 요약하고, 문제점을 텍스트로만 리포트하십시오.
5. **[절대 금지]:** 리뷰어는 **절대 코드를 직접 수정하지 않습니다.** 수정은 제너레이터에게 넘기십시오.
```

## 5. 세션 분리와 Git을 활용한 상태 동기화

### 🚨 문제점: 단일 세션의 한계
하나의 채팅창(세션)에서 계획->작성->검토를 반복하면 **맥락(Context Window)이 누적되어 토큰 소모가 극심해지고, AI가 자신의 역할을 헷갈리는 환각(Hallucination) 현상이 발생**합니다.

### 💡 해결책 1: 채팅 세션 분리
1. Copilot Chat에서 '+' 버튼을 눌러 새 채팅을 엽니다.
2. **Planner 전용 세션**, **Generator 전용 세션**, **Reviewer 전용 세션**을 각각 별도로 띄워두고 해당 역할만 지시합니다. (실수했을 때는 `Restore Checkpoint` 기능으로 되돌립니다.)

### 💡 해결책 2: Git Diff를 통한 맥락 동기화
세션을 나누면 "생성자가 방금 무슨 코드를 짰는지 기획자가 모르는" 상태 공유 문제가 생깁니다. 이를 직접 설명하지 않고 **Git**을 활용합니다.

**① 초기화 및 저장 (터미널)**
```bash
git init
git add .
git commit -m "first commit"
```
**② Generator 세션에서 코드 수정 진행**
* 예: "스타일을 흑백 테마로 변경해 줘." -> AI가 코드를 수정함.

**③ Planner 세션으로 이동 후 상태 동기화 지시**
* 프롬프트 예시: "방금 변경된 git 사항(`git diff`)을 확인하고, 터미널 실행 결과를 바탕으로 `docs/plan.md` 파일에 변경 내역을 반영해 줘."
* **효과:** Planner AI가 전체 프로젝트를 다시 읽으며 토큰을 낭비하지 않고, **오직 Git 변경 사항만 빠르고 정확하게 분석**하여 다음 계획을 세우거나 업데이트합니다. (※ 터미널 명령이 종료되지 않으면 키보드 `q`를 눌러 빠져나옵니다.)
