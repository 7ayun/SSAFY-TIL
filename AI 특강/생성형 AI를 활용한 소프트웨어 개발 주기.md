# 🤖 [AI 특강] 생성형 AI를 활용한 소프트웨어 개발 주기

* **강연자:** 유신 교수 (KAIST 전산학부)
* **주제:** 대규모 언어 모델(LLM)의 원리와 에이전틱 AI가 소프트웨어 개발 주기에 미치는 영향

---

## 1. 대규모 언어 모델(LLM)의 작동 원리 🧠
LLM은 사람처럼 '생각'하거나 '추론'하는 것이 아니라, **강력한 통계적 언어 모델**입니다.

* **다음 토큰 예측 (Next Token Prediction):** 현재까지의 맥락(Context)을 바탕으로 다음에 올 가장 **자연스러운(확률이 높은) 단어**를 수학적으로 계산하여 뱉어내는 기계입니다.
* **코딩을 잘하는 이유:** 프로그래밍 언어 역시 자연어처럼 반복적이고 예측 가능한 패턴을 가집니다. 특정 맥락(예: `for`)이 주어지면 그다음에 올 자연스러운 코드(예: `i in range()`)를 통계적으로 산출하는 것입니다.
* **GPT의 의미:** * **G**enerative (생성형: 본 적 없는 새로운 문장/코드 생성)
  * **P**re-trained (사전 학습 완료)
  * **T**ransformer (구글이 발표한 모델 아키텍처)

---

## 2. 프롬프트 엔지니어링과 창발적 능력 🛠️
모델의 크기와 데이터가 커지면서, 훈련하지 않은 능력(번역, 요약, 추론 등)이 저절로 나타나는 **창발적 능력(Emergent Abilities)**이 발생했습니다. 이를 극대화하는 기법들은 다음과 같습니다.

* **인컨텍스트 러닝 (In-Context Learning):** 모델을 재학습시키지 않고, 프롬프트(대화 맥락) 창에 예시를 몇 개 던져주는 것만으로도 새로운 규칙을 학습하여 답변합니다. (Zero-shot, One-shot, Few-shot)
* **CoT (Chain of Thought):** "차근차근 생각해보자"라고 지시하여 중간 풀이 과정(스텝)을 강제로 생성하게 만듭니다. 중간 단계를 거치면 토큰 예측 확률이 정교해져 정답률이 비약적으로 상승합니다.
* **RAG (검색 증강 생성):** 모델이 모르는 최신 정보나 사내 비공개 데이터를 외부 DB에서 검색해 프롬프트에 끼워 넣어 답변하게 만드는 기술입니다.
* **ReAct (Reasoning + Acting):** LLM이 단순히 텍스트만 생성하는 것을 넘어, **외부 도구(계산기, 웹 검색 등)를 사용**할 수 있도록 계획하고 행동하게 만드는 기법입니다.

---

## 3. 에이전틱 AI (Agentic AI)의 등장 🤖💼
에이전트는 단순히 묻는 말에 답하는 챗봇을 넘어, **목표를 달성하기 위해 자율적으로 도구를 사용하고 행동하는 AI**입니다.

> **에이전트의 핵심 요소 = 자율성(Autonomy) + 숙련도(Proficiency, 도구 사용 능력)**

* **작동 방식:** 환경 인지(Perception) ➡️ 계획(Planning) ➡️ 도구 사용(Action)의 사이클을 반복합니다.
* **종류:** * **반독립적 에이전트:** 정해진 워크플로우 안에서만 움직임 (예: 자동 버그 탐지기)
  * **완전 자율 에이전트:** 로컬 PC의 파일 시스템이나 IDE에 직접 접근하여 마음대로 코드를 수정하고 터미널을 실행함 (예: Cursor, OpenDevin 등)

## 4. AI 시대의 소프트웨어 개발 주기(SDLC) 변화 🔄
코딩을 AI가 대신해 주면서, 기존 개발 주기(요구사항 ➡️ 설계 ➡️ 구현 ➡️ 검증 ➡️ 유지보수)의 중요도가 재편되고 있습니다.

1. **요구사항 (중요도 ⬆️):** 기계에게 명확히 지시하려면 요구사항을 극도로 정교하게 분석하고 문서화해야 합니다. 애자일 시대에 잠시 등한시되었던 '요구사항 문서화'가 다시 중요해질 것입니다.
2. **설계/아키텍처 (중요도 ⬆️):** 코딩(구현)이 자동화될수록, 어떤 시스템을 어떻게 조합할 것인지 '큰 그림'을 그리는 아키텍트의 역할이 핵심이 됩니다.
3. **구현 (자동화 됨):** 코드를 직접 작성하는 일은 과거의 기계어(어셈블리어)를 다루는 것과 같은 취급을 받게 될 것입니다. 코드는 '안 쓸수록(적을수록)' 좋습니다.
4. **검증 (병목 구간 ⚠️):** 테스트를 완전히 자동화하는 것(완전한 오라클 문제)은 불가능에 가깝습니다. 어떤 입력값에 대한 올바른 정답이 무엇인지는 결국 사람이 판단하고 검증 루프를 설계해야 합니다.
5. **유지보수 (패러다임 변화 ❓):** 코드를 생성하는 비용이 0에 수렴한다면, 기존 코드를 힘들게 고치기보다 **"그냥 새로 짜는 것"**이 더 저렴해질 수도 있습니다.

## 5. 개발자의 미래와 핵심 역량 🚀
AI가 모든 코드를 짜주는 시대에도 **우리가 여전히 코딩의 원리를 공부해야 하는 이유**가 있습니다.

* **사고 범위 문제 (Frame Problem):** AI는 상식이 없습니다. (예: '1년은 12월 31일까지다'라는 것을 굳이 알려주지 않으면 달력 코드를 짤 때 엉뚱한 로직을 생성할 수 있음). 결국 비즈니스 도메인의 경계와 상식을 정해주는 것은 사람의 몫입니다.
* **자동화의 역설:** 평소에 AI에게만 코딩을 맡기다가 치명적인 장애나 예외 상황이 발생했을 때, 코드를 볼 줄 모르는 개발자는 시스템을 통제할 수 없게 됩니다.
* **결론:** AI가 작성한 코드가 통계적 추론의 결과물(블랙박스)임을 이해하고, 이를 검증, 통제, 유지보수할 수 있는 능력을 갖추기 위해 **코드를 직접 짜보고 원리를 이해하는 경험은 결코 손해 보는 일이 아닙니다.**
