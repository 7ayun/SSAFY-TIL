## 1. 바이브 코딩이란

### 1-1. 정의 및 등장 배경

바이브 코딩은 엄격한 규칙 대신 **직관적인 흐름과 느낌으로 자연어를 통해 빠르게 코드를 작성**하는 방식이다. IDE 내 AI 에이전트가 파일 생성·수정까지 직접 수행하는 코딩 패러다임으로, 커서(Cursor), 윈드서프(Windsurf), 안티그래비티(Antigravity) 등 VS Code 포크 기반의 에이전트 IDE가 이를 대표한다.

세 도구 모두 VS Code 기반이므로, VS Code + Copilot으로 에이전트 통제 방법을 익혀 두면 어떤 도구로도 컨텍스트 전환 비용 없이 동일한 방식으로 사용할 수 있다.

> **강사님 강조**: 우리의 목표는 커서를 잘 쓰는 개발자, 윈드서프를 잘 쓰는 개발자가 아니다. AI 에이전트를 잘 다루는 개발자가 되는 것이다. 도구가 바뀌어도 방법론은 그대로다.

### 1-2. 바이브 코딩의 세 가지 위험 습관

```
1. 코드 변경 사항을 확인하지 않고 Keep(수용)하는 행위
2. 요청하지 않은 수정 사항이 포함되어도 그냥 넘기는 행위
3. 실행 테스트 없이 "잘 됐겠지" 하고 종료하는 행위
   → 3번까지 해당되면 문제 발생 시 책임 소재를 파악할 수 없다
```

> **강사님 강조**: AI가 잘못 만든 것이 아니다. 구조 없이 사용한 것이 문제다. 코드 한 줄을 써도 실행해서 정상 동작을 확인하는 것이 기본이다. 책임 소재는 명확하게 내게 있다.

## 2. VS Code + GitHub Copilot 에이전트

### 2-1. 에이전트 모드 특징

Copilot 채팅 패널의 **Agent 모드**는 현재 열린 프로젝트의 모든 파일에 대한 읽기·수정 권한을 갖는다. 요청에 따라 파일 생성, 코드 수정, 터미널 명령 실행까지 자율 수행한다.

| 모드 | 동작 | 코드 수정 |
|------|------|-----------|
| Ask (S) | 텍스트 응답만 반환 | 없음 |
| Plan | 작업 계획 수립 + 체크리스트 제공 | 없음 |
| Agent | 계획 + 코드 생성 + 파일 수정 | 있음 |

### 2-2. GitHub 계정 연동 및 사용 한도

Copilot은 GitHub 계정 기반으로 동작한다. VS Code 우측 상단 Copilot 버튼을 눌러 GitHub 계정으로 로그인하면 사용 가능 할당량이 표시된다.

> **강사님 주의**: 무료 계정은 채팅 메시지 사용량 제한이 있다. 실습 전체를 진행하면 약 46% 소진된다. 공용 PC 사용 후에는 반드시 VS Code에서 GitHub 계정 로그아웃을 진행해야 한다.

## 3. 전체 지침 파일 — copilot-instructions.md

### 3-1. 파일 위치와 역할

프로젝트 루트에 `.github/copilot-instructions.md` 파일을 생성하면, 해당 프로젝트에서 Copilot이 항상 이 파일의 지침을 따른다. **채팅 세션마다 페르소나를 다시 입력할 필요 없이** 파일 하나로 에이전트를 프로젝트 단위로 통제한다.

```
프로젝트 루트/
├── .github/
│   ├── copilot-instructions.md   ← 전체 지침 (라우팅 규칙 포함)
│   └── rules/
│       ├── planner.md             ← 플래너 역할 프롬프트
│       ├── generator.md           ← 제너레이터 역할 프롬프트
│       └── reviewer.md            ← 리뷰어 역할 프롬프트
└── docs/
    └── plan.md                    ← 플래너가 생성하는 계획서
```

### 3-2. 전체 지침 구성 요소

`copilot-instructions.md`에 포함해야 할 핵심 항목:

- **기본 원칙**: 요청에 바로 답변하기 전에 사용자 의도를 먼저 분류한다
- **라우팅 규칙**: 질문 유형에 따라 어떤 역할 파일을 참조할지 지정
- **제약 사항**: 한 번에 하나의 역할만 수행, 역할 간 혼합 금지
- **예외 처리**: 모호한 질문이면 역할을 추정해 실행하지 않고 재질문한다

```markdown
# 예시 — copilot-instructions.md 핵심 구조

## 기본 원칙
이 프로젝트의 AI 파트너로서 요청에 직접 답변하기 전에
사용자의 의도를 분류하라.

## 라우팅 규칙
- 기능 설계·계획 질문  → .github/rules/planner.md 참조
- 코드 생성·수정 요청  → .github/rules/generator.md 참조
- 코드 검증·리뷰 요청  → .github/rules/reviewer.md 참조
- 모호한 질문          → 어떤 모드로 도와드릴까요? 재질문

## 제약 사항
- 한 번에 하나의 역할만 수행한다
- 자의적으로 역할을 전환하지 않는다
```

> **강사님 팁**: 파일이 팀 프로젝트 레포에 포함되면 팀원 모두가 동일한 지침으로 에이전트를 사용하게 된다. 한 번 만들어 두면 재사용 가능한 팀 규칙이 된다.

## 4. 역할 파일 — planner / generator / reviewer

### 4-1. planner.md

플래너는 **코드를 작성하지 않고 계획만 수립**하는 역할이다. 사용자 목표를 한 문장으로 재정의하고, 불명확한 점을 최대 3개 이내로 질문한다. 작업 완료 조건(인수 조건)을 반드시 명시하고, 결과물은 `docs/plan.md`에 저장한다.

> **강사님 강조**: 인수 조건을 정의하지 않으면 에이전트가 판단하는 완료 기준이 사용자의 기대와 달라진다. 결과물이 발산하는 주요 원인이다.

### 4-2. generator.md

제너레이터는 **플래너가 작성한 plan.md에 정의된 변경 사항만** 구현한다. 최소한의 파일 수정만 진행하고, 기존 코딩 스타일과 디렉토리 구조는 변경하지 않는다.

금지 항목:
- 파일 전체 재작성
- 요청하지 않은 리팩토링
- API·데이터베이스 스키마의 하위 호환성을 깨는 변경

### 4-3. reviewer.md

리뷰어는 **코드를 직접 수정하지 않고 텍스트로만 피드백**을 제공한다. 변경 범위가 plan.md의 요구 사항을 초과하지 않았는지 검토하고, 위험 요소와 롤백 필요 여부를 판별한다.

```
리뷰어 출력 형식 예시:

[심각도: 치명] 로그인 상태 초기화 로직이 새로고침 시 실행됨
[심각도: 경고] generator.md 범위 외 CSS 파일 수정 발생
[개선 제안] LocalStorage 키 네이밍 컨벤션 통일 필요
```

## 5. 세션 분리 운영

### 5-1. 단일 세션의 한계 — 컨텍스트 누전

하나의 세션에서 플래너 역할로 계획을 세운 후 제너레이터 역할로 코드를 생성하면, 앞선 대화가 쌓이면서 **역할 판단 기준이 흐려지기 시작**한다. 대화가 길어질수록 할루시네이션 발생 확률이 증가하고, 토큰도 빠르게 소진된다.

> **강사님 강조**: 하나의 세션에 역할을 나눠 놔도 맥락이 계속 누전되면 고장이 난다. 작은 요청 범위라도 점점 재작성 유도가 커지고 결과물이 이상해진다.

### 5-2. 세션 분리 방법

새 채팅 세션을 열고 **세션 시작 시 역할을 고정**한다. 플래너 세션은 계획 수립만, 제너레이터 세션은 코드 생성만, 리뷰어 세션은 검증만 수행한다.

```
[플래너 세션]
- 시작 시: "너는 .github/rules/planner.md를 따르는 플래너야"
- 용도: plan.md 계획서 작성 및 수정

[제너레이터 세션]
- 시작 시: "너는 .github/rules/generator.md를 따르는 제너레이터야"
- 용도: plan.md 기반 코드 생성·수정

[리뷰어 세션]
- 시작 시: "너는 .github/rules/reviewer.md를 따르는 리뷰어야"
- 용도: 변경된 코드 검증 및 피드백
```

세션 간 인수인계는 **파일을 통해** 수행한다. plan.md에 플래너가 계획을 기록하면, 제너레이터 세션에서 해당 파일을 참조해 구현한다. LLM 채팅에서 세션을 3개 열어 운영하던 방식과 구조는 같으나, 에이전트가 파일을 직접 읽고 수정하므로 매번 내용을 복사해 붙여 넣지 않아도 된다.

### 5-3. 리스토어 체크포인트

Copilot 에이전트는 각 작업 시점의 **리스토어 체크포인트(Restore Checkpoint)** 를 자동 생성한다. 잘못된 세션에 지시를 보내거나 불필요한 변경이 발생했을 때, 해당 시점으로 되돌릴 수 있다. 단, 이미 소진된 토큰은 환불되지 않는다.

> **강사님 주의**: 세션 분리의 단점은 실수로 잘못된 세션에 지시를 보낼 수 있다는 것이다. 리뷰어 세션에 코드 수정을 요청해도 지침을 잘 지키는 경우 거절하지만, 그렇지 않을 수도 있다. 항상 어느 세션에 작업 중인지 확인하는 습관이 필요하다.

## 6. Git 기반 변경 관리

### 6-1. Git Diff로 변경 범위 추적

에이전트가 코드를 수정한 후 `git diff`로 변경 사항을 확인하면, 어떤 파일의 어떤 줄이 바뀌었는지 파악할 수 있다. 요청 범위를 초과한 수정이 있다면 해당 커밋을 분리하거나 롤백할 수 있다.

```bash
# 변경된 파일 목록 확인
git diff --name-only

# 특정 파일의 변경 내용 확인
git diff script.js
```

### 6-2. 작업 단위 커밋 전략

한 번의 Copilot 요청 = 한 번의 커밋을 원칙으로 삼으면, 나중에 문제가 생겼을 때 어느 지시로 어떤 변경이 발생했는지 추적할 수 있다. 로그아웃 기능 수정과 스타일 변경을 한 번의 에이전트 요청으로 처리하면, 두 변경이 동일 커밋에 섞여 롤백 단위가 불분명해진다.

> **강사님 강조**: 에이전트에게 두 가지를 한 번에 시키지 않는다. 하나 시키고, 변경 사항 확인하고, 커밋하고, 다음 요청을 보낸다. 그것이 안전한 바이브 코딩이다.
