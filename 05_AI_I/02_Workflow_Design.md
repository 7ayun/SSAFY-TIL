## 학습 목표

* AI를 단순 채팅 도구가 아닌 통제 가능한 어시스턴트로 다룰 수 있다
* 단일 세션 방식의 한계를 설명하고 역할 분리가 필요한 이유를 말할 수 있다
* 계획-생성-검증(계생검) 구조로 작업을 분해해 프롬프트를 설계할 수 있다
* 역할 프롬프트의 핵심 구성 요소(역할·목표·맥락·예시·출력 형식)를 작성할 수 있다
* 좋은 프롬프트와 나쁜 프롬프트의 차이를 실제 예시로 구분할 수 있다

## 1. AI 코딩 어시스턴트 등장 배경

### 1-1. 기존 개발 방식의 문제

개발자가 겪는 반복 작업의 핵심은 **컨텍스트 스위치(Context Switch)** 다. 공식 문서 확인, ChatGPT 질의, IDE 코드 작성, Gemini 재질의를 화면을 오가며 반복하는 것이 생산성을 떨어뜨린다.

AI 코딩 어시스턴트는 이 맥락 전환 비용을 줄이기 위해 등장했다. 초기 형태는 IDE 내 채팅 패널에서 LLM을 그대로 쓰는 수준이었지만, 현재는 파일 생성·수정까지 수행하는 에이전트 모드로 빠르게 진화했다.

### 1-2. AI 에이전트 구조

에이전트는 단순히 응답을 생성하는 LLM이 아니라, **목표를 향해 반복적으로 생각하고 행동하고 관찰하는 루프**를 갖춘 시스템이다.

```
사용자 요청
    → LLM 판단: 어떤 도구가 필요한가?
    → 도구 실행 (코드 작성, 파일 수정, 검색 등)
    → 결과 관찰: 요청과 일치하는가?
    → 일치 시 완료(Finish) / 불일치 시 재계획
```

> **강사님 강조**: 에이전트가 특별한 지시 없이 방임되면 시키는 대로 혼자 생각하고 혼자 실행하고 혼자 완료한다. 통제 구조 없이 쓰면 어디서 잘못됐는지 추적할 수 없다.

## 2. 프롬프트 엔지니어링

### 2-1. 프롬프트란 무엇인가

프롬프트는 단순한 입력이 아니라 **AI가 어떻게 출력할 것인지를 안내하는 인터페이스**다. 모델의 응답 품질은 프롬프트의 구조, 명료성, 맥락 정보에 크게 영향을 받는다.

LLM은 확률 기반으로 다음 토큰을 예측하므로, 좋은 프롬프트란 **예측 가능한 토큰의 범위를 원하는 방향으로 좁혀 주는 것**이다. 역할 설정만으로도 출력 가능한 단어의 통계적 확률 분포가 달라진다.

### 2-2. 나쁜 프롬프트 vs 좋은 프롬프트

```
# 나쁜 예 — 맥락 없는 단순 지시
노드 JS로 사용자 CRUD API 만들어 줘

# 좋은 예 — 제약 조건과 목적 명시
Node.js + Express 기반으로 사용자 CRUD API를 구현할 것이다.
- 입력 검증 포함
- RESTful 규칙 준수
- Jest 기반 테스트 코드 작성
- 코드 구조: 컨트롤러와 서비스 반드시 분리
```

좋은 프롬프트도 여전히 한계가 있다. 모델이 요구 사항 해석 → 설계 판단 → 코드 구현 → 테스트 작성을 **한 세션 안에서 혼자** 수행하므로, 각 단계의 중간 검증이 없다.

> **강사님 강조**: LLM이 혼자 짜고 혼자 검증한 결과물은 실제로 코드를 실행한 것이 아니다. 확률적으로 그럴듯한 코드를 만들어 낸 것이므로, 동일한 오류를 계속 반복할 수 있다.

### 2-3. 역할·맥락·목적·예시·출력 형식

좋은 프롬프트의 핵심 구성 요소:

| 요소 | 역할 | 예시 |
|------|------|------|
| 역할(Persona) | 출력 토큰 범위를 특정 도메인으로 제한 | "10년 경력 Python 개발자" |
| 맥락(Context) | 이전 상태나 프로젝트 배경 제공 | "현재 Django + DRF 기반 프로젝트" |
| 목적(Goal) | 달성해야 할 결과물 명시 | "알고리즘 코드의 예외 상황 분석" |
| 예시(Few-shot) | 출력 형식과 패턴 고정 | 원하는 답변 예시 1~3개 제공 |
| 출력 형식(Format) | 응답 구조와 길이 제한 | "3개 항목으로 요약, 마크다운 표 사용" |

> **강사님 팁**: 장문의 역할 지시는 세션 시작 시 한 번만 작성하고, 이후는 간단하게 요청해도 된다. 단, 대화가 길어질수록 초기 역할 설정이 흐려지므로 새 세션에서 다시 역할을 부여해야 한다.

## 3. 단일 세션의 한계

### 3-1. 컨텍스트 오염

하나의 세션 안에서 오답이 섞인 채팅이 쌓이면, 이후 응답의 기준이 되는 **컨텍스트가 오염**된다. LLM은 이전 잘못된 답변을 수정 없이 다음 토큰 예측의 근거로 삼는다.

```
# 단일 세션 문제 시나리오
1. CRUD API 코드 생성 (요청 A)
2. 비동기 로직 추가 (요청 B) → 요청 A의 맥락 유지
3. 에러 핸들링 강화 (요청 C) → 요청 A, B의 맥락 모두 유지
   → 어디서 어디까지 코드가 바뀌었는지 추적 불가
   → 이전에 추가한 핫픽스가 조용히 원래대로 되돌아갈 수 있음
```

### 3-2. 책임 위치 불명확

에이전트가 코드를 수정할 때 변경 범위가 너무 넓어지면 **어느 명령에 의해 무엇이 바뀌었는지 파악**하기 어려워진다. 이는 협업 프로젝트에서 특히 치명적이다.

> **강사님 강조**: 에이전트가 코드를 수정했을 때 "킵(Accept)" 버리는 습관이 생기면, 의도하지 않은 변경을 인지하지 못한다. AI가 잘못한 것이 아니라, 구조 없이 쓴 것이 문제다.

## 4. 계생검 — 계획·생성·검증 구조

### 4-1. 역할 분리의 원리

단일 LLM 세션에서 모든 작업을 처리하는 대신, **역할을 외부에서 나눠 주는 것**이 핵심이다. 여러 연구 논문이 이 방향을 지지한다.

- **Chain of Thought (2022)**: 중간 추론 단계를 명시해 성능 향상
- **Reflection**: 언어적 피드백으로 에이전트가 스스로 실수를 인지하는 구조
- **역할 분리 에이전트**: 계획·생성·검증을 별도 세션에서 독립 수행

### 4-2. 계생검 구조 설계

```
[플래너 세션]           [제너레이터 세션]      [리뷰어 세션]
역할: 요구 사항 분석    역할: 코드 구현        역할: 코드 검증
  ↓                       ↓                      ↓
요구 사항 문서 출력  →  코드 파일 생성     →  품질·오류 분석 보고
  ↑                                              ↓
추가 요구 사항 ←─────────────────── 개선 필요 항목 피드백
```

각 세션은 **독립적인 컨텍스트**를 유지한다. 제너레이터에서 코드를 수정하더라도 플래너의 요구 사항 맥락은 오염되지 않는다.

> **강사님 강조**: 계생검은 AI에게 책임 위치를 명확하게 만드는 구조다. 리뷰어가 비동기 처리 문제를 발견하면, 플래너에게 새 계획을 요청하고 제너레이터로 재구현하면 된다.

## 5. 역할 프롬프트 작성법

### 5-1. 역할 프롬프트 필수 요소

역할 분리 에이전트에서 각 세션에 부여하는 **역할 프롬프트(Role Prompt)** 에는 다음이 포함되어야 한다.

- **역할 선언**: "너는 [역할명]이다. [한 줄 설명]"
- **목표 정의**: 이 역할이 완수해야 하는 결과물
- **금지 사항**: 역할 범위를 벗어난 행동 명시 (예: 플래너는 코드를 작성하지 않는다)
- **입력 맥락**: 이전 단계에서 받아야 할 정보의 형식
- **출력 형식**: 다음 단계로 전달할 결과물의 구조
- **예시 (Few-shot)**: 대표적인 입출력 예시 1개 이상

### 5-2. 플래너·제너레이터·리뷰어 역할 프롬프트 구조

```
# 플래너 프롬프트 구조 (예시)
역할: 너는 소프트웨어 프로젝트 기획자다.
목표: 사용자의 요구 사항을 받아 기능 목록과 구현 순서를 작성한다.
금지: 코드를 직접 작성하지 않는다.
출력 형식: 마크다운 표 형식의 기능 목록 + 각 기능의 입출력 설명
예시: [사용자 스토리 → 기능 목록 변환 예시]

# 제너레이터 프롬프트 구조 (예시)
역할: 너는 시니어 백엔드 개발자다.
입력: 플래너가 정의한 요구 사항 문서
목표: 요구 사항에 따라 파일 단위로 코드를 구현한다.
금지: 요구 사항에 없는 기능을 임의로 추가하지 않는다.

# 리뷰어 프롬프트 구조 (예시)
역할: 너는 코드 리뷰 전문가다.
입력: 제너레이터가 생성한 코드 + 원래 요구 사항
목표: 코드 품질, 요구 사항 준수 여부, 잠재 오류를 분석한다.
출력: 심각도별 이슈 목록 (치명적 / 경고 / 개선 제안)
```

> **강사님 팁**: 역할 프롬프트는 한 번 만들어 프롬프트 라이브러리(Typing Mind 등)에 저장해 두면 재사용 가능하다. 새 세션 시작 시 저장된 프롬프트를 불러와 즉시 역할을 활성화한다.

## 6. 실습 환경 — Typing Mind

### 6-1. Typing Mind 특징

Typing Mind는 브라우저 기반 LLM 채팅 프론트엔드로, **대화 기록과 API 키를 로컬 스토리지에 저장**한다. 별도 백엔드 서버가 없어 API 키가 외부로 전송되지 않는다.

| 기능 | 설명 |
|------|------|
| 멀티모델 지원 | OpenAI, Google, Anthropic 등 API 키 연결 |
| 프롬프트 라이브러리 | 역할 프롬프트 저장 및 재사용 |
| 로컬 저장 | 대화 기록·API 키 모두 브라우저 로컬 스토리지 |

### 6-2. 보안 주의사항

> **강사님 주의**: API 키와 대화 내역이 로컬 스토리지에 저장된다. 공용 PC(강의장 등)에서 사용 후 반드시 로컬 스토리지를 삭제하고 자리를 이동해야 한다. 개발자 도구 → Application → Local Storage에서 확인 및 삭제 가능하다.

## 정리

| 구분 | 핵심 포인트 |
|------|-------------|
| AI 코딩 어시스턴트 등장 | 컨텍스트 스위치 비용 감소. 채팅 → 에이전트로 진화 |
| 에이전트 구조 | 생각(Reason) → 행동(Act) → 관찰(Observe) 루프 반복 |
| 단일 세션 한계 | 컨텍스트 오염, 변경 범위 추적 불가, 책임 위치 불명확 |
| 프롬프트 핵심 | 역할·맥락·목적·예시·출력 형식으로 토큰 예측 범위 제한 |
| 계생검 구조 | 플래너·제너레이터·리뷰어를 독립 세션으로 분리 |
| 역할 프롬프트 | 역할 선언, 금지 사항, 입출력 형식, 예시 포함 |
| 컨텍스트 보존 | 각 역할 세션 독립 유지 → 수정 시 해당 역할 세션에만 요청 |
| 재사용성 | 완성된 역할 프롬프트는 라이브러리 저장 후 재호출 |
