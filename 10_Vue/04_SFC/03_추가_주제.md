## 1. Virtual DOM (가상 DOM)

### DOM 직접 접근을 권장하지 않는 이유

Vue에서는 JavaScript의 DOM 접근 메서드를 **직접 사용하지 않는 것**을 권장한다.

```javascript
// ❌ Vue에서 사용 지양
document.querySelector('.title')
document.createElement('div')
element.addEventListener('click', handler)
```

대신, Vue의 **디렉티브**와 **ref()**로 대체한다.

| 직접 접근 | Vue 방식 |
|-----------|----------|
| `createElement` + DOM 삽입 | `v-if`로 렌더링 제어 |
| `querySelector` | 템플릿 `ref` 속성 + `ref()` 변수 |
| `addEventListener` | `@click`, `@input` 등 이벤트 디렉티브 |

이유는 **성능과 코드 예측 가능성** 극대화다. Vue는 내부적으로 Virtual DOM 시스템을 통해 DOM을 관리하는데, 외부에서 직접 건드리면 가상 DOM과 실제 DOM 간 불일치가 발생해 오동작이 생긴다.

### Virtual DOM이란?

가상 DOM은 실제 DOM의 모습을 그대로 복사해 **메모리 상에만 존재하는 JavaScript 객체**다.

```javascript
// vnode (가상 DOM 노드)의 개념적 표현
{
  tag: 'div',
  children: [
    { tag: 'h1', text: 'Hello' },
    { tag: 'p', text: 'World' }
  ]
}
```

### 내부 렌더링 과정

```
① HTML 템플릿
        ↓
② 렌더 함수 코드 (컴파일)
        ↓
③ Virtual DOM 트리 (메모리의 JS 객체)
        ↓
④ 실제 DOM에 마운트
        ↓
⑤ 컴포넌트 반응형 상태 변경 감지
        ↓
⑥ 새 Virtual DOM 생성 → 이전 Virtual DOM과 비교(diff)
        ↓
⑦ 변경된 부분만 실제 DOM에 패치(patch)
```

### Virtual DOM의 장점

| 장점 | 설명 |
|------|------|
| **효율성** | 실제 DOM 조작을 최소화, 변경된 부분만 업데이트 |
| **반응성** | 데이터 변경을 감지해 UI를 자동으로 갱신 |
| **추상화** | 개발자는 DOM 직접 조작 없이 컴포넌트·템플릿 중심으로 UI 설계 |

### DOM 직접 접근이 꼭 필요한 경우

`ref` 속성과 `ref()` 변수를 조합해 특정 DOM 엘리먼트에 접근할 수 있다.

```vue
<template>
  <input ref="input" />
</template>

<script setup>
import { ref, onMounted } from 'vue'

// 변수명은 템플릿의 ref 값과 반드시 일치
const input = ref(null)

onMounted(() => {
  console.log(input.value) // <input> 엘리먼트
})
</script>
```

반드시 `onMounted` 내에서 접근해야 한다. (마운트 전에는 `null`)

## 2. Composition API vs Option API

Vue는 컴포넌트를 작성하는 두 가지 스타일을 지원한다.

### Composition API (Vue 3 권장)

`import`해서 가져온 API 함수들로 컴포넌트 로직을 정의한다.

```vue
<template>
  <button @click="increment">{{ count }}</button>
</template>

<script setup>
import { ref, onMounted } from 'vue'

const count = ref(0)
function increment() { count.value++ }

onMounted(() => {
  console.log(`초기값은 ${count.value}`)
})
</script>
```

### Option API (Vue 2 방식)

`data`, `methods`, `mounted` 같은 **객체의 키**로 로직을 정의한다. Vue 3에서도 지원되나, Vue 2 프로젝트 유지보수 목적으로 남아있다.

```vue
<script>
export default {
  data() {
    return { count: 0 }
  },
  methods: {
    increment() { this.count++ }
  },
  mounted() {
    console.log(`초기값은 ${this.count}`)
  }
}
</script>
```

### 권장 사항

| 상황 | 권장 방식 |
|------|-----------|
| 규모가 있는 앱 전체 구축 | **Composition API + SFC** |
| 빌드 도구 없이 쓰거나 복잡성이 낮은 프로젝트 | Option API |

## 3. Single Root Element

모든 컴포넌트의 `<template>` 최상단에는 **하나의 루트 HTML 요소**를 작성하는 것이 권장된다.

```vue
<!-- ❌ bad — 최상위 요소가 2개 -->
<template>
  <h2>Heading</h2>
  <p>Paragraph</p>
</template>

<!-- ✅ good — div로 감싸 루트를 1개로 -->
<template>
  <div>
    <h2>Heading</h2>
    <p>Paragraph</p>
  </div>
</template>
```

Vue 3에서는 루트 요소가 여러 개여도 렌더링은 되지만, 가독성·스타일링·명확한 구조를 위해 단일 루트를 유지하는 것이 권장된다.

## 4. CSS scoped

### `scoped` 속성의 역할

`<style scoped>`를 사용하면 해당 컴포넌트 내부의 스타일이 **현재 컴포넌트 내부 요소에만 적용**되도록 범위를 제한한다.

```vue
<style scoped>
div {
  color: red;  /* 이 컴포넌트의 div에만 적용 */
}
</style>
```

`scoped`를 붙이지 않으면 스타일이 전역으로 적용되어 다른 컴포넌트의 동일 태그에도 영향을 미친다. 디버깅이 매우 어려워지므로 컴포넌트 스타일에는 항상 `scoped`를 사용한다.

### 부모 → 자식 스타일 전파 (예외)

`scoped`가 설정되어 있어도, **자식 컴포넌트의 최상위 요소(root element)** 에는 부모의 scoped 스타일이 예외적으로 적용될 수 있다.

```vue
<!-- App.vue -->
<template>
  <MyComponent />
</template>

<style scoped>
div { color: red; }   /* scoped지만 MyComponent의 최상위 div에도 영향 */
</style>
```

```vue
<!-- MyComponent.vue -->
<template>
  <div>   <!-- 이 최상위 div는 부모의 scoped 스타일도 받을 수 있음 -->
    <h2>MyComponent</h2>   <!-- 이 안쪽 요소는 영향 없음 -->
  </div>
</template>
```

이는 부모가 자식 컴포넌트를 **레이아웃할 때** (외곽 크기, 마진 조정 등) 필요하기 때문에 Vue가 의도적으로 허용한 동작이다.

> **권장 패턴**: 최상위 App 컴포넌트에서 레이아웃 스타일을 전역으로 구성하고, 나머지 컴포넌트는 모두 scoped 스타일을 사용한다.

## 5. Scaffolding (스캐폴딩)

스캐폴딩은 새로운 프로젝트나 모듈을 시작할 때 **초기 구조와 코드를 자동으로 생성**하는 과정이다.

건물을 지을 때 세우는 뼈대처럼, 개발을 바로 시작할 수 있도록 필요한 파일과 폴더 구조를 자동으로 만들어준다.

```bash
npm create vue@latest    # Vue 프로젝트 스캐폴딩
django-admin startproject mysite  # Django 프로젝트 스캐폴딩
```

### 관심사 분리 vs 파일 유형 분리

SFC에서 HTML/CSS/JS를 한 파일에 담는 것이 이상하지 않냐는 의문이 생길 수 있다. 이는 **파일 유형**(HTML, CSS, JS)이 아닌 **사용 목적**(하나의 컴포넌트)에 따라 코드를 묶는 것이기 때문이다.

- **파일 유형에 따른 결합**: HTML 파일 하나, CSS 파일 하나, JS 파일 하나 → 프로젝트가 커질수록 관련 코드를 찾기 어려워짐
- **사용 목적에 따른 결합**: Button 컴포넌트의 HTML + CSS + JS를 `Button.vue` 하나로 → 관련 코드가 한 곳에 모여 관리 용이

## 6. 패키지 관리 주의사항

| 주의사항 | 설명 |
|----------|------|
| `npm install` 실행 위치 | 항상 `package.json`이 있는 **프로젝트 루트 디렉토리**에서 실행 |
| `node_modules` 직접 수정 금지 | `npm install`로 언제든 재생성 가능, Git 관리 불필요 |
| `package.json`, `package-lock.json` 직접 편집 자제 | `npm install <패키지명>` 명령으로 자동 업데이트하는 것이 안전 |
| 문제 발생 시 재설치 | `node_modules` 삭제 후 `npm install` 재실행 |

```bash
# 패키지 재설치 방법
rm -rf node_modules
npm install
```
