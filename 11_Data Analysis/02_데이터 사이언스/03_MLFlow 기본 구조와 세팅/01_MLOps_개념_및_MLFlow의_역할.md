# [데이터 사이언스] MLOps 개념 및 MLFlow의 역할

---

## 1. MLOps란 무엇인가

MLOps(Machine Learning Operations)는 머신러닝 모델의 개발 과정과 실제 서비스에 적용되는 운영 과정을 통합하여, 개발부터 배포·모니터링·유지보수·재학습에 이르는 전 과정을 자동화하고 효율화하는 일련의 관행이다.

모델을 잘 학습시키는 것만으로는 끝나지 않는다. 배포하고, 서비스가 잘 도는지 모니터링하고, 시간이 지나면 재학습하고, 지속적으로 유지보수하는 사이클 전체를 자동화·효율화하려는 고민이 MLOps에 녹아 있다.

- **DevOps와의 비교**: DevOps가 소프트웨어의 개발과 운영을 연결하는 개념이라면, MLOps는 모델의 전체 생애주기(Lifecycle)를 관리하기 위한 자동화 체계라고 볼 수 있다.
- **협업 기능으로서의 MLOps**: 머신러닝뿐 아니라 DevOps, 데이터 엔지니어링 등 다양한 요소가 얽혀 있는 영역에서 공통되는 개념을 하나로 묶어 처리하는 협업 기능이다. 데이터 사이언티스트(모델 설계·실험), DevOps 엔지니어(배포·자동화), IT/인프라팀(전산·보안) 등이 함께 ML 기반 서비스를 관리할 수 있게 해준다.

## 2. 기존 머신러닝 프로세스의 한계

| 한계점 | 내용 |
|---|---|
| 데이터 품질·양 의존성 | 좋은 모델을 만들려면 고품질 데이터가 많이 필요하지만, 현실 데이터는 노이즈가 많고 불완전한 경우가 많아 성능 저하로 이어짐 |
| 특징 추출의 어려움 | 도메인 전문가가 직접 수동으로 피처(Feature)를 추출해야 하는 경우가 많아 비용·시간이 많이 소모됨 (예: 금융 사기 탐지에서 "짧은 시간 내 동일 장소 결제" 같은 피처) |
| 새로운 상황 대응 문제 | 모델은 학습한 데이터 범위 내에서만 정확한 예측이 가능함 (생성형 AI의 할루시네이션도 같은 맥락의 문제) |
| 모델 해석의 어려움 | 복잡한 모델일수록 내부 동작 방식을 이해하기 어려움 |
| 데이터 분포 변화(Data Drift)에 대한 민감성 | 시간이 지나며 데이터 패턴(신조어, 검색 패턴 등)이 바뀌면 기존 학습 모델의 성능이 자연스럽게 저하됨 |

이러한 한계를 극복하기 위해 딥러닝과 함께 MLOps 같은 새로운 접근법이 등장했다.

## 3. MLOps의 필요성

- **반복 실험의 체계화**: 수많은 하이퍼파라미터 조합, 전처리 방식, 피처 선택을 실험하면서 결과를 자동으로 기록해야 체계적인 개발이 가능
- **협업 효율성 향상**: 같은 실험을 반복하지 않도록 결과를 공유하고, 버전 관리를 통해 변경 사항을 추적
- **재현성 확보**: 동일한 코드 + 데이터 + 환경이라면 언제 어디서든(내 컴퓨터든 다른 서버든) 동일한 결과가 나와야 서비스나 연구에 의미가 있음
- **추적성 확보**: 어떤 실험 조건·환경에서 어떤 성능이 나왔는지 기록되어 있어야 결과를 분석하고 최적화 방향을 잡기 유리함

## 4. MLOps 전체 흐름

모든 시작은 **비즈니스 질문**(어떤 문제를 풀고, 어떤 가치를 만들 것인가)에서 출발한다.

```
비즈니스 질문
   ↓
모델 개발 (데이터 수집 → 전처리 → 피처 엔지니어링 → 모델 학습/평가, 반복)
   ↓
배포 준비 (실행 환경 구성, 리스크 점검, QA)
   ↓
운영 환경 배포 (CI/CD, 컨테이너화 등)
   ↓
모니터링 (성능·데이터 드리프트 확인) → 다시 모델 개선으로 피드백 루프
```

이 흐름을 4단계로 요약하면 다음과 같다.

| 단계 | 세부 내용 |
|---|---|
| 데이터 준비 | 데이터 수집, 전처리, 특성 엔지니어링 |
| 모델 학습 및 검증 | 모델 개발, 학습, 검증 |
| 모델 배포 | 배포 준비, 배포, 배포 전략 |
| 모델 모니터링 및 관리 | 성능 모니터링, 데이터 드리프트 감지, 모델 업데이트 |

## 5. 자동화 구조로서의 MLOps (CI / CT / CD)

- **CI (Continuous Integration, 지속적 통합)**: 코드(모델 스크립트, 파이프라인 등)가 변경될 때마다 자동으로 테스트를 수행해 코드 품질을 보장
- **CT (Continuous Training, 지속적 학습)**: 데이터가 변하거나 성능이 떨어지는 시점에 자동으로 재학습을 수행해 모델의 최신성을 유지. 정기적 스케줄 또는 이벤트 기반으로 동작하며, MLFlow 같은 실험 추적 도구와 함께 쓰면 특히 효과적
- **CD (Continuous Delivery, 지속적 배포)**: 학습이 완료된 모델을 자동으로 서빙 환경에 배포. REST API 형태, 클라우드 환경 등 다양하게 적용 가능

## 6. MLFlow란?

MLFlow는 **실험의 전체 생애주기(Lifecycle)를 관리하는 오픈소스 플랫폼**이다. 머신러닝 모델을 만들고, 실험하고, 배포하기까지의 과정을 체계적이고 재현 가능하게 관리해주는 도구다.

- **등장 배경**: 2018년 Databricks에서 개발. Databricks는 Spark를 만든 팀이 설립한 회사로, 최근 클라우드 영역에서 자주 언급된다.
- **특징**: 다양한 프레임워크에 독립적이며 설치가 간편한 오픈소스. 실험 기록, 모델 저장, 버전 관리, 배포를 하나로 지원한다.
- 흔히 **"머신러닝 실험의 Git"이자 "운영 자동화 도구"** 로 표현된다.
- 요즘의 클라우드 기반 MLOps 관리 서비스들도 내부적으로 MLFlow를 많이 사용한다.

### 붕어빵 장사로 이해하는 MLFlow

MLFlow의 역할을 붕어빵 장사에 비유하면 이해가 쉽다.

| 붕어빵 장사 | MLFlow 개념 |
|---|---|
| 반죽 100g, 팥 100g, 굽는 시간 1분처럼 레시피를 바꿔가며 여러 번 시도 | 하이퍼파라미터를 바꿔가며 반복 실험 |
| 가장 맛있는 레시피를 발견 | 가장 성능 좋은 모델을 선택 |
| 실험 중 만들어진 붕어빵 | Artifact (이미지, 로그 등 산출물) |
| 맛·재료·칼로리 등 붕어빵 정보 | 메타데이터 |
| 팥, 슈크림, 김치 붕어빵을 동시에 판매 | 여러 모델을 동시에 운영 |

## 7. MLFlow가 필요한 이유 — 4대 컴포넌트

기존 머신러닝 운영에서 발생하는 문제점을 MLFlow의 4가지 컴포넌트가 각각 해결해준다.

| 기존 문제점 | 해결 방식 | 담당 컴포넌트 |
|---|---|---|
| 실험 추적의 어려움 | 학습에 사용된 데이터·설정을 자동으로 로깅하여 체계적으로 추적 | **Tracking** |
| 재현성 부족 | 코드·환경 설정·의존성을 표준화하여 패키징, 언제 어디서든 동일한 결과 보장 | **Projects** |
| 모델 배포의 복잡성 | 다양한 프레임워크(Scikit-learn, TensorFlow, PyTorch 등)로 만든 모델을 일관되게 패키징·배포 지원 | **Models** |
| 모델 관리의 비효율성 | 모델 버전, 상태, 주석 등을 중앙집중식으로 관리해 여러 협업자가 접근 가능 | **Model Registry** |

## 8. MLFlow의 장점

- **협업 향상**: 실험 데이터를 중앙에서 관리해 팀원들이 결과를 공유하고 협업할 수 있음
- **실험 추적 효율화**: 파라미터, 메트릭, 아티팩트 등의 로그를 자동으로 기록
- **재현성 강화**: 코드와 실행 환경을 패키징하여 동일한 조건에서 실험을 재현 가능. 이는 로컬 개발 환경과 실제 운영 서버가 다른 경우(SI 납품, 별도 운영 서버 등)에 특히 중요하다.
