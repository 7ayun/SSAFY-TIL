# [데이터 사이언스] A/B Test 예제

---

## 1. 실습 목표와 전체 흐름
A/B Test가 어떻게 동작하는지 개념을 이해했다면, 실제 구현 자체는 어렵지 않다. 핵심은 다음 세 가지다.
1. A/B 그룹 분할
2. 지표 비교
3. 통계적 검증 수행

전체 분석 흐름은 다음과 같다.

**데이터 → 그룹 분할 → 트래픽 균등성 검증 → 지표 계산 → 통계 검정 → 결론**

## 2. User-Level 데이터 구조
User-Level 데이터는 **사용자 한 명이 한 행(row)**을 차지하는 구조다. 각 사용자마다 몇 번 노출됐고, 몇 번 구매했고, 얼마를 썼는지가 하나의 행에 담긴다.

| 컬럼 | 설명 |
|---|---|
| user_id | 사용자 식별자 |
| impression | 노출 수 |
| purchase | 구매 수 |
| revenue | 매출 |
| converted | 전환 여부 (Boolean) |

**Conversion Rate**는 converted 값의 평균으로 계산한다.
- A 그룹 [True, False, True] → 66%
- B 그룹 [True, True, True] → 100%

## 3. 데이터 불러오기와 품질 확인
데이터를 불러온 뒤 가장 먼저 할 일은 품질 확인이다.
- 전체 데이터 개수, 중복 여부, 이상치·결측치 확인
- **논리적 일관성 확인**: 구매(purchase)가 있는데 전환(converted)이 False인 경우, 반대로 매출(revenue)이 있는데 전환이 안 된 경우처럼 앞뒤가 맞지 않는 데이터는 없는지 점검

## 4. Hash 기반 A/B 그룹 분할
사용자를 A/B 그룹으로 나눌 때는 **user_id 기반 해시**를 사용한다. (실습에서는 MD5 라이브러리 활용)

```python
import hashlib

def assign_variant(experiment_id, user_id):
    hash_input = f"{experiment_id}{user_id}"
    hash_value = int(hashlib.md5(hash_input.encode()).hexdigest(), 16)
    bucket = hash_value % 100
    return "A" if bucket < 50 else "B"
```

- 해시 결과를 0~99 사이 값으로 변환한 뒤, 0~49는 A(Control), 50~99는 B(Test)로 배정
- experiment_id를 함께 사용해 실험별로 관리 가능 (예: "결제 버튼 문구 변경" 실험)
- **같은 user_id는 항상 같은 그룹으로 배정되는지** 검증이 필요하다 → 동일 사용자를 반복 조회해 그룹이 바뀌지 않는지 확인
- 임의(랜덤)로 나누면서도 동일 사용자는 항상 고정되어야 하는 이유는, 실험 도중 그룹이 바뀌면 실험 자체가 깨지기 때문이다

전체 사용자에게 이 함수를 적용(apply)하면 각 사용자에게 variant(A/B)가 배정된다.

## 5. 트래픽 균등성 검증 (1-Proportion Z-test)
그룹을 나눈 뒤 가장 먼저 확인할 것은 **트래픽이 의도한 비율(50:50)대로 분배되었는가**이다.

실습 데이터에서 실제 분배 비율은 **A 49.98% : B 50.02%**로, 눈으로 보기엔 거의 차이가 없다. 하지만 이를 통계적으로 검증해야 한다.

- 귀무가설(H₀): B그룹 비율 = 0.5
- 대립가설(H₁): B그룹 비율 ≠ 0.5
- 유의수준 5% 기준값: **1.96**

여기서 사용하는 검정은 **1-Proportion Z-test**다. "1"이 붙는 이유는 독립된 두 그룹을 비교하는 것이 아니라, 하나의 관측 비율을 하나의 기대값(0.5)과 비교하기 때문이다. (독립표본 여부에 따라 검정 이름이 달라지는 것은 T-test에서도 마찬가지다.)

**결과**: Z-score = 0.0283, p-value가 충분히 크게 나옴 → 기대 비율에서 크게 벗어났다고 보기 어려움 → **트래픽이 정상적으로 분배됨**

## 6. Rollout 검증
트래픽 분배에 문제가 없음을 확인한 뒤에는 실제로 일부 트래픽부터 열어(Rollout)본다.
- 예: B 사용자 수의 10%만 우선 사용
- 확인 결과 실제 비율이 기대 비율에서 크게 벗어나지 않음을 재확인

이렇게 트래픽 검정을 먼저 하는 이유는, 새 기능을 처음부터 전체 사용자에게 노출하지 않고 일부 사용자에게만 노출해 리스크를 줄이기 위함이다.

## 7. Variant별 지표 집계
문제가 없다면 A/B 그룹별로 지표를 집계한다 (Variant 기준 group by).

| 지표 | A | B |
|---|---|---|
| 전환율(Conversion Rate) | 13.8% | 14.6% |

B가 A보다 약 **0.82%p** 높게 나타난다. 하지만 숫자상 차이가 있다고 곧바로 "B가 더 좋다"고 단정할 수는 없다. 이 시점에서는 "좋아 보인다" 정도까지만 말할 수 있으며, 통계적 검정이 필요하다.

## 8. 2-Proportion Z-test로 유의성 검정
A와 B의 Conversion Rate가 실제로 다른지 검정하기 위해 **2-Proportion Z-test**를 수행한다.

```
Z = (B전환율 - A전환율) / SE
```

- 이때 표준오차(SE)를 구할 때 두 그룹의 비율을 합친 **Pooled Proportion**을 사용한다.
- 1-Proportion Z-test와 2-Proportion Z-test의 차이는 이 Pooled Proportion을 사용하는지 여부에 있다.
- 계산 결과: **p-value = 0.4** (> 0.05), **|Z| < 1.96**

## 9. 결론
p-value가 0.05보다 크고 |Z|도 1.96보다 작으므로, **0.82%p 차이는 통계적으로 유의미하다고 말하기 어렵다.**

> B가 숫자상으로는 조금 높지만, 현재 데이터만으로는 B를 적용할 근거가 통계적으로 명확하다고 보기 어렵다.

이 예제를 통해 정리한 A/B Test 핵심 절차는 다음과 같다.
1. 데이터 확인 및 그룹 분할
2. 트래픽 균등성 검증 (1-Proportion Z-test)
3. Rollout으로 안전하게 확대
4. 그룹별 지표 집계
5. 지표 차이에 대한 통계적 검증 (2-Proportion Z-test)
6. 결론 도출
