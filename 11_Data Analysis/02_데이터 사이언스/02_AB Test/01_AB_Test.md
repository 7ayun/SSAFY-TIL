# [데이터 사이언스] A/B Test

---

## 1. 데이터 기반 의사결정이 필요한 이유
서비스를 운영하다 보면 "새로운 기능을 도입하면 정말 성과가 좋아질까?"라는 질문을 계속 마주하게 된다. 버튼 색깔 변경, 추천 알고리즘 변경, 체크아웃 UI 변경 등이 대표적인 예다.

문제는 의견만으로 결정할 때 발생한다.
- 기획자: "빨간 버튼이 눈에 잘 띈다"
- 디자이너: "파란색이 UX가 더 좋다"
- 개발자: "기존 디자인이 안정적이다"

각자의 주관적 판단이 부딪히면 무엇이 정말 더 나은지 증명할 방법이 없다. 그래서 **데이터 기반의 의사결정**이 필요하다.

## 2. 데이터 기반 의사결정의 네 가지 유형
| 유형 | 설명 | 예시 |
|---|---|---|
| 기술 통계 / 현황 분석 | 이미 발생한 데이터를 요약해 현상을 파악 | 지난달 매출은 얼마인가, 어떤 제품이 가장 많이 팔렸는가 |
| 탐색적 데이터 분석(EDA) | 특정 현상이 발생한 원인을 탐색, 데이터에서 패턴을 찾음 | 지역별 매출 차이가 있는가, 체류 시간이 길수록 구매율이 높은가 |
| 예측 분석(Predictive Analytics) | 과거 데이터를 기반으로 미래를 예측 (머신러닝 모델 활용, 100% 정확하지는 않음) | 특정 사용자가 구매할 확률, 이 고객이 이탈할 가능성 |
| 실험 기반 분석(Experimentation) | 변수를 의도적으로 변경해 그 변화가 결과에 미치는 영향을 측정 | 어떤 방법이 실제로 더 좋은 결과를 만드는가? |

A/B Test는 이 중 **실험 기반 분석**에 속하는 대표적인 방법이다.

## 3. 실험 기반 분석 방법의 종류
| 실험 방법 | 설명 |
|---|---|
| A/B Test | 두 버전 비교 |
| A/B/n Test | 여러 버전 비교 |
| Multivariate Test | 여러 요소 동시 실험 |
| Multi-Armed Bandit | 실시간 트래픽 최적화 |
| Holdout Test | 기존 시스템과 장기 비교 |

이번 강의에서는 이 중 **두 버전을 비교하는 A/B Test**를 다룬다.

## 4. A/B Test 기본 구조
- 실제 사용자를 대상으로 수행하는 실험
- 서비스의 기존 버전(**Control, A**)과 새로운 버전(**Test, B**)을 비교
- 사용자 트래픽을 **랜덤**으로 분할해 실험 진행 → 무작위 추출처럼 두 그룹의 표본 특성을 비슷하게 만들어 변경된 요소 외의 외부 변인을 통제하기 위함
- 두 그룹의 성과 지표(Metric)를 비교해 효과를 검증

**예시: 구매 체크아웃 페이지 A/B 테스트**
- 사용자 50% → A(기존/컨트롤): 구매 전환율 10%
- 사용자 50% → B(새로운/테스트): 구매 전환율 20%

겉보기엔 B가 훨씬 좋아 보이지만, 이 차이가 **우연**인지 **의미 있는 차이**인지는 별도의 통계적 검증이 필요하다.

## 5. 좋은 A/B Test 가설 만들기
A/B Test는 단순 비교가 아니라 **가설을 검증**하는 실험이다. 좋은 가설은 **변경 대상 → 기대 행동 변화 → 측정 지표**가 유기적으로 연결되어야 한다.

- 나쁜 예: "버튼을 바꾸면 좋아질 것이다" → 무엇을 어떻게 바꿔서 무엇이 좋아지는지 판단할 기준이 없음
- 좋은 예: "결제 버튼 문구를 바꾸면 구매 전환율이 증가할 것이다" → 변경 대상(버튼 문구) + 기대 행동 변화(구매 증가) + 측정 지표(구매 전환율)

가설과 검정할 지표는 **실험을 시작하기 전에** 먼저 정해야 한다. 실험이 끝난 뒤에 지표를 고르면, 원하는 결과가 나오는 지표만 골라버릴 위험이 있기 때문이다.

## 6. 실험 구조와 성과 지표
전체 실험 구조를 정리하면 다음과 같다.
- Control(A): 현재 서비스 버전 / Test(B): 변경된 새로운 버전
- 사용자 트래픽을 랜덤 분할하여 실험 수행
- 각 그룹의 성과 지표(Metric)를 비교

| 지표 | 계산식 | 의미 |
|---|---|---|
| CTR | Click / Impression | 관심 또는 반응 |
| CVR (Conversion Rate) | Converted Users / Users | 전환 성과 |
| Revenue per User | Revenue / User | 사용자당 매출 성과 |

이 지표들은 사용자 행동 흐름을 단계별로 파악하기 위한 것이므로 하나만 보고 판단하면 안 된다. 예를 들어 CTR(클릭률)은 올랐는데 CVR(전환율)이 오르지 않았다면, 겉으로는 좋아 보여도 실질적인 영향력이 없거나 오히려 매출이 나빠질 수도 있다.

A/B Test는 보통 실제 서비스가 돌아가는 **프로덕션 환경**에서 수행된다. 신규 런칭 서비스는 사용자 수가 적어 표본을 충분히 확보하기 어렵기 때문에 A/B Test에 적합하지 않을 수 있다. 또한 서비스 내에서 여러 A/B 테스트가 동시에 진행될 수 있고, 한 명의 사용자가 여러 실험에 동시에 포함될 수도 있다.

## 7. Primary Metric과 Guardrail Metric
| 구분 | 정의 | 예시 |
|---|---|---|
| Primary Metric | 실험의 성공 여부를 판단하는 핵심 지표 | 구매 전환율, 매출, 클릭률, ARPU |
| Guardrail Metric | 악화되면 안 되는 부작용을 확인하는 보호 지표 | 이탈률, 환불률, 페이지 로딩 시간, CS 증가, 객단가 하락 |

예를 들어 문구를 자극적으로 바꿔 클릭률(Primary)은 올랐지만, 이탈률·환불률·CS 문의(Guardrail)도 함께 늘었다면 이 실험은 성공으로 보기 어렵다. **클릭률이 올라도 구매율이나 매출이 떨어지면 성공이라고 보기 어렵다.**

## 8. A/B Test를 하는 이유
1. **효과의 객관적 측정** — 서비스 변경이 비즈니스 지표에 실제로 영향을 미치는지 가설 기반으로, 실제 사용자 데이터를 비교해 검증
2. **위험 최소화** — 새 기능을 전체 사용자에게 한 번에 적용하면 위험이 크므로, 일부 사용자에게 먼저 적용해 문제 발생 가능성을 확인
3. **빠른 실험과 개선(애자일)** — 작은 변화 → 실험 → 결과 분석 → 개선을 반복하며 제품 개선 사이클을 단축

## 9. A/B Test를 사용하면 안 되는 경우
- 브랜드 전략, 방향성처럼 데이터보다 비즈니스적 판단이 필요한 경우
- 데이터(표본)가 충분하지 않은 경우 → 유의미한 차이를 드러내기 어려움
- 버그 수정처럼 문제가 명확한 경우 → 실험 자체가 불필요
- 명확한 가설이 없는 경우
- 비교 대상(Control)이 없는 경우

## 10. A/B Test 프로세스와 Rollout
전체 프로세스는 **가설을 기반으로 실험을 설계하고 결과를 반복적으로 개선**하는 사이클이다.

1. **실험 제안 및 설계**: 가설 기반 실험 목적 정의, 영향 지표·신뢰수준 설정, 테스트할 기능/UI(MVP) 설계
2. **구현 및 QA**: 실험 기능 구현, 트래픽 분할 설정, 데이터 수집 확인
3. **배포(Rollout)**: 점진적으로 트래픽 확대
4. **결과 리뷰 및 반복 개선**: 실험 결과 분석 후 다음 실험 설계

**Rollout**은 한 번에 전체 사용자에게 적용하지 않고 단계적으로 확대한다.
- **스모크 테스트(Smoke Test)**: 1% 이하의 극소수 사용자에게 먼저 적용. 성과를 판단하기 위함이 아니라, 실험 설정이 정상적으로 동작하고 데이터 수집에 오류가 없는지 점검하기 위한 단계다.
- **중간 단계**: 문제가 없으면 트래픽을 25% → 50% → 100%처럼 점진적으로 확대
- **최종 단계**: 문제가 없다면 더 좋은 성과를 낸 Winner 버전을 전체 사용자에게 제공

이렇게 단계적으로 확대하는 이유는 리스크를 최소화하기 위함이다. 예를 들어 UI를 크게 개편할 때 전체 사용자에게 한 번에 적용하면, 문제가 생겼을 때 영향 범위가 지나치게 커진다.

## 11. A/B Test 분석에 필요한 데이터
| 구분 | 내용 |
|---|---|
| 사용자 실험 버킷(Bucket) 정보 | 사용자가 어떤 실험 그룹(A/B)에 속하는지. experiment_id, variant_id, user_id, timestamp 등을 로그 또는 RDB 형태로 기록 |
| 사용자 행동 데이터 (Funnel 정보) | 사용자가 실제로 한 행동. 노출, 클릭, 구매, 매출 등 |

수집된 로그 데이터는 보통 곧바로 분석에 쓰이지 않고, 데이터 웨어하우스나 데이터 레이크에 먼저 적재된 뒤 분석에 필요한 형태로 다시 꺼내어 사용된다.

## 12. 트래픽을 A/B로 나누는 방법
**어떤 ID를 기준으로 나눌 것인가**는 실험의 특성에 따라 선택한다.

| 기준 | 특징 |
|---|---|
| User ID | 로그인 사용자 기반. 사용자 단위로 일관된 실험이 가능. 로그인하지 않은 사용자에게는 적용 불가 |
| Device ID | 브라우저 쿠키·디바이스 정보 기반, 비로그인 사용자도 포함 가능. 더 많은 트래픽 확보가 가능하지만, 같은 사용자가 다른 기기·브라우저를 쓰면 다른 그룹으로 배정될 수 있음 |

**트래픽 분배 방식**

| 방식 | 설명 | 특징 |
|---|---|---|
| 사전 분배 | 모든 사용자를 미리 A/B 그룹으로 분배 | 로그인 사용자 기반 서비스에 적합. 신규·비로그인 사용자는 적용 어려움 |
| 동적 분배 | 사용자가 접속할 때 실시간으로 A/B 그룹 결정 | 로그인 여부와 관계없이 가장 일반적으로 사용. 여러 A/B 테스트가 동시에 실행되면 실험 간 상호작용(interaction)으로 결과가 왜곡될 수 있음 |

**Hash 기반 Bucketing**

완전한 랜덤 분배는 같은 사용자가 여러 번 방문할 때 매번 다른 그룹에 들어갈 위험이 있다(그러면 실험이 깨진다). 그래서 랜덤하되 일관성 있게 나누는 **해시 기반 버케팅**을 사용한다.

```
variant = hash(experiment_id + user_id) % 100
# 0 ~ 49  → Control (A)
# 50 ~ 99 → Test (B)
```

같은 사용자는 항상 같은 그룹에 배정되며, 실험 도중 그룹이 바뀌면 실험 자체를 신뢰할 수 없게 되므로 이 일관성이 중요하다.

## 13. Funnel(사용자 행동 흐름) 분석
일반적인 서비스의 행동 흐름은 다음과 같다.

**노출(Impression) → 클릭(Click) → 구매(Purchase) → 소비(Consumption)**

이 흐름을 Funnel이라고 하며, 각 단계에서 어떤 변화가 발생했는지를 통해 전환율 변화, 사용자 행동 변화, 기능의 영향을 분석할 수 있다. Funnel을 제대로 분석하려면 사전에 다음을 설정해둬야 한다.
- 측정하려는 목표
- 목표까지의 단계
- 데이터 트래킹 방식

이 설정이 없으면 데이터는 쌓이는데 정작 분석은 어려운 상황이 발생할 수 있다.

## 14. 실험 분석 = Bucket Data + Funnel Data Join
실제 분석은 "이 사용자가 A그룹인데 클릭을 했는가?", "B그룹인데 구매를 했는가?"처럼 그룹 정보와 행동 데이터를 사용자 단위로 결합해서 이루어진다. Bucket 데이터와 Funnel 데이터를 조인해 분석용 테이블을 만들고, 여기에 연령·성별 같은 메타 정보를 추가하면 더 다양한 관점에서 분석할 수 있다. (예: 전체적으로는 차이가 없어도 특정 연령대나 성별에서는 차이가 나는 경우가 있다.)

**분석 전 반드시 먼저 확인할 것: 트래픽 균등성**

A/B 그룹의 사용자 수가 의도한 비율대로 분배되었는지 먼저 확인해야 한다. 50:50 실험이라면 실제 비율 차이가 통계적으로 유의하지 않아야 한다.

| Metric | A | B |
|---|---|---|
| Users | 50 | 50 |
| 노출 | 120 | 115 |
| 클릭 | 10 | 15 |
| 구매 | 3 | 1 |
| 매출(원) | 90,000 | 30,000 |

## 15. A/A Test
A/B Test를 시작하기 전에 **시스템이 정상적으로 동작하는지** 검증하는 과정이다.
- 동일한 서비스를 두 그룹으로 나눠 비교 (A와 B가 완전히 동일한 형태)
- 트래픽이 50:50으로 잘 분배되는지, 로그가 정상 수집되는지, 지표 계산이 잘 되는지 등을 점검
- **모든 지표에서 통계적으로 유의미한 차이가 없어야 정상**

만약 A/A 테스트에서 차이가 발견된다면, 나중에 진행할 A/B 테스트에서 차이가 났을 때 그것이 실험(변경 요소) 때문인지 시스템 자체의 문제인지 헷갈릴 수 있다. A/A Test로 이를 미리 배제해두는 것이다.

## 16. A/B Test의 통계적 검증
A/B Test의 핵심 질문은 "B가 정말 더 좋은가, 아니면 우연히 좋아 보이는 것인가?"이다. 이를 판단하기 위해 **통계적 검정(Statistical Test)**을 사용한다.

A/B Test는 **귀무가설**에서 시작한다: A와 B는 차이가 없다고 가정한다. (예: A 전환율 = B 전환율, 즉 B - A = 0)

지표의 형태에 따라 사용하는 검정 방법이 다르다.

| 지표 형태 | 예시 | 사용하는 검정 |
|---|---|---|
| 비율(Proportion) 비교 | CTR, Conversion Rate, Traffic Split | Proportion Z-test |
| 평균(Mean) 비교 | 평균 구매 금액, 평균 체류 시간 | Two-sample T-test |

**정규분포를 사용할 수 있는 이유**

사용자가 B그룹에 속하는지 여부는 베르누이 분포를 따른다. 하지만 샘플 수가 충분히 많으면 **중심극한정리(CLT)**에 의해 표본 비율의 분포가 정규분포에 가까워지기 때문에 Proportion Z-test를 사용할 수 있다. 표본이 크면 Z-test, 작으면 T-test를 쓰는데, 표본이 커질수록 T-test 값도 Z-test에 가까워진다.

**Proportion Z-test 공식**
```
Z = (P - P₀) / √(P₀(1-P₀)/N)
```
| 기호 | 의미 |
|---|---|
| P | 실제 비율 |
| P₀ | 기대 비율 |
| N | 샘플 수 |

분모(표준오차)를 쓰는 이유는, 검정하는 대상이 통계량(평균, 비율)이기 때문에 그 통계량 자체가 얼마나 흔들리는지(변동성)를 기준으로, 실제 비율이 기대 비율에서 얼마나 떨어져 있는지를 표준화해서 판단하기 위함이다.

**해석**: Z-score가 **-1.96 ~ 1.96** 범위를 벗어나면 우연한 차이로 보기 어렵다 → 귀무가설 기각. 샘플 크기가 크거나 A/B 간 차이가 클수록 통계적 유의성이 커진다.

**트래픽 균등성 검증에 적용하면**
- 귀무가설(H₀): A/B 테스트가 정상 동작한다면 P(A) = P(B), 즉 P(B) = 0.5
- 대립가설(H₁): P(B) ≠ 0.5 → 트래픽 분배가 균등하지 않음

이 트래픽 균등성 검증은 **A/B Test 분석 전에 항상 가장 먼저 확인해야 하는 지표**다.

## 💡 한 줄 요약
> A/B Test는 두 버전을 실제 사용자에게 랜덤 분할해 비교하고, 그 차이가 우연인지 통계적으로 유의미한지 검증해 데이터 기반으로 의사결정을 내리는 실험 기법이다.
