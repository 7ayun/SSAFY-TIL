# [데이터 사이언스] 모델 관리 및 배포

---

## 1. MLflow Model Registry란

실험을 반복하는 것 자체가 목적이 아니라, 결국 **좋은 모델을 찾고 그것을 잘 관리·배포하는 것**이 최종 목적이다. MLflow는 실험 기록을 남기는 **Tracking Server**와, 모델 저장을 관리하는 **Model Registry**를 서로 연결해서 제공한다. 이 둘이 연결되어 있어 실험 결과를 바탕으로 바로 모델을 저장하고 배포하는 것이 가능해진다.

MLflow는 TensorFlow, PyTorch, scikit-learn, XGBoost, Spark 등 다양한 프레임워크와 호환되며, 각 프레임워크로 저장된 모델은 **Flavor**라는 형태로 관리된다.

## 2. 모델 스테이지 (Stage)

Model Registry는 모델을 단순 저장하는 것을 넘어, 모델이 현재 어떤 상태에 있는지를 **Stage**로 표현한다.

```
None(실험 단계) → Staging(테스트 환경 배포) → Production(서비스 배포) → Archived(더 이상 사용하지 않음)
```

| Stage | 의미 |
|---|---|
| None | 개발/실험 단계, 아직 검증 전 |
| Staging | 성능 검증을 마치고 테스트 환경까지 배포된 상태 |
| Production | QA를 통과하고 실제 서비스에 배포된 상태 |
| Archived | 새 모델에 밀려 더 이상 서비스되지 않는 상태 |

이렇게 버전 관리와 상태 관리가 동시에 이루어지므로, 어떤 모델이 현재 서비스 중인지 쉽게 파악할 수 있고 배포 안정성·롤백 가능성 측면에서도 관리가 용이하다.

## 3. 모델 버전 관리와 Alias

하나의 모델 이름 아래 여러 버전(version 1, 2, 3...)이 등록되며, 모델의 히스토리를 따라가거나 성능이 개선된 버전으로 점진적으로 교체할 수 있다.

최근에는 Stage 대신 **Alias**(자유로운 문자열 별칭)로 버전을 관리하는 경우가 많다.

```python
client.set_registered_model_alias("wine-quality", "staging", version=1)

model = mlflow.pyfunc.load_model("models:/wine-quality@staging")
```

Alias의 장점은, 실제 버전이 1에서 2로 바뀌어도 **코드에서 참조하는 이름(`@staging`)은 그대로 유지**할 수 있다는 점이다. 즉 서비스가 바라보는 지점을 코드 변경 없이 alias 재매핑만으로 바꿀 수 있어, 대부분의 저장소/서비스 전환 상황에서 널리 쓰이는 방식이다.

## 4. 모델 Flavor와 저장 구조

모델은 각 Run ID 기반의 디렉토리에 저장되며, 그 안에 다음 요소들이 함께 저장된다.

- **환경 정보**: 파이썬 실행 환경, 필요한 패키지 목록(`requirements.txt` 등)
- **모델 메타 정보(MLmodel 파일)**: 어떤 Flavor로 만들어졌는지, 어떻게 다시 불러올지에 대한 정보
- **실제 모델 파일**: 예) `model.pkl` (pickle/joblib 형태)

모델 파일 하나만 달랑 저장하면 나중에 그 모델이 어떤 환경에서 학습됐는지 알 수 없기 때문에, MLflow는 **모델 + 환경 정보 + 메타데이터를 함께 저장**하는 것을 원칙으로 한다. 이는 재현성과 협업 측면에서 중요한 특징이다.

## 5. 모델 저장(log_model)과 불러오기(load_model)

```python
# 모델 저장 (예: scikit-learn 모델)
mlflow.sklearn.log_model(model, "model")
```

`log_model`로 저장하면 실행 환경 정보와 함께 저장되어 Artifact에 자동 등록되고, UI에서도 해당 모델이 어떻게 만들어졌는지 확인할 수 있다.

```python
# Run ID 기반으로 모델 불러오기
model_uri = f"runs:/{run_id}/model"
model = mlflow.sklearn.load_model(model_uri)
```

다양한 프레임워크의 모델을 공통 인터페이스로 다루고 싶다면 `mlflow.pyfunc`를 사용할 수도 있다. 모델 저장 위치는 기본적으로 로컬 디스크지만, 팀 단위 공유가 필요하다면 클라우드 저장소(S3 등)로 지정할 수 있고, 메타데이터는 SQLite 같은 RDB에 별도로 저장하는 구성도 가능하다.

## 6. Signature: 입출력 스키마 검증

모델을 관리·배포할 때는 **Flavor 정보**뿐 아니라 **Signature(입출력 데이터 형태를 명확히 정의한 메타데이터)** 도 함께 담기게 된다.

Signature를 정의해두면, 이후 이 모델을 API로 호출하거나 추론할 때 입력 형식이 맞는지 자동으로 검증해준다. 즉, 이상한 데이터 타입이나 컬럼이 들어오면 그 시점에 막아주는 역할을 한다. 모델을 학습하고 `log_model`로 남길 때 `infer_signature` 등을 통해 입출력 형태를 함께 넘겨주는 방식으로 사용한다.

## 7. 모델 서빙: mlflow models serve

MLflow는 저장된 모델을 쉽게 서빙할 수 있는 명령어를 기본 제공한다.

```bash
mlflow models serve -m "models:/wine-quality/1" -p 5002
```

- 기본적으로 RESTful API 형태로 서버가 뜨며, 엔드포인트는 `/invocations`로 고정되어 있다.
- 이 엔드포인트에 컬럼명과 실제 데이터 값을 POST 요청으로 보내면 예측 결과를 받을 수 있다.
- 내부적으로는 Flask 기반이었으나 최근에는 FastAPI 기반으로 서빙 엔진이 제공된다.

서빙 환경을 구성할 때 고려할 점:
- 입출력 스키마가 복잡할수록 Signature를 명확히 지정해야 한다.
- 기본 제공되는 서버는 **단일 스레드 기반**이라 동시 요청 처리에 한계가 있으므로, 실무 배포 시에는 별도 서버로 감싸서 처리 성능을 확장하는 것이 일반적이다.
- Docker 기반으로도 서빙할 수 있어 컨테이너 이식성을 확보할 수 있다.

## 8. 배포 방식

| 방식 | 설명 |
|---|---|
| `mlflow models serve` | 간단한 추론 서버를 로컬/단일 서버에 직접 띄우는 방식 (FastAPI 기반) |
| Deploy 기능 | 클라우드 기반 서비스(SageMaker, Databricks 등) 또는 Kubernetes 클러스터 등 특정 플랫폼과 연동해 대규모 환경으로 배포 |

대규모 서비스나 고성능 처리가 필요할 때는 확장형 서빙 엔진과 연동할 수 있으며, 학습 단계에서는 우선 `mlflow models serve`로 직접 서버를 띄워 연결하는 방식을 다룬다.

## 9. 실습: Wine Quality 데이터로 실험 → 등록 → 배포

공개된 Wine Quality 데이터셋으로 RMSE를 최소화하는 회귀 모델(Keras 기반)을 학습하며, 학습률(learning rate)과 모멘텀(momentum)을 하이퍼파라미터로 Hyperopt 기반 튜닝을 진행하는 실습이다.

### 9-1. Nested Run + Hyperopt로 튜닝 실행

```python
from hyperopt import fmin, tpe, hp, Trials

def objective(params):
    with mlflow.start_run(nested=True):
        result = train_model(params, epochs, train_x, train_y, valid_x, valid_y)
        mlflow.log_params(params)
        mlflow.log_metric("val_rmse", result["val_rmse"])
        mlflow.tensorflow.log_model(result["model"], "model")
        return {"loss": result["val_rmse"], "status": "ok"}

space = {
    "lr": hp.loguniform("lr", -5, -1),
    "momentum": hp.uniform("momentum", 0.0, 1.0),
}

with mlflow.start_run(experiment_id="wine-quality") as parent_run:
    trials = Trials()
    best = fmin(
        fn=objective,
        space=space,
        algo=tpe.suggest,
        max_evals=8,
        trials=trials,
    )
```

- `objective`(목적 함수) 안에서 학습 → 검증 → 파라미터/메트릭 로깅 → 모델 저장까지 한 번에 수행된다.
- `space`는 하이퍼파라미터 탐색 범위, `algo=tpe.suggest`는 베이지안 기법(TPE) 사용을 의미한다.
- `max_evals=8`로 설정하면 총 8번의 시도(Trial)가 각각 하나의 **Child Run**으로, 전체 튜닝 과정은 하나의 **Parent Run**으로 기록된다.
- Experiment(`wine-quality`)는 사전에 생성되어 있어야 한다.

### 9-2. MLflow UI에서 결과 확인 및 Best Run 선택

- UI의 컬럼 설정에서 `eval_rmse`(또는 `val_rmse`) 지표를 표시해 각 Run을 비교한다.
- RMSE가 가장 낮은 Run을 Best Run으로 판단한다.
- 해당 Run에서 **Register Model**을 클릭해 모델을 정식 등록한다. (예: 모델명 `wine-quality`, 최초 등록 시 `version 1`)
- 등록 후에는 버전 관리, 설명/태그 추가, 어떤 실험(Run)에서 나온 모델인지 확인이 가능하다.

### 9-3. REST API로 배포 및 추론 요청

```bash
mlflow models serve -m "models:/wine-quality/1" -p 5002
```

curl을 이용한 요청:

```bash
curl -X POST http://127.0.0.1:5002/invocations \
  -H "Content-Type: application/json" \
  -d '{
    "columns": ["fixed acidity", "volatile acidity", "citric acid", "..."],
    "data": [[7.4, 0.7, 0.0, "..."]]
  }'
```

Python 코드로 요청:

```python
import requests

data = {
    "columns": [...],  # 와인 데이터셋의 컬럼명
    "data": [[...]],   # 예측하고자 하는 실제 값
}

response = requests.post("http://127.0.0.1:5002/invocations", json=data)
print(response.json())
```

응답으로 받은 `predictions` 값은 Wine Quality 데이터셋 기준 0~10 스케일의 예측 점수(예: 약 6점대)로 나타난다.
