# [데이터 엔지니어링] Kafka Producer

---

## 1. Kafka 구조 복습 (토픽 · 파티션 · 오프셋 · 세그먼트)

- **토픽(Topic)**: 메시지를 저장하는 논리적 단위. 택배를 찾을 때의 "주소"와 비슷한 느낌으로, 어떤 데이터인지를 구분해주는 카테고리 역할을 한다.
- **파티션(Partition)**: 토픽에 담긴 메시지를 병렬로 처리하기 위한 단위. 큐(Queue)와 유사하며, 택배 창고처럼 실제 데이터가 나뉘어 저장되는 공간이다.
- **오프셋(Offset)**: 파티션 내 메시지의 순서를 나타내는 고유 번호. 데이터가 들어올 때마다 0부터 증가하며 한 번 부여되면 변경되지 않아 파티션 내 순서를 보장한다.
- **세그먼트(Segment)**: 파티션이 실제로 저장되는 물리적 단위(파일 형태). 일정 주기가 지난 데이터를 삭제할 때 세그먼트 단위로 처리하면 훨씬 효율적이기 때문에 이렇게 나눠서 관리한다.

토픽과 파티션은 1:N 관계이며, 파티션은 물리적으로 여러 브로커에 나뉘어 저장된다. 예를 들어 파티션 3개 · 브로커 3대 · 복제 팩터 3으로 구성하면, 각 파티션(P0, P1, P2)이 서로 다른 브로커에 리더로 배치되고 나머지 브로커에는 팔로워 형태로 복제본이 저장된다.

## 2. 클러스터 구성요소 (컨트롤러 · 주키퍼 · 레플리카)

Kafka의 브로커들은 모두 동등한 역할을 하는 것이 아니라, 클러스터 안에 두 개의 관리 축이 존재한다.

| 구성요소 | 역할 |
|---|---|
| 컨트롤러(Controller) | 클러스터의 내부 실행을 관장하는 "대장" 브로커. 장애 처리, 리더 파티션 선출 등 클러스터 전반의 실무를 책임진다. |
| 주키퍼(Zookeeper) | 클러스터를 관리하는 외부 관리자. 메타데이터 확인, 브로커 헬스체크(생사 확인), 컨트롤러 선정 등 컨트롤러보다 상위의 역할을 수행한다. |
| 레플리카(Replica) | 파티션의 복제본을 여러 브로커에 저장하는 방식. 하나의 리더(Leader)와 나머지 팔로워(Follower)로 구성된다. |

## 3. Producer란? — 메시지가 브로커까지 가는 3단계

**프로듀서(Producer)**는 Kafka의 토픽으로 데이터를 전송하는 클라이언트다. 로그, 사용자 이벤트, 센서 데이터 등 실시간으로 발생하는 다양한 외부 소스가 모두 프로듀서 역할을 할 수 있다.

Kafka Producer는 메시지를 바로 전송하는 것이 아니라 다음 3단계를 거친다.

```
[메시지] → 직렬화(Serialize) → 파티션 결정(Partitioner) → 압축(Compression) → RA 버퍼 저장 → 전송 스레드가 브로커로 전송
```

Kafka는 소량의 데이터를 한 건씩 처리하기보다, 대량의 데이터를 효율적으로 처리하는 것을 기본 목적으로 설계되었다. 그래서 메시지를 버퍼링해서 묶어 보내는 방식으로 성능을 극대화한다.

## 4. Producer Record의 구조

Kafka에서 데이터를 주고받는 기본 단위를 **레코드(Record)**라고 부른다.

| 필드 | 설명 | 필수 여부 |
|---|---|---|
| Topic | 전송될 Kafka 토픽 | 필수 |
| Value | 전송할 값(실제 데이터 내용) | 필수 |
| Key | 파티션을 지정할 키 값 | 선택 |
| Partition | 전송될 파티션 번호 | 선택 |
| Headers | 기타 메타 정보 | 선택 |
| Timestamp | 생성 시간(유닉스 타임스탬프) | 선택 |

예시: `Topic: UserAction`, `Value: "로그인 시도"`, `Key: "User 003"`, `Partition: 3`

Key를 로그인 이벤트처럼 사용자 ID 기반으로 지정하면, 같은 Key는 항상 같은 파티션으로 전송되어 **해당 사용자에 대한 이벤트 순서**가 보장된다. 파티션 내부에서는 순서가 보장되기 때문이다.

## 5. 직렬화(Serialization)와 역직렬화(Deserialization)

직렬화는 Kafka뿐 아니라 컴퓨터 전반에서 쓰이는 개념으로, 문자열·JSON 같은 고수준 데이터를 바이트 배열(저수준 표현)로 바꾸는 작업이다. Kafka 내부는 모든 메시지를 바이너리로 다루기 때문에, 프로듀서는 전송 전 Key와 Value를 각각 직렬화한다. 반대로 저장된 바이트 데이터를 다시 사람이 읽을 수 있는 원본 형태로 복원하는 과정을 **역직렬화**라고 한다.

직렬화를 거치는 이유:
1. 네트워크 전송에 유리하다.
2. 스토리지 저장이 더 빠르다.
3. 압축이 편리하다.
4. 무결성 검증 및 복구가 용이하다.

## 6. 파티션 선택 전략

프로듀서가 메시지를 보낼 파티션을 정하는 방식(파티셔너)은 여러 가지가 있다.

| 전략 | 방식 | 비고 |
|---|---|---|
| Round Robin | 파티션 1→2→3→1→2→3… 순서로 균등 분산 | 과거 기본값. 배치가 작게 쪼개져 전송 효율이 떨어지는 단점이 있음 |
| **Sticky (현재 기본값)** | 하나의 파티션에 최대한 몰아서 채운 뒤, 조건 충족 시 다른 파티션으로 전환 | 균등하게 분산되면서도(uniform) 배치를 꽉 채워 보내 전송 효율을 극대화 |
| Key Base | 키 값을 해시(Hash) 함수에 넣어 파티션 결정 | 같은 키는 항상 같은 파티션 → 키 단위 순서 보장. **사용 중 파티션 수 변경 금지** (해시 나머지 값이 달라져 순서 보장이 깨짐) |
| 파티션 지정 | 파티션 번호를 명시적으로 지정 | 프로듀서가 지정한 값이 **키 기반 해싱보다 항상 우선**되므로, 키 기반 순서 보장이 필요하면 함부로 사용하지 않는 것이 좋음 |

> 참고: Kafka는 파티션 개수를 늘리는 것은 가능하지만 **줄이는 것은 아예 막혀 있다.** 오프셋을 포함한 로그 구조가 고정되어 있어, 기존 파티션 데이터를 다른 파티션으로 재분배하는 로직 자체가 불가능하기 때문이다.

## 7. 압축(Compression)

프로듀서 설정에서 압축 옵션을 켜면, RA 버퍼에 저장되기 직전 단계에서 메시지가 압축된다.

| 포맷 | 특징 |
|---|---|
| gzip | 압축률이 높은 편 |
| Snappy | 구글이 만든 방식, 빠르고 가벼움 |
| LZ4 | 속도와 압축률 모두 준수한 중간 포지션 |

압축의 이점: 네트워크 전송 속도 향상, 브로커 저장 공간 절약, 그리고 레플리카 복제 시에도 압축된 상태 그대로 전송되므로 복제 속도까지 함께 개선된다.

## 8. RA 버퍼(Record Accumulator)와 배치 전송 조건

**RA 버퍼(Record Accumulator)**는 프로듀서 내부에서 파티션별로 메시지를 임시로 모아두는 큐(메모리 공간)다. 여기 쌓인 메시지 묶음을 **배치(Batch)**라고 부르며, 다음 세 조건 중 하나라도 만족하면 전송 스레드가 배치를 브로커로 흘려보낸다(**Drain**).

| 조건 | 의미 |
|---|---|
| `batch.size` | 배치(버퍼)가 지정한 크기만큼 꽉 찼을 때 |
| `linger.ms` | 배치가 다 차지 않아도 일정 시간이 지나면 그냥 전송 |
| `buffer.memory` | 프로듀서 전체가 쓸 수 있는 버퍼 총 메모리 한도가 부족해지면 강제 전송 |

**PiggyBack**: 조건을 만족하지 못한 배치가 있더라도, 같은 브로커를 향하는 다른 파티션의 배치가 전송될 때 함께 묶어 하나의 네트워크 요청으로 보내는 최적화 기법이다.

## 9. 전송 스레드(Sender Thread)와 Acknowledge(ack) 옵션

프로듀서 내부에서는 메인 스레드와 별도로 **전송 스레드**가 백그라운드에서 동작한다. 메인 스레드는 메시지를 RA 버퍼에 넣고 콜백만 등록한 뒤 바로 다음 작업으로 넘어가고(비동기), 실제 전송과 응답 확인은 전송 스레드가 전담한다.

- **동기(Sync) 전송**: 메시지가 브로커에 확실히 저장된 것을 확인할 때까지 대기. 안전하지만 느리고 배치 효율도 떨어져 거의 사용하지 않는다.
- **비동기(Async) 전송**: 응답을 기다리지 않고 다음 작업을 처리. Kafka의 기본 동작 방식이며, 콜백 함수로 성공 시 로그를 남기고 실패 시 재시도/예외 처리를 한다.

**ack(Acknowledge) 옵션** — 브로커로부터 얼마나 응답을 받아야 전송 성공으로 볼 것인가:

| 값 | 동작 | 특징 |
|---|---|---|
| `ack=0` | 브로커가 받았는지 확인하지 않음 | 가장 빠르지만 유실 가능성 가장 높음 |
| `ack=1` | 리더 브로커만 받으면 OK, 못 받으면 재전송 | 팔로워 복제 여부는 확인하지 않음 |
| `ack=-1` (all) | 리더 + 팔로워까지 모두 복제 확인 후 OK | 가장 안전하지만 가장 느림. **Kafka의 기본값** |

**`min.insync.replicas`**: `ack=-1`일 때 최소 몇 개의 복제본이 ISR(In-Sync Replica)에 존재해야 하는지를 지정하는 **브로커 측** 설정이다. 예를 들어 `min.insync.replicas=2`로 설정하면 리더 외 팔로워 최소 1대가 ISR에 포함되어야 ack를 준다. 반대로 팔로워가 느려져 ISR에서 빠지면, 리더 혼자 ISR에 남아 있어도 ack가 나갈 수 있다는 점은 유의해야 한다. 이 옵션이 있어야 "복제가 최소 조건을 못 채우면 아예 전송을 실패시켜라"는 보호 장치가 걸린다.

## 10. 멱등성 프로듀서(Idempotence Producer)

기본적으로 Kafka 프로듀서는 **최소 한 번(At-Least-Once)** 전달을 원칙으로 한다. 문제는 브로커에 메시지가 저장되었는데 ack 전송만 실패하는 경우, 프로듀서가 이를 실패로 오인해 재전송하면서 **중복 저장**이 발생할 수 있다는 점이다.

**멱등성 프로듀서(Idempotence Producer)**는 이 문제를 해결하기 위해, 메시지를 보낼 때 **Producer ID + Sequence Number**를 함께 전송한다. 브로커는 이미 처리한 조합인지 확인해서, 중복이면 저장하지 않고 "이미 받았다"는 ack만 다시 보내준다. 이를 통해 최소 한 번 전달을 사실상 **정확히 한 번(Exactly Once)**에 가깝게 만들 수 있다. (`enable.idempotence=true`로 설정, 현재는 기본 활성화)

## 11. 코드로 살펴보는 Kafka Producer (kafka-python)

```python
from kafka import KafkaProducer

producer = KafkaProducer(
    bootstrap_servers='localhost:9092',      # 브로커 주소
    value_serializer=lambda v: v.encode('utf-8')  # Value 직렬화(UTF-8 인코딩)
)

for i in range(5):
    producer.send('test-topic-1', f'Hello Kafka {i}')

producer.flush()  # RA 버퍼에 남아있는 메시지를 모두 강제 전송
producer.close()
```

- `bootstrap_servers`: 데이터를 보낼 Kafka 브로커의 위치
- `value_serializer`: Value를 어떤 방식으로 직렬화할지 지정 (문자열 UTF-8 인코딩 또는 `json.dumps(...).encode('utf-8')` 형태로 JSON 직렬화도 가능)
- `send(topic, value)`: 지정한 토픽으로 메시지 전송
- `flush()`: 버퍼에 남은 메시지를 모두 즉시 전송하도록 강제
- 별도로 토픽을 생성하는 명령을 실행하지 않아도 Kafka가 자동으로 토픽을 생성해준다. 다만 실무에서는 파티션 수·복제 개수 등을 명확히 지정해 토픽을 미리 생성하는 것이 좋다.
