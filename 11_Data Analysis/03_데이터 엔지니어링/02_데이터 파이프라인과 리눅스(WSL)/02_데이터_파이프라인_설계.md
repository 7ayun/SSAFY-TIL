# [데이터 엔지니어링] 데이터 파이프라인 설계

---

## 1. 파이프라인 설계에는 정답이 없다

데이터 엔지니어링 관점에서 아키텍처를 설계할 때는, 데이터를 단순히 "처리"하는 것을 넘어서 **수집부터 분석까지 하나의 구조로 이어지는 설계**가 중요하다. 전체 흐름은 크게 4단계로 볼 수 있다.

```
Source → Data Preparation(가공) → Target Data Storage(저장) → 분석(BI/ML 등 활용)
```

파이프라인 설계 방식은 온프레미스인지 클라우드인지, 실시간 처리가 필요한지, 비즈니스가 데이터를 얼마나 빠르게 처리해야 하는지 등 환경과 요구사항에 따라 달라지기 때문에 **정답이 없다.** 결국 핵심 기준은 "이 데이터를 언제까지, 얼마나 빠르게 처리해야 하는가"이다.

## 2. 배치 중심 설계 vs 스트리밍 중심 설계

이 기준에 따라 크게 두 방향으로 설계를 생각할 수 있다.

| 구분 | 배치 전용 설계 | 배치+스트림 병행 / 스트리밍 중심 설계 |
|---|---|---|
| 방식 | 일정 시간 동안 데이터를 모아 처리 | 데이터가 들어오는 즉시 처리 |
| 예시 | 하루 1회 매출 데이터 집계 | 사용자 클릭을 실시간 분석해 추천에 반영 |
| 단점 | 실시간성이 떨어짐, 즉시 반영 안 됨 | - |

실시간 처리가 필요한 경우를 해결하기 위해 대표적으로 참고하는 아키텍처가 **람다(Lambda) 아키텍처**와 **카파(Kappa) 아키텍처**다.

## 3. 람다(Lambda) 아키텍처

2011년에 제시된 아키텍처로, **배치 처리와 스트리밍 처리를 동시에** 사용하는 구조다.

```
                 ┌─→ 배치 레이어(Batch Layer) ──┐
데이터 소스 → Queue                              → 서빙 레이어(Serving Layer) → 조회
                 └─→ 스피드 레이어(Speed Layer) ─┘
```

- **배치 레이어**: 전체 데이터를 기반으로 정확한 결과를 만들어냄 (정확성 중시)
- **스피드/스트림 레이어**: 실시간으로 빠른 결과를 만들어냄 (실시간성 중시)
- **서빙 레이어**: 배치 레이어에 저장된 데이터를 빠르게 보여주기 위한 서비스 계층. 사용자가 쿼리하면 기본적으로 배치 기반 데이터를 제공하되, 필요시 스피드 레이어의 데이터를 결합해서 제공한다.

동작 흐름을 보면, 배치 레이어에서 테이블 갱신이 완료될 때까지는 스트림 레이어가 그 이후 유입되는 데이터를 실시간으로 저장·정제해 보완한다. 이후 배치 시점이 되면 전체 데이터를 다시 계산해서 정확한 결과로 덮어쓰는 방식으로 동작한다.

- **장점**: 정확성과 실시간성을 동시에 잡을 수 있다.
- **단점**: 같은 데이터를 배치·스트리밍 두 곳에서 각각 처리해야 하므로 코드·로직·운영이 모두 이중화되어 구조가 복잡하고 운영 난이도가 높다.

> 람다 아키텍처는 하나의 컨셉을 제공하는 참고 모델일 뿐, 반드시 이 형태를 그대로 써야 하는 것은 아니다.

## 4. 카파(Kappa) 아키텍처

람다 아키텍처의 단점(이중 처리로 인한 복잡성)을 보완하기 위해 등장했다.

```
데이터 소스(주로 메시지 큐, 예: Kafka) → 스피드 레이어(스트림 처리) → 서빙 레이어
```

배치 레이어를 아예 없애고, 배치 레이어가 하던 일까지 **스피드 레이어 하나로 모두 처리**하는 구조다. 데이터 소스는 주로 Kafka 같은 메시지 큐를 사용하며, 과거 데이터를 다시 계산해야 할 경우에는 스트림을 다시 흘려보내 재처리한다.

- **장점**: 로직이 하나로 통일되어 구조가 훨씬 단순해진다.
- **단점**: 재처리 등 스트림 자체의 설계·구현 난이도가 배치 처리보다 높을 수 있다.

## 5. 람다 vs 카파 비교

| 구분 | 람다 아키텍처 | 카파 아키텍처 |
|---|---|---|
| 레이어 구성 | 배치 레이어 + 스피드 레이어 (이중) | 스피드 레이어 단일 |
| 데이터 처리 | 배치/스트림 각각 처리 | 스트림 처리로 통합 |
| 정확성 | 배치 레이어에서 정확한 결과 보장 | 재처리로 정확성 확보 |
| 구조 복잡도 | 높음 (코드·로직·운영 이중화) | 낮음 (단일 로직) |
| 대표 데이터 소스 | Queue | Kafka 등 메시지 큐 |

두 아키텍처 모두 반드시 지켜야 하는 규칙이 아니라 **참고 모델**이다. 모든 데이터를 하나의 아키텍처 형태로 만들 필요는 없으며, 파이프라인마다 데이터의 활용 요건을 분석해서 어떤 아키텍처를 따를지, 어떤 데이터 뷰를 쓸지 판단해야 한다.

## 6. 실전 예시: 종합 인터넷 쇼핑몰의 데이터 파이프라인

"종합 인터넷 쇼핑몰 사장"이라고 가정했을 때, 파이프라인이 실제로 어떻게 구성되는지 단계별로 살펴본다.

```
Sources → Ingestion & Transformation → Storage → Historical/Predictive → Output
```

### ① Sources (소스)
고객 정보, 제품 정보, 행동(클릭) 정보, 구매/결제 로그 등 서로 다른 시스템에서 데이터가 발생한다. 이 단계에서는 정제·가공 없이 발생한 그대로 가져온다.

### ② Ingestion and Transformation (수집 및 변환)
소스에서 내용을 추출하고, 저장에 적합한 형태로 변환한다. 예를 들어 여러 테이블/로그에 흩어져 있던 정보를 `고객 ID, 제품 ID, 제품 카테고리, 가격, 구매 여부`처럼 하나의 필요한 형태로 통합한다. 수집 시에는 데이터가 끊기지 않고 안정적으로 모이는 것이 중요하다.

### ③ Storage (저장)
가공된 데이터는 성격에 따라 저장 위치가 갈린다.
- 가공이 끝난 데이터 → **데이터 웨어하우스**
- 아직 가공되지 않은 데이터 → **데이터 레이크**로 넘겨 이후 처리

### ④ Historical & Predictive (분석)
- **Historical(과거 분석)**: 이미 쌓인 데이터를 기반으로 의미를 뽑아낸다. 예: "이번 주 인기 상품 TOP N"
- **Predictive(예측)**: 과거 데이터를 학습한 머신러닝 모델로 미래를 예측한다. 예: "이 고객이 다음에 살 가능성이 높은 상품은?"

같은 "인기 상품"이라도 **실시간 인기 상품**(지금 많이 클릭되는 것)과 **과거 데이터 기반 인기 상품**(일정 기간 안정적으로 많이 팔린 것)은 의미가 다르며, 이에 따라 처리 방식과 활용 전략도 달라진다.

### ⑤ Output (출력/활용)
분석된 결과를 대시보드로 시각화하거나 실제 서비스에 반영한다. 예: "금주 인기 상품 10% 할인 쿠폰 발급", "앱 메인 화면 노출" 등 비즈니스 액션으로 연결한다.

## 7. 파이프라인을 지탱하는 부가 요소

파이프라인이 잘 설계되어 있어도 아래 요소가 뒷받침되지 않으면 신뢰성 있는 데이터 분석이 어려워진다.

- **메타데이터 관리(Metadata Management)**: 데이터에 대한 정보를 체계적으로 관리
- **품질과 테스트(Quality and Testing)**: 데이터의 정확성·일관성을 검증
- **권한과 보안(Entitlements and Security)**: 접근 권한 및 보안 관리
- **모니터링(Observability)**: 각 단계의 상태를 실시간으로 체크

---

## 💡 한 줄 요약
> 데이터 파이프라인 설계에는 정답이 없으며, 람다·카파 아키텍처는 실시간성과 정확성 사이의 트레이드오프를 다루기 위한 참고 모델일 뿐이므로, 결국 비즈니스가 요구하는 처리 속도와 정확도 기준에 맞춰 설계를 선택해야 한다.
