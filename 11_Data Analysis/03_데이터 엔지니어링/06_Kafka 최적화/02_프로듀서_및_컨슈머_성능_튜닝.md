## 1. 직렬화(Serialization) 방식 선정

메시지는 네트워크로 전달되기 전에 반드시 직렬화를 거쳐 바이트 형태로 변환된다. 대표적인 직렬화 방식은 4가지다.

| 방식 | 특징 |
|---|---|
| StringSerializer | 단순 문자열 직렬화(UTF-8 인코딩). 눈으로 바로 확인 가능해 실습·간단한 테스트에 적합하지만 압축 효율이 낮음 |
| ByteArraySerializer | 데이터를 바이트 배열 그대로 전송. 다양한 형식 처리가 가능하고 빠르지만 가독성이 떨어져 디버깅이 불편함. 압축된 로그·바이너리 파일 전송에 유용 |
| JsonSerializer | JSON 형태로 직렬화. 가독성이 좋아 디버깅·테스트·로그 분석에 적합하지만 텍스트 기반이라 압축 효율이 낮아 운영 환경에서는 잘 쓰지 않음 |
| AvroSerializer | **Kafka 공식 권장 방식.** 스키마 기반으로 직렬화하며 압축 효율이 좋고 빠름 |

```python
# StringSerializer 예시 (kafka-python)
producer = KafkaProducer(
    bootstrap_servers='localhost:9092',
    key_serializer=str.encode,
    value_serializer=str.encode
)
producer.send('test-topic', key='my_key', value='Hello Kafka!')
```

### Avro + Schema Registry
- Avro는 데이터 구조(필드명·타입)를 **스키마**로 정의하고, 이 스키마를 별도로 구축한 **Schema Registry** 서버에 등록해서 사용한다.
- 프로듀서는 메시지 전송 시 등록된 스키마 ID를 함께 포함해 직렬화하고, 컨슈머는 이 스키마 ID로 Schema Registry에서 스키마를 불러와 자동으로 역직렬화한다.
- 스키마 ID만 포함시키므로 압축 효율이 높고, 스키마가 정해져 있어 직렬화 속도도 빠르다. 또한 버전 관리가 가능해 필드 추가/삭제가 있어도 이전 데이터와의 호환성을 유지할 수 있다.
- 사용 흐름이 복잡하고 Registry 서버를 별도로 운영해야 하는 부담이 있지만, 안정성과 효율 때문에 실무에서 널리 쓰인다.

```python
# Schema Registry 없이 Avro 스키마만 사용하는 예시
from fastavro import parse_schema, schemaless_writer
import io

avro_schema = {
    "type": "record",
    "name": "User",
    "fields": [
        {"name": "name", "type": "string"},
        {"name": "age", "type": "int"}
    ]
}
parsed_schema = parse_schema(avro_schema)

record = {"name": "Alice", "age": 25}
bytes_writer = io.BytesIO()
schemaless_writer(bytes_writer, parsed_schema, record)
avro_bytes = bytes_writer.getvalue()

producer = KafkaProducer(
    bootstrap_servers='localhost:9092',
    key_serializer=str.encode,
    value_serializer=lambda v: avro_bytes  # 이미 직렬화됨
)
producer.send("avro-topic", key='user1', value=avro_bytes)
```

**직렬화 선택 기준**
- 빠른 개발 / 디버깅이 중요 → JSON
- 대용량 / 성능이 중요 → Avro
- 구조 없는 데이터(이미지, 압축된 바이너리 등) → ByteArray

## 2. 파티셔닝 방식 선정

프로듀서가 메시지를 어느 파티션으로 보낼지 결정하는 방식이다.

| 방식 | 특징 |
|---|---|
| Key 기반 파티셔닝 | 해시 기반. 같은 key를 가진 메시지는 항상 같은 파티션으로 가서 순서를 보장한다. 단, 키 분포가 한쪽으로 쏠리면 특정 파티션에만 부하가 몰릴 수 있어 해시 알고리즘을 함께 점검할 필요가 있음 |
| 특정 파티션 지정 | 바이트 배열 그대로 원하는 파티션 번호로 직접 전송. 로드가 한 파티션에 몰려 병렬 처리 이점이 사라지므로 실제로는 거의 사용하지 않고, 테스트 용도로 주로 사용 |
| StickyPartitioner (기본값) | 파티션 하나에 배치를 최대한 채워서 보낸 뒤 다른 파티션으로 전환. Round Robin처럼 매번 하나씩 순차 배분하는 것보다 배치 활용도가 높아 네트워크 효율이 좋음. (Kafka 2.4→2.5 버전대에서 기본값으로 채택) |
| 커스텀 파티셔너 | 직접 로직을 정의해서 사용. `kafka-python` 라이브러리는 지원하지만, `confluent-kafka-python`은 내부적으로 C 라이브러리(librdkafka)를 감싼 구조라 커스터마이징이 불가능 |

```python
# Key 기반 파티셔닝
keys = ["user1", "user2", "user3", "user1", "user2"]
for i, key in enumerate(keys):
    producer.send('test-topic', key=key, value=f"Data {i}")

# 특정 파티션 지정
for i in range(5):
    producer.send('test-topic', value=f"Fixed Partition Data {i}", partition=0)

# 커스텀 파티셔너 (kafka-python)
class CustomPartitioner:
    def __call__(self, key, all_partitions, available_partitions):
        key_int = int(key.decode())
        return key_int % len(all_partitions)  # 짝수는 0번, 홀수는 1번
```

## 3. Batching 설정 최적화

프로듀서는 메시지를 한 건씩 보내지 않고 내부 버퍼에 쌓았다가 배치 단위로 전송한다. 이때 세 가지 설정을 함께 고려한다.

| 파라미터 | 설명 | 기본값 |
|---|---|---|
| `buffer.memory` | 프로듀서 내부에서 저장할 수 있는 전체 버퍼의 최대 크기 | 32MB |
| `batch.size` | 배치 하나의 크기. 다 차면 바로 전송 준비 | 16KB |
| `linger.ms` | 배치가 다 차지 않았을 때 얼마나 더 기다릴지에 대한 대기 시간 | 0(대기 없음) |

```python
producer = KafkaProducer(
    bootstrap_servers='localhost:9092',
    value_serializer=str.encode,
    buffer_memory=33554432,  # 32MB
    batch_size=32768,        # 16KB보다 크게 설정해 배칭 효율 증가
    linger_ms=5               # 5ms 대기 후 전송
)
```

- **전송량을 늘려야 할 때**(대규모 데이터, 실시간성 불필요): 버퍼·배치 크기·linger.ms를 모두 늘려 더 많이 모아서 보낸다.
- **전송량을 줄여야 할 때**(IoT 센서 데이터처럼 실시간 처리가 중요한 경우): 버퍼·배치 크기를 작게, linger.ms도 거의 0에 가깝게 유지해 즉시즉시 전송한다.
- `flush()`는 지금까지 쌓인 데이터를 조건과 무관하게 즉시 전송하라는 의미다.

## 4. Compression(압축) 방식 결정

| 방식 | 압축률 | 처리 속도 | CPU 사용량 | 특징 |
|---|---|---|---|---|
| Gzip | 높음 | 느림 | 높음 | 확실한 압축이 필요할 때 |
| LZ4 | 중간 | 준수 | 중간 | 압축률과 CPU 사용의 균형 |
| Snappy | 낮음 | 빠름 | 낮음 | 속도가 중요할 때 |

- 압축률이 높을수록 디스크 공간과 네트워크 트래픽을 아낄 수 있지만, 처리 속도가 중요한 경우 빠른 압축 방식이 유리하다.
- 압축 성능은 대상 데이터에 따라 달라지므로 수치 자체보다 "압축을 하는 것이 안 하는 것보다 나은가"를 실측으로 확인하는 것이 중요하다. 네트워크 대역폭이 병목이라면 압축이 확실히 유리하다.

```python
producer = KafkaProducer(
    bootstrap_servers='localhost:9092',
    compression_type='gzip',  # 'snappy', 'lz4'도 가능
    value_serializer=str.encode
)
```

## 5. Acknowledge(acks) 방식 결정

| 값 | 의미 |
|---|---|
| `acks=0` | 프로듀서가 전송 후 응답을 확인하지 않음 |
| `acks=1` | 리더 브로커만 메시지를 받으면 성공으로 간주 |
| `acks=all`(`-1`, 기본값) | 모든 복제본(ISR)이 메시지를 수신할 때까지 대기 |

- `acks=all`이 항상 안전한 것은 아니다. **ISR(In-Sync Replica)** 구성이 명확해야 하며, 이를 위해 `min.insync.replicas`로 정상 동작해야 하는 최소 replica 수를 함께 지정해야 한다. (예: replica 3개 중 2개는 반드시 in-sync 상태여야 전송 성공으로 처리)
- `min.insync.replicas`는 보통 `server.properties`(브로커 단위) 또는 토픽 생성 시 설정한다.

```python
producer = KafkaProducer(
    bootstrap_servers='localhost:9092',
    value_serializer=str.encode,
    acks='all'  # 또는 0, 1
)
```

```properties
# config/server.properties
min.insync.replicas=2
```

## 6. Transaction

- `kafka-python`은 트랜잭션 관리 기능이 없고, `confluent-kafka`(컴플루언트 카프카)에서 지원한다.
- 트랜잭션은 여러 메시지를 하나의 단위로 묶어 **EOS(Exactly Once Semantics, 정확히 한 번 처리)**를 보장하고 중복 전송을 방지하기 위해 사용한다.
- 트랜잭션 단위는 너무 짧으면 사용하는 의미가 없고, 너무 길면 병목이 발생하므로 적절한 길이로 관리해야 한다.

```python
from confluent_kafka import Producer

producer = Producer({
    'bootstrap.servers': 'localhost:9092',
    'transactional.id': 'my-transactional-producer',
    'enable.idempotence': True,
    'acks': 'all',
    'retries': 5,
    'max.in.flight.requests.per.connection': 5
})
producer.init_transactions()

producer.begin_transaction()
try:
    for i in range(5):
        producer.produce('tx-topic', key=f'key-{i}', value=f'value-{i}')
    producer.commit_transaction()
except Exception as e:
    producer.abort_transaction()
```

## 7. Retry 관련 옵션

| 파라미터 | 설명 | 기본값 |
|---|---|---|
| `retries` | 메시지 전송 실패 시 재시도 횟수 | INT_MAX(매우 크게 설정됨) |
| `max.in.flight.requests.per.connection` | Ack을 받지 않고 동시에 보낼 수 있는 요청 수 | - |
| `enable.idempotence` | 멱등성 프로듀서 설정(중복 전송 방지) | true |

- `max.in.flight.requests.per.connection` 값이 클수록 요청은 빨리 나가지만 리소스(커넥션) 사용량이 늘어난다.
- **멱등성 프로듀서**가 정상 동작하려면 세 조건이 함께 충족되어야 한다: 동시 요청 수가 일정 수준 이하일 것, 재시도가 충분히 설정될 것, `acks=all`일 것.

```python
producer = KafkaProducer(
    bootstrap_servers='localhost:9092',
    value_serializer=str.encode,
    retries=5,
    max_in_flight_requests_per_connection=1,
    enable_idempotence=True
)
```

## 8. [Consumer] Coordinator 설정 최적화

컨슈머 그룹은 브로커 중 하나인 **코디네이터**가 관리하며, 컨슈머는 하트비트(Heartbeat)로 살아있음을 알린다.

| 파라미터 | 설명 | 기본값 |
|---|---|---|
| `heartbeat.interval.ms` | 하트비트 전송 간격. 보통 `session.timeout.ms`의 1/3 수준 | 3초 |
| `session.timeout.ms` | 하트비트를 기다리는 시간. 이 시간이 지나도 응답이 없으면 컨슈머를 제거하고 리밸런싱 | 10초 |
| `max.poll.records` | 컨슈머가 한 번의 poll 호출로 가져갈 수 있는 최대 레코드 수 | 500 |
| `max.poll.interval.ms` | poll 호출 간 최대 허용 간격. 이 시간 내에 poll을 호출하지 않으면 다운된 것으로 간주해 리밸런싱 | 5분 |

- 세션 타임아웃이 10초, 하트비트 간격이 3초라면 대략 3번 정도 하트비트를 확인할 기회가 있는 셈이다.
- 처리 속도가 느린 컨슈머라면 `max.poll.interval.ms`를 넉넉히 늘려 불필요한 리밸런싱을 방지해야 한다.

```python
consumer = KafkaConsumer(
    'coordinator-test',
    bootstrap_servers='localhost:9092',
    group_id='group-1',
    auto_offset_reset='earliest',
    enable_auto_commit=False,
    max_poll_records=100,
    session_timeout_ms=15000,
    heartbeat_interval_ms=5000,
    max_poll_interval_ms=60000,
    value_deserializer=lambda v: v.decode('utf-8')
)
```

## 9. [Consumer] Fetching 방식 선정

| 파라미터 | 설명 | 기본값 |
|---|---|---|
| `fetch.min.bytes` | 가져올 최소 데이터 크기. Throughput과 비례, Latency와 반비례 관계 | 1 |
| `fetch.max.bytes` | 한 번에 받을 수 있는 최대 데이터 크기 | 50MB |
| `fetch.max.wait.ms` | 데이터가 모일 때까지 기다리는 최대 시간 | 500ms |
| `max.partition.fetch.bytes` | 파티션 하나당 가져올 수 있는 최대 데이터 크기 | 1MB |

- `fetch.min.bytes`를 키우면 한 번에 가져오는 데이터양이 커져 Throughput은 늘지만, 그만큼 브로커가 응답을 더 기다리게 되어 Latency는 늘어날 수 있다. → 실시간성이 중요하면 값을 낮게, 대량 처리가 중요하면 값을 높게 잡는다.

```python
consumer = KafkaConsumer(
    'fetch-test',
    bootstrap_servers='localhost:9092',
    group_id='fetch-group',
    auto_offset_reset='earliest',
    value_deserializer=lambda x: x.decode('utf-8'),
    fetch_min_bytes=1024,
    fetch_max_bytes=10 * 1024 * 1024,
    fetch_max_wait_ms=1000,
    max_partition_fetch_bytes=2 * 1024 * 1024
)
```

## 10. [Consumer] Partitioning(Assignor) 관련 설정

어떤 파티션을 어떤 컨슈머가 가져갈지 결정하는 전략이다.

| Assignor | 방식 |
|---|---|
| RangeAssignor (기본값) | 토픽당 N개씩 연속된 파티션을 순차 분배 |
| RoundRobinAssignor | 컨슈머 수에 맞춰 하나씩 순차 배분 → 균등 분배 |
| StickyPartitionAssignor | 기존 할당을 최대한 유지하며 변경 최소화 → 리밸런싱이 잦을 때 유리 |
| CooperativeStickyAssignor | Sticky를 기본으로 하되, 일부 컨슈머 변경 시에도 나머지 컨슈머는 계속 동작 → **Zero-Downtime 리밸런싱**, 가장 일반적으로 추천 |

```python
consumer = KafkaConsumer(
    'my-topic',
    bootstrap_servers='localhost:9092',
    group_id='group-A',
    auto_offset_reset='earliest',
    partition_assignment_strategy=[
        "org.apache.kafka.clients.consumer.CooperativeStickyAssignor"
    ]
)
```

## 11. [Consumer] Commit 관련 설정

| 파라미터 | 설명 | 기본값 |
|---|---|---|
| `enable.auto.commit` | 자동으로 offset을 커밋할지 여부 | true |
| `auto.commit.interval.ms` | 자동 커밋 시 커밋 간격 | 5초 |

- **자동 커밋의 위험성**: 메시지를 가져오기만 하고 처리를 완료하지 못한 상태에서도 주기적으로 offset이 커밋될 수 있다. 이 상태에서 컨슈머가 다운되면, 재시작 후 이미 커밋된 offset부터 읽기 때문에 처리하지 못한 메시지가 유실될 수 있다.
- **수동 커밋**: 정상 처리를 확인한 뒤 직접 `commit()`을 호출해, 처리 실패 시 이전 커밋 위치부터 다시 읽을 수 있게 해서 자동 커밋보다 안전하다.

```python
# 자동 커밋
consumer = KafkaConsumer(
    'auto-commit-topic',
    bootstrap_servers='localhost:9092',
    group_id='test-group',
    enable_auto_commit=True,
    auto_commit_interval_ms=5000,
    auto_offset_reset='earliest'
)

# 수동 커밋
consumer = KafkaConsumer(
    'manual-commit-topic',
    bootstrap_servers='localhost:9092',
    group_id='test-group',
    enable_auto_commit=False,
    auto_offset_reset='earliest'
)
for msg in consumer:
    print(f"Processing: {msg.value} (Offset: {msg.offset})")
    consumer.commit()  # 정상 처리 완료 후 커밋
```

**수동 커밋 전략 4가지**

| 전략 | 설명 | 적합한 상황 |
|---|---|---|
| Batch 단위 처리 | 일정 개수(예: 100개)가 모이면 처리 후 커밋 | 대용량 데이터 |
| 주기 처리 | 일정 시간 주기마다 커밋 | 실시간 로그, 모니터링 데이터 |
| 정상 처리 후 커밋 | 메시지 한 건마다 처리 확인 후 커밋 | 안전하지만 부하 높음. 금융 시스템 등 민감한 데이터 |
| 1+N Hybrid (Kafka 권장) | N개를 빠르게 처리한 뒤 마지막 메시지만 커밋. 실패 시 N개만 재처리하면 됨 | 안정성과 효율의 균형 |

## 12. [Consumer] `auto.offset.reset` 설정값

컨슈머 그룹이 처음 시작할 때, 커밋된 offset이 없다면 어디서부터 읽을지 결정하는 옵션이다.

| 값 | 의미 | 활용 |
|---|---|---|
| `earliest` | 가장 초기 offset부터 읽음 | 처음부터 다시 읽어야 할 때 |
| `latest` | 가장 마지막 offset부터 읽음 | 과거 데이터가 중요하지 않은 실시간 스트리밍·모니터링 |
| `none` | 커밋된 offset이 반드시 존재해야 동작(없으면 에러 발생) | 운영에서는 거의 사용하지 않고, 테스트·에러 상황 확인용 |

```python
consumer = KafkaConsumer(
    'my-topic',
    bootstrap_servers='localhost:9092',
    group_id='my-group',
    auto_offset_reset='earliest'  # 또는 'latest'
)
```
