# [데이터 엔지니어링] Kafka 개요

---

## 1. 메시징 시스템(Messaging System)이란?

애플리케이션 간에 데이터를 주고받을 때, **비동기적인 방식**으로 데이터를 전송하는 시스템을 메시징 시스템이라고 한다.

- **생산자(Producer)**: 메시지를 보내는 쪽
- **브로커(Broker)**: 메시지를 받아서 안전하게 보관하는 중간 관리자
- **소비자(Consumer)**: 브로커에서 메시지를 가져가는 쪽

핵심은 **보내는 시점과 받는 시점이 달라도 된다**는 것이다. 데이터를 보내는 즉시 상대가 읽어야 하는 게 아니라, 일단 브로커에 저장해두고 소비자가 원할 때 꺼내가는 구조다.

> **택배 보관함 비유**: 택배 기사님이 물건을 보관함에 넣고 가면, 수신자는 문 앞에서 바로 받는 게 아니라 시간이 될 때 보관함에서 꺼내간다. 여기서 보관함 역할을 하는 것이 브로커다.

메시지가 Queue 형태로 쌓인다고 해서 "메시지 큐"라고 부르기도 하는데, 엄밀히는 메시지 큐가 메시징 시스템의 하위 개념 중 하나다. 브로커가 없는 형태(Redis Pub/Sub, ZeroMQ 등)도 존재한다.

---

## 2. 왜 애플리케이션끼리 직접 통신하지 않고 메시징 시스템을 거치는가?

직접 통신(강한 결합) 방식은 빠르고 직관적으로 느껴질 수 있지만, 실제로는 두 가지 핵심 문제가 있다.

| 문제 | 강한 결합(직접 통신) 시 | 메시징 시스템(느슨한 결합) 도입 시 |
|---|---|---|
| **장애 전파** | 한쪽에 장애가 생기면 응답이 없어 전체 시스템이 같이 멈춤 | 한쪽에 장애가 나도 브로커에 메시지가 쌓여있어 복구 후 이어서 처리 가능 |
| **메시지 유실** | 받는 쪽 처리량 초과 시 처리 여부 확인이 어려워 유실 가능 | 브로커가 안전하게 보관하므로 유실 위험이 낮음 |

메시징 시스템을 두면 시스템 간 **결합이 느슨(loose coupling)** 해져서, 하나가 문제가 생겨도 나머지는 계속 동작할 수 있는 안정적인 구조가 된다.

또한 **확장성(Scalability)** 측면에서도 유리하다. 브로커를 하나만 늘려도 메시지를 보내는 것과 가져오는 것 모두 분산시킬 수 있어 성능이 선형적으로 증가한다. 이를 **수평 확장(Scale-out)** 이라고 하며, 처리량이 줄어들면 브로커 수를 다시 줄이는 식으로 유연하게 조절할 수 있다.

## 3. Kafka란?

Kafka는 대표적인 메시징 시스템이지만, 더 정확히는 **분산형 이벤트 스트리밍 플랫폼(Distributed Event Streaming Platform)** 이라고 표현하는 것이 맞다.

### 일반 메시지 큐와의 차이

| 구분 | 일반 메시지 큐 | Kafka |
|---|---|---|
| 메시지 소비 후 | 소비되는 순간 사라짐 | 로그처럼 계속 쌓아둠 (바로 삭제 X) |
| 다중 소비자 | 한 번 소비되면 끝 | 여러 컨슈머가 동일한 메시지를 반복해서 읽을 수 있음 |
| 구조 | Queue 기반 | 로그(Log) 기반 |

메시지를 읽었다고 바로 지우지 않기 때문에, 대시보드용 컨슈머와 다른 애플리케이션용 컨슈머가 **동시에 같은 데이터를 각자 읽어갈 수 있다**. 이런 특성 때문에 단순 메시지 큐가 아니라 "이벤트 스트리밍"이라는 표현을 쓴다.

### Kafka의 핵심 구성 요소

| 개념 | 설명 |
|---|---|
| **브로커(Broker)** | 카프카의 메시지를 관리하는 서버 |
| **클러스터(Cluster)** | 여러 브로커가 모여 함께 동작하는 집단 |
| **토픽(Topic)** | 메시지를 저장하는 **논리적 단위** (택배 주소 같은 개념, 카테고리) |
| **파티션(Partition)** | 토픽을 이루는 **실질적 저장 단위**, 파티션 기반으로 병렬 처리가 이루어짐 |

```
Kafka Cluster
┌───────────────────────────┐  ┌───────────────────────────┐
│        Kafka Broker       │  │        Kafka Broker       │
│  Kafka Topic   Kafka Topic│  │  Kafka Topic   Kafka Topic│
│ [Partition][Partition]... │  │ [Partition][Partition]... │
└───────────────────────────┘  └───────────────────────────┘
```

같은 토픽이라도 파티션이 여러 개면 각 파티션은 서로 다른 데이터를 나누어 저장한다(완전한 라운드 로빈은 아니지만, 이해를 돕기 위해 순서대로 분배된다고 생각하면 됨). 컨슈머는 여러 파티션에 대해 **병렬로 데이터를 읽어올 수 있어** 처리 속도와 확장성을 동시에 확보할 수 있다.

Kafka는 Java(JVM) 기반으로 개발되어 있어 실행을 위해 JVM 세팅이 필요하며, 여러 브로커로 구성된 클러스터가 정상 동작하도록 관리해주는 **Zookeeper**(분산 관리 시스템)가 함께 필요하다. (최신 버전에서는 Zookeeper 없이 동작하는 **Kraft 모드**가 권장되지만, 기존 운영 환경들이 Zookeeper 기반으로 많이 구성되어 있어 아직까지는 Zookeeper 기반 구조를 이해해두는 것이 실무에 유용하다.)

## 4. 데이터 파이프라인에서 Kafka의 역할

데이터 소스부터 아웃풋까지 이어지는 파이프라인에서 Kafka는 **Ingestion and Transformation(수집과 변환)** 단계, 그중에서도 **이벤트 스트리밍(Event Streaming)** 영역에 위치한다.

- 애플리케이션, CDC(데이터베이스 변경 감지), 로그 등 다양한 소스로부터 데이터를 **빠르게 수집**하고, **실시간으로 처리**하여 다른 시스템(Data Lake, 실시간 분석 시스템 등)으로 전달하는 역할을 한다.
- 이 관점에서 데이터를 보내는 쪽이 **Producer**, Kafka에 쌓인 데이터를 읽어가는 쪽이 **Consumer**가 된다.
- 저장소에서 데이터를 가져가는 것 외에도, 바로 다른 아웃풋으로 흘려보내는 등 다양하게 활용된다.

금융 데이터, 센서 값, 실시간 로그처럼 **끊임없이 발생하는 스트리밍형 데이터를 빠짐없이 수집·처리·전달**하는 데 강점을 가진 도구다.

## 5. Kafka를 쓰는 이유 (정리)

| 특징 | 설명 |
|---|---|
| **고성능** | 다양한 최적화를 통해 초당 수백만 개의 메시지 처리 가능 |
| **확장성** | 분산 구조로 브로커만 추가하면 수평 확장이 쉬움 |
| **내결함성** | 파티션의 복제본(Replica)을 여러 브로커가 나누어 가지고 있어 장애에 강함 |
| **메시지 유지** | 컨슈머가 읽어도 즉시 삭제하지 않아, 여러 컨슈머 그룹이 같은 데이터를 다시 읽을 수 있음 |
| **이벤트 기반 구조** | 여러 시스템이 동일한 데이터를 각자 읽고 처리할 수 있음 |

또한 DB에서 저장소로 바로 연결하는 대신 **DB → Kafka → 여러 시스템** 구조로 데이터 흐름을 분리해두면, 한 시스템의 장애가 전체를 멈추게 하지 않는다는 장점도 얻을 수 있다.

---

## 💡 한 줄 요약
> Kafka는 브로커·토픽·파티션 구조를 기반으로 대량의 실시간 데이터를 안정적으로 수집·분산 처리할 수 있게 해주는 분산형 이벤트 스트리밍 플랫폼이다.
