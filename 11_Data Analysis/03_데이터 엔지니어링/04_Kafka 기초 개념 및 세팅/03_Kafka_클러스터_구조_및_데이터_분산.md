# [데이터 엔지니어링] Kafka 클러스터 구조 및 데이터 분산

---

## 1. 클러스터를 구성하는 이유

Kafka는 브로커 하나만으로도 동작하지만, 여러 대를 묶어 클러스터로 운영하면 훨씬 큰 장점을 얻을 수 있다.

| 장점 | 설명 |
|---|---|
| **높은 Throughput** | 동시에 더 많은 데이터를 처리할 수 있음 |
| **데이터 안정성** | 복제(Replication)를 통해 데이터 유실률을 낮춤 |
| **고가용성(High Availability)** | 브로커 하나에 문제가 생겨도 전체 시스템은 멈추지 않음 |

여러 대의 서버를 병렬로 연결해 처리량을 늘리는 것을 **수평 확장(Scale-out)**, 한 대의 서버 성능 자체를 높이는 것을 **수직 확장(Scale-up)** 이라고 하는데, Kafka 클러스터는 수평 확장을 통해 처리량을 늘리는 방식이다.

복제본(Replica)을 두면 브로커 하나가 다운되어도 다른 브로커가 같은 데이터를 가지고 있으므로 서비스를 계속 유지할 수 있다. 즉, **처리량 증가 + 데이터 유실 위험 감소**를 동시에 달성하는 구조다.

---

## 2. 클러스터 관리의 복잡성

장점이 있는 만큼 관리해야 할 부분도 늘어난다.

- **공통 메타데이터 관리**: 브로커가 몇 개인지, 토픽이 몇 개인지, 토픽별 파티션이 몇 개인지 등을 중앙에서 관리해야 함
- **장애 대응 로직**: 팔로워 중 누가 새 리더가 될지, 컨트롤러는 누가 맡을지 등을 결정하는 로직 필요
- **분산 시스템 모니터링**: 네트워크 트래픽, 디스크 용량 등을 다중으로 모니터링해야 하므로 단일 서버 운영보다 복잡해짐

## 3. Zookeeper의 역할

Zookeeper는 Kafka 클러스터를 관리해주는 분산 관리 시스템(코디네이션 서비스)이다. 한마디로 "시스템을 위한 시스템"이라고 볼 수 있다.

| 역할 | 설명 |
|---|---|
| **공용 리소스 관리** | 브로커 수, 토픽 수, 파티션 수 등 공통 메타데이터/리소스를 중앙에서 관리 |
| **노드 Healthcheck** | 각 브로커로부터 하트비트(Heartbeat)를 주기적으로 받아 살아있는지 확인 |
| **리더/컨트롤러 선출 지원** | 메인 파티션인 리더 선출, 메인 브로커인 컨트롤러 선출을 도움 |
| **컨슈머 그룹 정보 저장** | 컨슈머 그룹 정보와 오프셋 정보를 관리 |

특정 브로커가 하트비트를 일정 시간 이상 보내지 못하면 Zookeeper는 해당 브로커가 죽었다고 판단하고 클러스터에서 제외한 뒤, 관련된 리더 재선출 등의 후속 조치가 이어진다.

> 참고: 최신 Kafka는 Zookeeper 없이 Kafka 내부에서 메타데이터를 처리하는 **Kraft 모드**를 권장하지만, 기존 운영 환경에는 Zookeeper 기반 구성이 여전히 많다.

## 4. 컨트롤러(Controller)

여러 브로커 중 하나는 클러스터 관리 및 장애 처리를 전담하는 **컨트롤러** 역할을 맡는다.

- 컨트롤러는 리더 선출, 파티션 배치 등 클러스터 전반을 관장하는 "브로커 대장" 역할이다.
- 각 브로커는 Zookeeper의 `/controller`라는 임시 노드(ephemeral znode)에 **가장 먼저 등록을 시도한 브로커**가 컨트롤러가 된다. 나머지 브로커는 등록에 실패하고 일반 브로커로 남는다.
- 다른 브로커들은 이 컨트롤러 노드를 계속 감시하고 있다가, 컨트롤러 브로커에 장애가 발생해 노드 등록 정보가 사라지면 나머지 브로커들이 다시 "내가 컨트롤러 할래"라며 등록을 시도하고, 가장 먼저 등록에 성공한 브로커가 새 컨트롤러가 된다.

```
Broker 1 등록 → /controller znode 등록 성공 → Controller
Broker 2 등록 → /controller 등록 실패
Broker 3 등록 → /controller 등록 실패
```

## 5. 리더-팔로워 데이터 분산

- **레플리카(Replica)**: 파티션 데이터를 보존하기 위해 만든 복사본
- **리더(Leader)**: Producer/Consumer와 직접 통신하는 메인 파티션(레플리카)
- **팔로워(Follower)**: 리더의 데이터를 실시간으로 복제해 가지고 있는 파티션(레플리카). 외부와 직접 통신하지 않음

### 리더 선출: 선호 리더(Preferred Leader)

파티션을 생성할 때, Zookeeper와 컨트롤러가 협력해서 각 파티션의 **선호 리더(Preferred Leader)** 를 기본적으로 **라운드 로빈(Round Robin)** 방식으로 지정한다. 클러스터가 처음 만들어질 때는 이 선호 리더에 맞춰 실제 리더가 결정된다.

```bash
./kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic test-topic
```

예시 결과(대괄호 안 숫자는 브로커 번호, 맨 앞이 선호 리더):

```
Partition A-1: [1, 2, 3]
Partition A-2: [2, 3, 1]
Partition B-1: [3, 1, 2]
Partition B-2: [1, 2, 3]
```

### 장애 발생 시 리더 재선출: ISR(In-Sync Replica)

리더가 있던 브로커가 다운되면 새로운 리더를 뽑아야 한다. 이때 기준이 되는 것이 **ISR(In-Sync Replica)** 목록이다. ISR은 리더 파티션과 **완전히 동일한 데이터를 가지고 있는 팔로워**들의 집합이다.

| 상황 | 처리 방식 |
|---|---|
| ISR에 속한 팔로워가 있는 경우 | ISR 목록 안에서 가장 순서가 빠른 팔로워가 새 리더로 승격 |
| ISR에 속한 팔로워가 없는 경우 | 리더가 복구될 때까지 대기 (서비스가 멈추는 대신, 정합성을 지키기 위해 기다림) |
| 서비스 중단을 감수할 수 없는 경우 | `unclean.leader.election.enable=true` 옵션 사용 시, ISR에 없더라도 그나마 가장 최신 데이터를 가진 팔로워를 리더로 승격 (데이터 정합성 일부 손실을 감수하고 서비스 가용성을 우선) |

즉, Kafka는 기본적으로 **데이터 정합성**을 우선시하여 ISR 안에서만 리더를 뽑지만, `unclean.leader.election.enable` 옵션으로 **가용성**을 우선시하도록 조정할 수도 있다. 이는 "시스템을 완전히 멈추기보다는 일부 데이터 손실을 감수하고 서비스를 살리겠다"는 판단이 필요할 때 사용한다.

**참고**: 장애가 났던 리더 브로커가 나중에 복구되더라도, 현재 리더가 정상적으로 동작 중이라면 자동으로 리더 자리를 다시 넘겨주지 않는다. 복구된 브로커는 팔로워로만 복귀한다.
