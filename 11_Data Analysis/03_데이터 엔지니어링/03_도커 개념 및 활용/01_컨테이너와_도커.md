# [데이터 엔지니어링] 컨테이너와 도커

---

## 1. 도커(Docker)란?

도커는 애플리케이션을 **컨테이너**라는 가볍고 독립적인 환경에서 실행할 수 있도록 도와주는 오픈소스 가상화 플랫폼이다. 핵심 키워드는 두 가지다.

- **컨테이너**: 독립적인 환경에서 실행할 수 있다는 특징
- **격리**: 외부 환경(PC 설정, 라이브러리 버전 등)과 완전히 분리된 상태에서 애플리케이션을 실행

일반적으로 프로그램을 실행하면 내 PC의 라이브러리나 설정에 영향을 많이 받는다. 도커를 사용하면 그런 외부 환경과 격리된 상태에서 애플리케이션을 실행할 수 있어서, **내 컴퓨터에서 잘 되면 다른 서버에서도 동일하게 동작**하도록 만들어준다. 이게 도커를 쓰는 가장 큰 이유다.

컨테이너를 생성·관리하기 위해 도커는 내부에 엔진과, 이를 명령어로 제어할 수 있는 CLI 도구로 구성되어 있다.

## 2. 컨테이너의 개념

컨테이너라는 단어 자체는 어떤 물체나 데이터를 **외부와 분리된 공간에 담아두는 것**을 의미한다. 격리된 상자를 떠올리면 된다. 이 안에는 애플리케이션, 라이브러리, 그리고 그것들을 사용하기 위한 실행 환경이 들어간다.

중요한 포인트는 **외부와 분리**되어 있다는 점이다. 내 PC 환경이 어떻든, 서버 환경이 어떻든 그 컨테이너 안에서는 동일하게 동작하게 만드는 것이 목적이다.

## 3. 컨테이너가 필요한 이유

| 이유 | 설명 |
|---|---|
| 환경 차이 없이 어디서든 실행 | 개발 PC, 테스트 서버, 클라우드 등 어디서 배포하든 동일하게 동작. "내 PC에서는 되는데 서버에서는 안 된다"는 문제를 크게 고려하지 않아도 됨 |
| 설치/설정 충돌 방지 | 하나의 서버에 여러 애플리케이션을 설치할 때 라이브러리 버전 충돌, 의존성 문제(예: PyTorch처럼 딸려오는 의존성이 많은 라이브러리, CUDA 버전 이슈 등)가 발생하기 쉬움. 컨테이너는 완전히 독립된 공간에서 실행되므로 여러 앱이 서로 영향을 주지 않고 안전하게 동시 운영 가능 |
| 빠른 실행과 이식성 | 가상 머신(VM)보다 훨씬 가볍고 빠르며 리소스도 적게 사용. 생성과 배포 모두 빠르게 처리 가능 |

## 4. 컨테이너 vs 가상 머신(VM)

겉으로는 비슷해 보이지만 핵심 차이는 **운영체제(OS)를 어떻게 쓰는가**에 있다.

- **가상 머신(VM)**: VM 하나하나마다 Guest OS가 들어간다. 즉 앱 하나를 실행하기 위해 OS를 통째로 하나 더 띄우는 구조 → 더 무겁고 느리고 리소스를 많이 잡아먹음
- **컨테이너**: Guest OS가 없다. 밑에 있는 Host OS를 공유하고, 그 위에서 도커가 컨테이너(애플리케이션)만 격리해서 관리 → 훨씬 가볍고 빠름

즉 VM은 OS까지 포함해서 통째로 격리하고, 컨테이너는 OS는 공유하되 애플리케이션만 격리한다. 이 OS 유무 차이 때문에 서비스 운영·배포 시 도커가 훨씬 더 많이 사용된다.

## 5. 도커의 아키텍처 (Client - Daemon - Registry)

도커는 크게 세 요소로 나뉜다.

- **Client**: 터미널에 명령어를 치거나 GUI를 조작하는 부분. 사용자가 직접 만지는 부분이며, 명령을 보내는 주체
- **Daemon(dockerd)**: 실제로 컨테이너를 만들고, 실행하고, 관리하는 역할을 수행하는 핵심 주체. 클라이언트가 명령어를 보내면 실제 작업은 여기서 처리됨
- **Registry**: 이미지를 저장해두는 저장소. 대표적으로 Docker Hub가 있음

전체 흐름: 클라이언트에서 명령어를 입력 → 데몬이 필요한 이미지를 확인(로컬에 없으면 레지스트리에서 받아옴) → 그 이미지 기반으로 컨테이너를 생성

이 흐름을 명령어로 보면 다음과 같다.

```
docker build   # 이미지를 생성 (Dockerfile 기반)
docker pull    # 레지스트리에서 이미지를 받아옴
docker run     # 이미지를 기반으로 컨테이너를 실행
```

## 6. 도커의 핵심 구성 요소

- **도커 엔진(Docker Engine)**: 도커의 중심이 되는 실행 시스템. 컨테이너를 실제로 생성하고 실행하는 역할. `dockerd`라는 데몬(서버)이 Docker API 요청을 받아 처리한다 (예: "컨테이너를 하나 만들어줘", "이 이미지를 실행해줘")
- **도커 클라이언트(Docker Client)**: 터미널에서 입력하는 도커 명령어가 여기 해당. 사용자가 입력한 명령은 내부적으로 도커 엔진에 전달되며, 실제 작업을 수행하는 것은 엔진이고 클라이언트는 요청하는 창구 역할

## 7. 도커 객체(Docker Objects)

도커에서 직접 다루는 주요 구성 단위다.

- **Image (이미지)**: 컨테이너를 만들기 위한 설계도 역할. 파이썬이 설치되고 코드가 들어 있고 실행 설정까지 세팅된 상태로, 실행 준비가 끝난 **정적인** 파일
- **Container (컨테이너)**: 이미지를 실제로 실행한 상태 = **동적인** 프로세스. 하나의 이미지로 여러 개의 동일한 컨테이너를 만드는 것도 가능하며, 각 컨테이너는 자신만의 파일 시스템과 프로세스를 독립적으로 가진다 (예: 같은 이미지로 서버 3개를 띄우면 컨테이너도 3개가 생성되고, 서로 격리된 상태로 각자의 파일 시스템을 가짐)
- **Service (서비스)**: 같은 역할을 하는 여러 개의 컨테이너를 묶어 하나의 서비스처럼 운영하는 단위(Docker Swarm, K8s). 예를 들어 웹서버 사용자가 많아져서 컨테이너를 3개, 5개로 늘릴 때 이 여러 컨테이너를 묶어서 보는 단위가 서비스다. (참고: 뒤에서 배울 Docker Compose에서도 "service"라는 용어가 나오는데, 거기서는 컨테이너 하나의 실행 설정 자체를 의미하므로 여기서 말하는 서비스와 헷갈리지 않도록 주의)
- **Registry (레지스트리)**: 이미지를 저장하고 공유할 수 있는 중앙 저장소. 대표적인 예가 Docker Hub이며, `pull`로 이미지를 내려받고 `push`로 자신이 만든 이미지를 업로드(계정 필요)할 수 있다

## 8. Dockerfile, Docker Image, Docker Container의 관계

세 개를 따로 보면 헷갈릴 수 있지만 순서로 보면 단순하다.

```
Dockerfile → (build) → Docker Image → (run) → Docker Container
   설계도                정적인 파일           동적인 프로세스
```

- **Dockerfile**: 이미지를 만들기 위한 설계도. 원하는 환경과 명령들을 스크립트 형식으로 작성 (어떤 OS를 쓸지, 어떤 파일을 복사할지, 어떤 명령어를 실행할지)

```dockerfile
# [Dockerfile]
FROM node:10.16.3
WORKDIR /app
ADD . /app
RUN npm install
CMD ["npm", "start"]
```

- **Docker Image**: Dockerfile을 빌드하면 만들어지는 실행 준비가 끝난 상태의 환경. OS(기반 계층), 소스코드, 의존성, 환경변수, 실행 명령어 등이 포함된 정적인 파일
- **Docker Container**: 이미지를 `docker run`으로 실행한 상태. 이미지의 복사본이 메모리에서 실행 중인 동적 프로세스이며, 각 컨테이너는 다른 컨테이너와 격리되어 자신만의 파일시스템과 프로세스를 가진다

## 9. 도커 사용 사례

- **개발 및 테스트**: 일관된 개발 환경 구축, 격리된 컨테이너에서 애플리케이션을 빠르게 테스트 ("내 PC에서는 되는데 다른 사람 PC에서는 안 된다" 방지)
- **마이크로서비스 아키텍처(MSA)**: 하나의 큰 서버 대신 여러 개의 작은 서비스로 나누어 운영. 컨테이너를 활용해 각 서비스를 독립적으로 배포하고 관리
- **지속적 통합/배포(CI/CD)**: 애플리케이션을 이미지로 패키징해 그대로 배포. 서버마다 환경을 직접 맞추고 설치하는 번거로움 없이, 내가 만든 실행 환경 그대로(컨테이너 상태 그대로) 배포 가능
- **빅데이터 및 머신러닝**: 의존성 문제를 많이 다뤄야 하는 분야인데, 도커로 묶으면 복잡한 환경 세팅 없이 바로 실행 가능 (예: Spark 같은 데이터 처리 프레임워크의 환경 구성 단순화)
