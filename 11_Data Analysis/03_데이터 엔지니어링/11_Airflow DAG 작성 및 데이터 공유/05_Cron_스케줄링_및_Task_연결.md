# [데이터 엔지니어링] Cron 스케줄링 및 Task 연결

---

## 1. DAG 스케줄, 핵심은 "실행 시각"이 아니라 "처리할 데이터 구간"

Airflow에서 가장 헷갈리기 쉬운 개념이 바로 시간(스케줄) 관련 개념이다. DAG 실행 시간을 **"언제 버튼을 눌렀는가"**로 생각하기 쉽지만, 실제로는 **"이번 실행이 어느 시간 구간의 데이터를 처리하는 실행인가"**로 이해하는 것이 핵심이다.

DAG 실행을 이해하려면 Airflow의 다음 네 가지 시간 개념을 정확히 이해해야 한다.

- `start_date`
- `logical_date`
- `schedule_interval` (스케줄)
- `data_interval`

```
schedule_interval
◄──────────────►
│              │  Task  │              │
2024.05.01    2024.05.02          2024.05.03    2024.05.04
13:00:00      13:00:00            13:00:00      13:00:00
start_date   data_interval_start  data_interval_end
             logical_date
```

---

## 2. start_date

- DAG이 **처리하기 시작할 데이터의 기준 시점**이지, DAG이 "실행되는 날짜"가 아니다.
- 첫 번째 `data_interval`의 시작점을 정의함
- DAG은 `start_date` **직후에 실행되지 않고, 해당 구간이 끝난 후에 처음 실행됨**
- 예: `start_date = 2025-01-01` → 첫 실행은 **2025-01-02 00:00**에 발생 (스케줄이 daily일 경우)
- 주의: `start_date`는 **미래 시점으로 설정하지 말아야** 함 — 문법적으로 틀린 것은 아니지만, 아직 데이터 구간(`data_interval`)이 완료되지 않아 스케줄 실행이 생성되지 않으므로 예상대로 동작하지 않을 수 있음

> 왜 `start_date`가 1월 1일인데 1월 1일에 실행되지 않을까? → Airflow는 "1월 1일에 실행할 작업"을 만드는 게 아니라, "1월 1일부터 시작되는 스케줄 구간 동안 쌓인 데이터를 처리하는 실행"을 만든다. 1월 1일의 데이터는 1월 1일이 다 지나야 완성되므로, 그 데이터 구간이 끝난 뒤(1월 2일 00시)에 실행이 생성되는 것이다. 데이터가 다 들어오기도 전에 처리해버리면 누락이나 정합성 문제가 생기기 때문에, Airflow는 **데이터 인터벌이 끝난 뒤에 DAG Run을 생성**한다.

## 3. logical_date

- 각 DAG Run을 식별하는 **논리적 날짜**
- `data_interval_start`와 동일하며, **어떤 데이터를 처리하는 run인지**를 나타냄
- **실제 실행 시간과는 다름** (예: `logical_date = 1월 1일` → 실행은 1월 2일 00:00 이후)
- 실행 시각은 스케줄러가 실제로 DAG Run/Task를 실행시킨 시각이고, `logical_date`는 그 실행이 담당하는 데이터 구간을 논리적으로 나타내는 기준 시각이다. (예: "어제 데이터를 집계했다"고 할 때, 그 "어제"가 바로 `logical_date` 기준)
- 참고로 이전 버전의 Airflow에서 쓰이던 `execution_date`가 지금의 `logical_date`와 같은 의미다.

### logical date 예시

DAG가 매일 실행되는 경우 (`schedule_interval = "@daily"`):

| Logical Date | DAG이 실행되는 실제 시간 (run_at) |
|---|---|
| 2025-03-01 | 2025-03-02 00:00:00 |
| 2025-03-02 | 2025-03-03 00:00:00 |
| 2025-03-03 | 2025-03-04 00:00:00 |

- Logical Date가 2025-03-01이면, DAG는 2025-03-02에 실행됨
- 항상 Logical Date보다 **늦게** 실행되므로 데이터 정합성을 유지하는 데 중요함
- 즉, 데이터가 모두 적재된 이후에 실행되므로 데이터 정합성을 보장

> `logical_date`와 `data_interval`은 수동 실행 시에도 존재하지만 스케줄 기반 계산이 아니므로, 수동으로 정확한 타이밍을 맞추기는 사실상 불가능하다. 이런 시간 개념은 자동 실행(스케줄러 기반) 기준으로 이해하는 것이 좋다.

## 4. schedule_interval (스케줄 간격)

- DAG이 실행되는 **주기를 결정하는 설정값**
- DAG이 얼마나 자주 실행될지를 정의하는 간격
- Cron 표현식 또는 예약어를 사용하여 주기를 정의
- DAG 실행 주기가 DAG의 `logical_date`(구 `execution_date`)를 결정함

### schedule_interval 설정 방법

| 설정 값 | 설명 |
|---|---|
| `None` | 수동 실행 (자동 실행 없음) |
| `@once` | DAG을 한 번만 실행 |
| `@hourly` | 매시간 실행 |
| `@daily` | 매일 자정(00:00)에 실행 |
| `@weekly` | 매주 일요일 00:00 실행 |
| `@monthly` | 매월 1일 00:00 실행 |
| `@yearly` | 매년 1월 1일 00:00 실행 |
| `"0 12 * * *"` | 매일 12시 정각 실행 (Cron 표현식 사용 가능) |

- Cron 표현식을 사용하여 맞춤형 실행 주기 설정 가능
- `schedule_interval=None` 설정 시 DAG는 자동 실행되지 않음

### Cron Schedule 표현

```
{분}{시}{일}{월}{요일}
```

**Examples**
```
30 5 * * *      : 매일 05시 30분
0 * * * *       : 매시 정각
1 * * * *       : 매시 1분
0 0 10 * *      : 매월 10일 0시 0분
30 9 * * 0      : 매주 일요일 09시 30분
*/5 * * * *     : 5분마다 (0분, 5분…) — (/는 증가값 지정을 의미)
5 9 * * 1-5     : 월요일부터 금요일까지 09시 5분에 배치
0 9-15/1 * * *  : 09시부터 15시까지 1시간마다
30 23 L * *     : 매월 마지막 일 23시 30분에 배치 (L = last)
0 9 * * 3#4     : 매월 4번째 수요일 9시 0분에 배치 (#은 N번째 요일)
```

## 5. 빈도 설정 (`timedelta`)

Cron 표현식은 "특정 시각"을 표현하는 데는 강하지만, **"3일에 한 번"처럼 특정 빈도 기반 스케줄은 정의하기 어렵다.** 이럴 때는 `timedelta` 인스턴스를 사용해 빈도 기반 스케줄을 정의한다.

```python
dag = DAG(
    dag_id="run_every_3_days_timedelta",
    start_date=datetime(2025, 3, 1),
    schedule_interval=timedelta(days=3),  # 정확히 3일 간격으로 실행
    catchup=False,
)
```

- Cron: 특정 시점/시각 기준 스케줄에 강함
- `timedelta`: 시작 시점 기준 일정한 간격 실행에 강함 (예: 정확히 3일마다)

## 6. Backfill이란?

- 특정 과거 `logical_date`(구 `execution_date`)에 대해 DAG를 **수동 실행하여 데이터를 복구**하는 작업
- 과거 실행이 누락되었거나, 데이터 오류가 발생했을 때 필요
- `airflow dags backfill` 명령어를 사용하여 특정 날짜 범위의 DAG 실행 가능

```bash
airflow dags backfill -s 2025-08-11 -e 2025-08-14 example_dag
```

과거의 특정 데이터 구간(위 예시에서는 8월 11일~8월 14일)에 대해서만 다시 DAG Run을 생성하고 실행하는 기능이다. 데이터 누락 복구나, 로직을 수정한 뒤 특정 과거 구간만 재처리해야 할 때 자주 쓰인다.

---

## 7. Catchup이란?

- DAG 시작 날짜(`start_date`) 이후 **누락된 실행을 보완**하기 위해 과거의 `logical_date`를 채우는 기능
- `catchup=True` 설정 시, 과거 미실행 DAG를 자동으로 실행하여 누락된 데이터를 처리
- `catchup=False` 설정 시, DAG는 가장 최신 실행 시간부터만 실행됨

예를 들어 `start_date`가 1월 1일이고 스케줄이 daily인데, 3월 1일에서야 처음 DAG를 활성화했다고 하자.
- `catchup=True`라면 → Airflow가 1월 1일부터 2월 말일까지 처리되지 않은 구간을 모두 순차적으로 실행해서 채운다.
- `catchup=False`라면 → 밀린 과거 구간은 무시하고, 현재 기준 가장 최근 구간만 처리한다.

Backfill이 "사용자가 명시적으로 과거 구간을 지정해서 재실행"하는 것이라면, Catchup은 "DAG가 활성화될 때 누락된 과거 구간을 자동으로 채워주는 것"이라는 차이가 있다.

실시간 처리나 최신 결과만 중요한 작업이라면 `catchup=False`가 적합하고, 과거 누락분까지 함께 처리해야 한다면 `catchup=True`를 사용한다.

## 8. 수동 실행 vs 자동 실행

- 자동 실행은 **스케줄러가 주기적으로 워크플로우를 관리** → 안정적 운영 중심
- 수동 실행은 **운영자나 개발자가 직접 트리거** → 테스트, 장애 복구, 백필 등에 활용
- 수동 실행 시에도 `logical_date`는 존재하지만, 스케줄 기반 계산이 아니므로 데이터 기준 구간과 어긋날 수 있음

| | 자동 실행 (Scheduler 기반) | 수동 실행 (Manual Trigger) |
|---|---|---|
| 실행 시점 | `data_interval`이 끝난 후 자동 실행 | 사용자가 즉시 실행 |
| Logical Date | 스케줄에 따라 자동 계산 (예: 2025-03-01) | 기본값: 트리거 시각 (직접 지정 가능) |
| Data Interval | 스케줄에 따라 자동 생성 (3/1 00:00 ~ 3/2 00:00) | 현재 시각 중심으로 생성됨 |
| 데이터 정합성 | 데이터가 모두 적재된 뒤 실행되어 정합성 보장 | 수집 중 데이터 포함 가능하며 정합성 깨질 수 있음 |
| 활용 목적 | 정기 워크플로우 운영 | 테스트, 긴급 실행, 백필(Backfill) |
| 명령 방식 | Airflow Scheduler 자동 실행 | `airflow dags trigger my_dag`, Web UI 수동 trigger 클릭 |

운영 환경에서 지속적으로 데이터를 쌓아 처리하는 경우라면 자동 실행이 기본이 되고, 수동 실행은 장애 복구·백필·학습/테스트 목적으로 직접 트리거해서 동작을 확인할 때 주로 사용한다.

---

## 💡 한 줄 요약
> Airflow의 DAG 실행은 "실행 시각"이 아니라 "처리할 데이터 구간(`data_interval`)" 관점에서 이해해야 하며, `start_date`·`logical_date`·`schedule_interval`(Cron/예약어/`timedelta`)이 맞물려 실행 시점을 결정하고, `catchup`과 `backfill`로 누락되거나 재처리가 필요한 과거 구간을 보완할 수 있다.
