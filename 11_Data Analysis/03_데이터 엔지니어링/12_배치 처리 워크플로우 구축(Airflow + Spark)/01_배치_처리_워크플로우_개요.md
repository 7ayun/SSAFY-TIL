# [데이터 엔지니어링] 배치 처리 워크플로우 개요

---

## 1. 배치 처리 vs 실시간 처리

배치 처리(Batch Processing)란 일정량의 데이터를 모아서 한꺼번에 처리하는 방식이다. 정해진 시간(예: 매일 밤 12시)이나 특정 이벤트(예: 파일 업로드) 발생 시 실행되며, 데이터가 발생하자마자 처리하는 것이 아니라 일정 기간(delay: 분/시간/일 단위) 데이터를 모아두었다가 한 번에 처리한다는 점이 핵심이다.

- 흐름: 여러 데이터 소스(Source) → Batch Processor → 목적지(Destination)에 결과 저장
- 목적지는 보통 데이터 웨어하우스(DW), 데이터 레이크 같은 저장소
- 대량 데이터를 안정적으로 처리하는 데 적합하며, ETL 파이프라인, 데이터 웨어하우스 적재, 머신러닝 학습 데이터 준비 등에 사용됨

실시간 처리(Real-time Processing)는 데이터가 발생하는 즉시(또는 거의 즉시, almost real-time) 처리하는 방식이다. 완전한 실시간이라기보다 지연을 최대한 짧게 가져가는 것이 목표다. 실시간 로그, IoT 센서 데이터처럼 계속 흘러 들어오는 스트리밍 데이터 처리에 적합하며, 이상 탐지·실시간 추천 시스템·실시간 모니터링 등에 활용된다. Spark의 Structured Streaming처럼 마이크로 배치 형태로 실시간에 가깝게 처리하는 방식도 존재한다.

| 항목 | 배치 처리 | 실시간 처리 |
|---|---|---|
| 데이터 처리 방식 | 일정량을 모아서 한 번에 처리 | 데이터가 들어오는 즉시 처리 |
| 처리 속도 | 느림 (분~시간 단위) | 빠름 (밀리초~초 단위) |
| 적용 사례 | 데이터 웨어하우스, 머신러닝 학습 데이터 준비 | 실시간 이상치 탐지, 추천 시스템, IoT 데이터 분석 |
| 리소스 사용 | 정해진 시점에 집중적으로 사용 | 지속적으로 사용 |
| 비용 | 상대적으로 저렴 | 고비용 |
| 사례 | 매일 오후 20시 로그 데이터 집계 | 실시간 주식 거래 분석 |

배치 처리는 정해진 시점에 리소스를 집중적으로 사용하기 때문에 그 시점의 리소스 관리가 중요하고, 실시간 처리는 지속적으로 리소스를 사용하기 때문에 상대적으로 고비용 구조가 된다.

## 2. Spark의 특징과 데이터 구조

Spark는 대규모 데이터를 빠르고 효율적으로 처리하기 위한 분산 데이터 처리 프레임워크다. 데이터를 여러 파티션으로 나눠 여러 Executor에서 병렬 처리할 수 있도록 설계되어 있다.

**In-Memory Computing**: Hadoop MapReduce는 디스크 기반으로 처리해 I/O가 많이 발생하지만, Spark는 데이터를 메모리(RAM)에서 유지한 채 연산을 이어갈 수 있어 반복 연산(머신러닝, 데이터 변환 등)에서 최대 100배까지 빠를 수 있다(항상 100배라는 의미는 아니다). 중간 연산 결과를 메모리에 유지하기 때문에 재사용이 가능해 성능상 이점이 크다.

**데이터 구조**
- **RDD(Resilient Distributed Dataset)**: Spark의 가장 기본적인 분산 데이터 추상화 단위. 여러 파티션으로 나뉘어 클러스터에서 병렬 처리되며, 변경 불가능(Immutable)하다. 변형이 일어나면 새로운 RDD가 생성된다. Driver Node가 연산을 스케줄링하고 각 Worker Node에 작업을 분배한다.
- **DataFrame**: Pandas처럼 행과 열로 구조화된 데이터를 다루기 위해 최적화된 데이터 구조. RDD보다 실제 사용 빈도가 훨씬 높다. Hive, CSV, JSON, RDBMS, XML, Cassandra 등 다양한 소스의 데이터를 통합해 표현할 수 있다.
- **Spark SQL**: DataFrame을 SQL 쿼리로 다룰 수 있게 해주는 모듈. Catalyst Optimizer가 실행 계획을 최적화하고, AQE(Adaptive Query Execution)가 실제 데이터 분포에 맞춰 후보정 최적화를 수행한다.

**RDD 배치 처리 과정**
1. `parallelize` 또는 외부 소스에서 데이터를 불러와 RDD 생성
2. Transformation 연산(`map`, `filter` 등)은 새 RDD를 만들지만 즉시 실행되지 않음 (Lazy Evaluation)
3. 여러 Transformation이 체이닝되어 실행 계획(DAG)을 구성
4. Action 연산이 호출될 때 비로소 DAG가 실행되어 실제 처리가 수행됨

Transformation에는 두 종류가 있다.
- **Narrow Transformation**: 파티션 간 데이터 이동이 발생하지 않는 연산
- **Wide Transformation**: 파티션 간 데이터 이동(shuffle)이 발생하는 연산. shuffle이 발생하는 시점에 Stage가 나뉜다.

**DataFrame 배치 처리 과정**
1. 다양한 데이터 소스에서 `read()`/`load()`로 DataFrame 생성
2. `select()`, `filter()`, `groupBy()` 등 Transformation 적용
3. 여러 단계의 Transformation이 체이닝되며 새로운 DataFrame이 연속 생성
4. `show()`, `count()`, `write()` 같은 Action이 호출되면 실제 실행

**주요 활용 사례**
- 데이터 웨어하우스 적재(ETL): CSV → Parquet 변환 후 Snowflake/BigQuery 적재
- 로그 데이터 분석: 클릭 로그 분석 후 마케팅 전략 최적화
- 머신러닝 데이터 전처리: 추천 시스템을 위한 사용자 행동 데이터 전처리

## 3. Airflow와 Spark를 함께 쓰는 이유

Pandas나 일반 파이썬 코드로도 데이터 처리 자체는 가능하지만, 데이터 규모가 커지면 한계에 부딪힌다.
- 하나의 머신 메모리에 로드할 수 있는 데이터 크기에 한계가 있음
- 데이터를 여러 노드로 나눠 처리하는 기능이 없어 병렬 처리가 어려움

이런 한계를 해결하기 위해 Spark의 분산 처리 기능을 활용한다. 다만 Spark 작업을 자동으로 스케줄링하고, 실패 시 재시도하고, 모니터링하는 오케스트레이션 기능은 Spark 자체에는 없다. 이 부분을 Airflow가 담당한다.

- 단순 SQL/Python으로 처리하기 어려운 대규모 데이터 → Spark가 처리
- Spark 작업을 태스크로 등록해 스케줄링·실행 상태 관리 → Airflow가 담당
- Spark 작업 실패 시 Airflow가 자동으로 감지하고 재시도 가능
- Airflow Web UI에서 로그를 확인해 어느 Task에서 문제가 발생했는지(병목 지점) 쉽게 파악 가능

즉, Spark가 실제 대량 데이터 연산을 수행하고, Airflow는 그 작업의 제출·추적·재시도·자동화를 담당하는 역할 분담 구조다.

## 4. 배치 워크플로우에서 DAG의 역할

Airflow의 DAG(여기서는 Spark의 실행 계획 DAG가 아니라 Airflow 워크플로우 DAG를 의미)는 배치 워크플로우에서 다음 역할을 한다.

- **자동화**: 사람이 직접 실행하지 않아도 정해진 스케줄에 따라 실행
- **유지보수 용이**: 실행 로그와 실패 이력이 기록되어 문제 해결이 쉬움
- **확장성**: 여러 작업을 DAG 내에서 관리하고 병렬 실행 가능
- **재시도 및 오류 감지**: Task 실패 시 자동으로 재시도하여 안정적인 운영 가능

**병렬 태스크 + 순차 태스크 구성 예시**

```
                Task_A1 → Task_A2
               ↗                 ↘
start(Empty) → Task_B1 → Task_B2 → end
               ↘                 ↗
                Task_C1 → Task_C2
```

- 시작 지점(`start`)은 EmptyOperator로 선언해 병렬 실행의 기준점으로 사용
- A1/B1/C1은 서로 의존성이 없어 동시에 병렬 실행 가능(예: 여러 데이터 소스를 동시에 읽는 작업)
- 각 체인(A1→A2, B1→B2, C1→C2)은 상위 태스크가 끝나야 하위 태스크가 실행되는 순차 구조
- 모든 체인이 끝나야 `end`로 합류하도록 구성해, 병렬 처리 후 전체 완료 시점에 종료 처리를 할 수 있다

작업 간 의존성을 명확히 설정하면서 병렬 처리로 전체 실행 시간을 단축할 수 있다는 점이 이런 구조의 핵심이다. 실습에서 사용한 `complex_parallel_example_dag`는 이 구조를 그대로 구현한 예시로, task_B 체인만 3단계(B1→B2→B3)로 구성해 병렬/순차 조합을 보여준다.

## 5. PythonOperator로 CSV 데이터 변환하기

Spark 없이도 PythonOperator + Pandas만으로 간단한 배치 처리를 Airflow와 연동할 수 있다.

```python
from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime, timedelta
import pandas as pd

CSV_FILE_PATH = "dags/input_data.csv"
OUTPUT_FILE_PATH = "dags/output_data.csv"

def transform_csv():
    # CSV 파일 읽기
    df = pd.read_csv(CSV_FILE_PATH)

    # 데이터 변환 (예: 컬럼명 변경 및 새로운 컬럼 추가)
    df.rename(columns={"old_column": "new_column"}, inplace=True)
    df["processed_date"] = datetime.now().strftime("%Y-%m-%d %H:%M:%S")

    # 변환된 데이터 저장
    df.to_csv(OUTPUT_FILE_PATH, index=False)
    print("Data transformation complete. Saved to", OUTPUT_FILE_PATH)

default_args = {"start_date": datetime(2025, 3, 1)}

dag = DAG(
    "csv_transform_dag",
    default_args=default_args,
    description="DAG to read and transform CSV file",
)

transform_task = PythonOperator(
    task_id="transform_csv_task",
    python_callable=transform_csv,
    dag=dag,
)
```

실행하면 `input_data.csv`의 컬럼명이 변경되고 `processed_date` 컬럼이 추가된 `output_data.csv`가 생성된다. Docker 환경에서 실행할 때는 Airflow 컨테이너와 데이터 파일 경로가 볼륨 마운트로 연결되어 있어야 하며, 실습에서는 `data`/`output` 디렉토리를 분리해 어느 작업 디렉토리에서 실행되든 경로가 꼬이지 않도록 통일했다.

## 6. BashOperator로 쉘 스크립트 실행하기

Shell 스크립트로 작성된 전처리 로직도 BashOperator를 통해 DAG 태스크로 실행할 수 있다.

```python
from airflow import DAG
from airflow.operators.bash import BashOperator
from datetime import datetime, timedelta

default_args = {"start_date": datetime(2025, 3, 1)}

dag = DAG(
    "bash_processing_dag",
    default_args=default_args,
    description="DAG to process using Bash script",
)

process_csv_task = BashOperator(
    task_id="process_csv",
    bash_command="/opt/airflow/plugins/shell/process_csv.sh ",
    dag=dag,
)
```

실습 중 주의할 점 두 가지가 있다.

1. **`bash_command` 끝에 공백을 넣어야 한다.** Airflow는 `.sh` 파일 경로를 그대로 넘기면 Jinja 템플릿 문법으로 잘못 해석해 셸 스크립트가 파일 형태로 실행되지 않는 경우가 있다. 뒤에 공백을 하나 붙여 "이건 셸 스크립트를 실행하는 명령이다"라는 것을 명확히 해줘야 한다. Airflow에서도 공식적으로 이 방식을 권장한다.
2. **셸 스크립트 파일에 실행 권한이 필요하다.** 권한이 없으면 태스크가 실패하므로, 대상 스크립트에 `chmod +x`로 실행 권한을 부여해야 한다.

```bash
chmod +x plugins/shell/process_csv.sh
```

이 스크립트는 특수문자가 섞인 데이터를 대문자로 변환하고 특수문자를 제거하는 간단한 전처리를 수행하며, 실행 로그에서 원본 데이터(Original Data)와 처리된 데이터(Final Processed Data)를 비교해 정상 동작을 확인할 수 있다.

## 💡 한 줄 요약
