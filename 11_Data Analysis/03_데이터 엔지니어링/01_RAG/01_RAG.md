# [데이터 엔지니어링] RAG

---

## 1. 생성형 AI(LLM)가 가진 한계

LLM은 방대한 텍스트 데이터셋을 학습해서 문장을 생성하고, 요약·번역 등 다양한 NLP 작업을 수행한다. 다만 아무리 큰 데이터셋으로 학습을 해도 다음과 같은 한계가 자연스럽게 따라온다.

| 한계 | 설명 |
|---|---|
| 환각 현상 (Hallucination) | 학습 데이터에 없는 내용을 사실인 것처럼 그럴듯하게 지어내는 문제 |
| 최신 지식 부족 | 특정 시점까지의 데이터로만 학습되어 최신 정보(예: 오늘 있었던 이벤트)에는 답할 수 없음 |
| 정보 출처 부재 | 방대한 코퍼스를 뭉뚱그려 학습했기 때문에 답변의 근거를 제시하기 어려움 |
| 높은 파인튜닝 비용 | 새로운 지식을 반영하려면 재학습이 필요한데, 시간·비용 소모가 크고 모델이 클수록 더 어려움 |

특히 회사처럼 특정 도메인(금융 등)에 소속되어 있으면, 그 산업에서만 쓰이는 용어나 사내 규정처럼 LLM이 학습한 적 없는 내용에 대해 정확한 답변이 필요해진다. 이런 상황에서 실제로 요구되는 것은 아래와 같다.

- 도메인별 정확한 답변
- 최신 정보 반영
- 생성된 콘텐츠의 추적 가능성(출처)
- 비용 효율성
- 보안 및 프라이버시 제어 (민감 정보는 아예 접근하지 못하게 시스템적으로 차단)

## 2. LLM 한계를 극복하는 방법: 모델 조정 vs 입력 조정

한계를 해결하는 접근은 크게 **모델 자체를 바꾸는 방식**과 **입력(문맥)을 바꾸는 방식**으로 나뉜다.

- **Fine-tuning**: 기존 모델의 가중치(weight)를 도메인 특화 데이터셋으로 추가 학습시켜 조정하는 방식. 모델에 지식을 직접 내재화한다.
- **Prompt Engineering**: 모델 가중치는 건드리지 않고, 특정 작업에 더 잘 반응하도록 입력 프롬프트 자체를 최적화하는 방식. 예시(0-shot/N-shot)를 주거나, Chain-of-Thought처럼 답을 도출하는 과정까지 프롬프트에 포함시키면 정답률이 올라간다.
- **In-context Learning**: 질문과 함께 필요한 문맥을 프롬프트에 제공해서 답변을 유도하는 방식.
- **RAG (Retrieval-Augmented Generation)**: 검색 기반의 외부 정보를 입력 프롬프트에 결합(증강)해서, 그 증강된 정보를 바탕으로 답변을 생성하게 만드는 방식. In-context Learning의 일종으로 볼 수 있다.

네 가지를 Context Optimization(문맥 최적화 정도)과 Model Adaption(모델 자체 조정 정도) 두 축으로 정리하면:

| | Model Adaption 낮음 | Model Adaption 높음 |
|---|---|---|
| Context Optimization 높음 | RAG | Hybrid (RAG + Fine-Tuning) |
| Context Optimization 낮음 | Prompt Engineering | Fine-Tuning |

RAG + Fine-tuning을 함께 쓰는 Hybrid 방식이 성능은 가장 좋을 수 있지만, 그만큼 구축 부담도 크기 때문에 상황에 맞게 선택하면 된다.

## 3. RAG란 무엇인가

**RAG(Retrieval-Augmented Generation)** = 검색 증강 생성. 사전 학습된 LLM(Pre-trained LLM)에 쿼리가 들어오면, Retriever가 먼저 쿼리와 가장 관련성 높은 문서(relevant docs)를 Knowledge Base에서 검색해오고, 그 문서들을 쿼리와 함께 LLM에 전달해서 답변을 생성하게 만드는 방식이다.

- **Retrieval (검색)**: 외부 데이터·소스를 검색해 정보 획득
- **Augmented (증강)**: 사용자의 질문을 보강해 더 정확한 문맥 제공
- **Generation (생성)**: 향상된 정보를 기반으로 더 좋은 답변 생성

이 구조 덕분에 답변할 때 확실한 출처를 기반으로 생성하게 되고, Retriever의 성능이 곧 전체 답변 품질에 직결되기 때문에(앞단이 무너지면 뒤도 무너진다) 검색 자체의 중요성이 매우 크다.

### RAG vs Fine-tuning

숟가락과 나이프에 비유하면, RAG는 필요할 때마다 정보를 가져와 쓰는 숟가락, Fine-tuning은 모델을 목적에 맞게 정교하게 깎아내는 나이프에 가깝다.

| | RAG | Fine-tuning |
|---|---|---|
| 장점 | 외부 지식 추가로 정확도·신뢰도 향상 / 새 정보 추가 시 재학습 불필요 | 특정 작업 성능 향상 (예: 요약 성능) / 구체적 태스크에 일관된 품질 제공 |
| 단점 | 검색된 정보의 품질에 의존 / 검색 시스템 가동으로 컴퓨팅 자원 소모 | 많은 학습 데이터 필요 / 학습한 데이터 외 질의에는 좋은 답변이 어려움 |

무엇이 항상 더 좋다고 할 수는 없고, 시스템이 실제로 필요로 하는 게 무엇인지(비용, 기존 인프라, 모델 업데이트 주기 등)에 따라 선택한다. 특히 최신 모델이 계속 나오는 상황에서는 매번 파인튜닝을 반복하기보다, 기존 데이터베이스를 그대로 활용할 수 있는 RAG가 실용적인 경우가 많다.

### RAG의 장점 정리
- 환각 현상(Hallucination) 감소
- 도메인 적응성 개선
- Open Domain QA 성능 향상
- 참고한 Knowledge Base가 적절한지 판단 가능
- 정보 검색에 강함

## 4. 검색(Retrieval) 방식 ① Keyword Search (Lexical Search)

키워드 기반의 단어 매칭 검색. 핵심은 **역색인(Inverted Index)** 구조다.

- 일반 색인: 문서 번호 → 문서 내용(위치)으로 찾아감 (RDB의 인덱싱과 유사)
- 역색인: 단어 → 그 단어가 등장한 문서 목록으로 연결. 예를 들어 "학교"라는 단어가 3, 49, 100번 문서에 있다는 걸 미리 연결해두고, 검색 시 바로 해당 문서들을 불러올 수 있게 한다.

### TF-IDF
단어가 특정 문서를 얼마나 잘 대표하는지 점수로 표현하는 대표적인 방식.

```
TF-IDF(t, d, D) = TF(t, d) × IDF(t, D)
  t = 단어, d = 문서, D = 전체 문서

TF(t, d) = 문서 d에서 단어 t가 등장한 횟수 / 문서 d에 등장한 모든 단어의 수
IDF(t, D) = log(총 문서의 개수 / 단어 t를 포함하는 문서의 수)
```

- TF: 한 문서 안에서 그 단어가 얼마나 자주 등장했는가 (자주 등장할수록 값이 커짐)
- IDF: 전체 문서에서 그 단어가 얼마나 흔하게 등장하는가 (여러 문서에 흔하면 값이 작아짐 → "is"처럼 흔한 단어의 가중치를 낮춤)
- 즉, 한 문서에서만 자주 나오는 단어일수록 가중치가 높아지고, 여러 문서에 걸쳐 흔한 단어는 가중치가 낮아지는 방식으로 균형을 맞춘다.

다만 TF-IDF는 단어가 반복될수록 관련도가 선형적으로 계속 올라간다는 단점이 있다(10번 등장한 문서가 1번 등장한 문서보다 정확히 10배 중요한 건 아님).

### BM25
TF-IDF의 단점을 보완한, 텍스트 기반 검색에서 가장 널리 쓰이는 방식. 일정 수준을 넘어가면 증가폭을 줄이는 보정값이 들어간다.

```
score(D, Q) = Σ IDF(qi) · [ f(qi, D)·(k1+1) / (f(qi, D) + k1·(1 - b + b·|D|/avgdl)) ]
```

수식을 암기할 필요는 없고, "쿼리와 문서 간 관련도에 순위를 매겨준다"는 흐름만 이해하면 된다. 단순 라이크(LIKE) 매칭은 순위 없이 매칭 여부만 판단하지만, TF-IDF·BM25는 순위를 매겨 가장 적합한 문서를 제공할 수 있다.

### 유사도 계산 방식
- **코사인 유사도**: 두 벡터 사이의 각도를 기준으로 판단. 각도가 작을수록(1에 가까울수록) 유사
- **L2 거리**: 두 벡터 사이의 유클리드 거리를 기준으로 판단. 거리가 작을수록(0에 가까울수록) 유사

### Keyword Search의 한계
TF-IDF, BM25는 결국 단어 통계 기반 검색이기 때문에, 문서와 쿼리의 단어가 정확히 일치할 때는 강하지만 **표현이 달라지면 의미가 같아도 놓칠 수 있다.** 예를 들어 "휴가"에 대해 질문했는데 문서에는 "연차"라는 단어만 쓰였다면 단어 일치만으로는 관련성을 찾기 어렵다.

## 5. 검색(Retrieval) 방식 ② Semantic Search

단어 일치의 한계를 보완하기 위해, 텍스트를 벡터(숫자)로 변환하는 **임베딩(Embedding)**을 활용한다. 통계 기반 검색은 값이 늘어날수록 차원이 커지는 **희소 벡터(Sparse Vector)**를 만들지만, AI 임베딩 모델은 고정된 차원의 **밀집 벡터(Dense Vector)**로 의미를 표현한다.

- 텍스트를 토큰화하고, 각 토큰이 벡터 공간 안에서 위치를 학습(Word2Vec, BERT 등)
- 문맥상 의미가 비슷한 단어일수록 벡터 공간에서 가까운 위치에 놓임 (예: king-queen, walking-swimming 같은 관계가 유사한 벡터 거리로 나타남)
- 따라서 질문과 문서에 같은 단어가 없어도, 의미가 유사하면 검색될 수 있음

### Vector DB
벡터로 표현된 데이터를 저장하고, 유사한 벡터를 빠르게 검색하도록 하는 시스템. In-memory, Persistent, 클라우드 저장 방식이 있으며 chroma, Pinecone, Milvus, PostgreSQL(pgvector), Elasticsearch 등이 대표적이다.

- 쿼리를 임베딩 모델에 통과시켜 벡터로 변환
- Vector DB에 저장된 문서 청크의 벡터들과 유사도 비교
- 유사도가 높은 순으로 결과 반환

### ANN (Approximate Nearest Neighbor)
데이터가 수백만~수억 건이 되면 모든 벡터를 하나하나 비교하는 것은 병목(bottleneck)이 된다. 이를 해결하기 위해 정확하게 전수 비교하는 대신, 근사적으로 가까운 후보들을 빠르게 찾아주는 방식이 ANN이며, 대표적으로 HNSW 같은 알고리즘이 쓰인다. 약간의 정확도를 포기하는 대신 속도를 크게 확보하는 트레이드오프 구조다.

## 6. RAG의 핵심 구성요소

| 구성요소 | 역할 |
|---|---|
| 임베딩 모델 | 텍스트의 의미를 벡터로 변환하는 엔진 |
| 벡터 데이터베이스 | 벡터를 저장하고 ANN 등을 통해 빠르게 검색 |
| 리트리버 (Retriever) | 가장 관련성 높은 문서를 찾아오는 전략 (Semantic Search, Keyword Search, Hybrid Search) |
| 생성 모델 | 검색된 문맥을 바탕으로 자연스러운 답변을 생성 (GPT 등) |

### RAG 챗봇의 동작 흐름
1. 사용자가 질문
2. 챗봇이 곧바로 모델에 질문을 넘기지 않고, 관련 문서를 데이터소스에서 검색·활용
3. 관련 문서를 포함해 (근거와 함께) 더 길어진 질문을 AI 모델에 전달
4. AI 모델이 그 문서를 참고해 답변을 생성 → 챗봇을 거쳐 사용자에게 전달

RAG가 없는 일반 챗봇은 질문 → 모델 전달 → 답변의 단순한 구조라 출처를 확인하거나 사내 문서처럼 학습되지 않은 정보를 검색해오는 과정 자체가 없다. 반면 RAG/에이전트 기반 서비스를 만든다면 단순히 Retriever나 Generator만이 아니라 프롬프트, 에이전트, 답변 템플릿까지 전부 커스터마이징이 필요하다는 점도 함께 고려해야 한다.

## 💡 한 줄 요약
> RAG는 LLM의 환각·최신성·출처 부재 문제를 검색(Retrieval)으로 보완하는 방식이며, 그 성능은 결국 앞단 Retriever(Keyword Search + Semantic Search)의 품질에 크게 좌우된다.
