# [데이터 엔지니어링] Elasticsearch의 아키텍처와 분산처리

---

## 1. 클러스터(Cluster)와 노드(Node)

- **클러스터(Cluster)**: 하나 이상의 노드(Node)로 구성된 그룹. 고유한 이름을 가지며, 데이터를 분산 저장·관리하는 역할을 수행
- **노드(Node)**: Elasticsearch의 개별 실행 인스턴스. 각 노드는 데이터를 저장하며, 클러스터의 색인 및 검색 기능에 참여

클러스터 구조가 중요한 이유:

| 항목 | 설명 |
|---|---|
| 분산된 데이터 처리 | 여러 노드가 데이터 저장·검색·분석 작업을 함께 수행 |
| 노드의 역할과 관리 | 각 노드는 고유한 이름과 IP로 클러스터에 참여하며, 특정 역할(마스터/데이터/인제스트 등)을 담당 |
| 안정성과 가용성 확보 | 장애 대비·데이터 보호를 위해 여러 지역에 노드를 분산 배치하고 복제(replica) 기능 활용 |
| 유연한 확장성과 성능 최적화 | 필요에 따라 노드를 추가하기만 하면 클러스터에 자연스럽게 참여해 확장됨 |

---

## 2. 노드 유형(Node Types)

대표적인 노드 유형 4가지:

| 노드 유형 | 역할 |
|---|---|
| **마스터 노드**(Master Node) | 클러스터 전체 작업을 총괄. 인덱스 생성/삭제, 노드 상태 관리(헬스체크) 등 |
| **데이터 노드**(Data Node) | 실제 데이터를 저장. CRUD, 검색, 집계(Aggregation) 작업 처리. CPU·I/O·메모리 등 리소스를 가장 많이 소모 |
| **인제스트 노드**(Ingest Node) | 색인 전 필터링·변환·정제 등 전처리 작업 수행 |
| **코디네이팅 노드**(Coordinating Node) | 클라이언트 요청을 라우팅하고, 여러 노드에 분산된 검색 로드를 균형 있게 처리 |

> 이 외에도 ML, remote_cluster_client, transform 등 특정 용도에 특화된 노드 유형이 존재한다.

노드 하나만 띄우면 그 노드가 마스터·데이터·인제스트 역할을 모두 수행한다. 규모가 커질수록 역할을 분리해서 운영하는 것이 리소스 낭비를 줄이는 데 유리하다. 역할을 별도로 설정하지 않으면 모든 노드가 인제스트·코디네이팅 역할을 자연스럽게 수행할 수 있다.

### 마스터 노드 상세

- 클러스터의 핵심 관리자로, 클러스터의 안정적인 운영을 담당
- 인덱스 생성/삭제, 노드 관리, 샤드 분배 등 주요 작업을 결정
- 클러스터 운영이 중단되지 않으려면 **최소 1개 이상**의 마스터 노드가 반드시 필요
- 마스터 노드가 하나뿐이면 장애 시 클러스터 전체가 중단될 위험이 있음 → 운영 환경에서는 보통 **3개 이상의 마스터(후보) 노드**를 구성해 장애 시 안정성 확보
- 클러스터 상태를 지속적으로 모니터링하고, 필요 시 다른 노드로 마스터 역할을 전환하여 안정적인 운영 유지

### 데이터 노드 상세

- 실제 데이터 저장·관리, 색인/검색/집계 작업 담당 → 리소스 소모가 가장 큼
- 클러스터 안정성을 위해 적절한 개수의 데이터 노드 유지, 장애 대비 샤드 운영 필요
- 데이터 특성·접근 패턴에 따라 데이터 노드 유형을 조정 가능
  - 예: **Hot/Warm/Cold 티어링** — 자주 조회되는 최신 데이터는 고성능 장비(Hot), 오래되어 조회가 드문 데이터는 상대적으로 저사양 장비(Cold)에 배치해 비용과 성능을 함께 최적화

### 인제스트 노드 상세

데이터 노드에 저장되기 전, 색인 전 단계에서 필터링·변환·정제 작업을 수행한다.

```
{"message": "a b c"}
        │
        ▼
   Ingest Node
 grok → date → set   (Processors)
        │
        ▼
{"field1":"a", "field2":"b", "field3":"c"} → Data Node
```

- 필드 추가/삭제, 날짜 변환, 텍스트 정규화 등 다양한 데이터 변환 지원
- 예: 로그 원문(`2026-08-05 10:16:50 INFO user_id=1234 action=login`)이 인제스트 노드를 거치며 `timestamp`, `level`, `user_id`, `action` 등 필드로 구조화되어 데이터 노드에 저장됨
- CPU·메모리 사용량이 높아 데이터 노드와 **분리 운영**을 권장

### 코디네이팅 노드 상세

- 클러스터의 요청을 라우팅하고 상태를 관리하는 역할
- 검색/색인 요청을 적절한 데이터 노드로 분산 처리
- 별도로 지정하지 않으면 요청이 가장 먼저 도달한 노드가 코디네이팅 역할을 수행
- 대규모 클러스터에서는 별도로 분리 운영하여 부하를 줄이는 것이 효과적

## 3. 노드 역할 흐름 (인덱싱 요청 vs 검색 요청)

```
                         Index
   ┌───────────────────────────────────────────────┐
   │  Data Node          Data Node                  │
   │  (Primary)Shard1  (Secondary)Shard3            │
   │  (Secondary)Shard4 (Primary)Shard2              │      Master(eligible) Node
   │                                                  │  ───  Master Node
   │  Data Node          Data Node                   │      Master(eligible) Node
   │  (Secondary)Shard1  (Secondary)Shard2           │
   │  (Primary)Shard3    (Primary)Shard4              │
   └───────────────────────────────────────────────┘
Coordinating Node ─ Search ──▶
Ingest(+Coordinating) Node ─ Indexing ──▶
```

**인덱싱 요청 처리 순서**
1. 코디네이팅 노드가 요청을 수신 → 인제스트 노드로 전달
2. 해당 문서가 저장될 샤드를 결정
3. 해당 Primary Shard를 가진 데이터 노드로 요청 전달, Primary Shard에 문서 저장
4. 같은 샤드 번호의 **Replica Shard**로 복제 요청을 **비동기**로 전송
5. Primary 저장이 성공하면 클라이언트에 즉시 성공 응답 (Kafka와 달리 Replica까지 저장 완료를 기다리지 않음)

**검색 요청 처리 순서**
1. 코디네이팅 노드가 검색 요청을 수신, 쿼리를 분석
2. 인덱스가 가진 **모든 샤드**(Primary·Replica 구분 없이 각 샤드별로 1개씩)에 검색 요청을 분산 전송
3. 각 샤드는 자신이 가진 데이터 중 쿼리에 맞는 상위권 결과를 반환
4. 코디네이팅 노드가 결과를 조합해 최종 결과를 사용자에게 반환

## 4. 샤드(Shard)

| 구분 | 설명 |
|---|---|
| **Shard** | 데이터를 나누어 저장하는 작은 단위. 노드 간 분산 저장으로 성능·확장성 보장 |
| **Primary Shard** | 색인 생성 및 CRUD 작업을 수행하는 원본 샤드 |
| **Replica Shard** | Primary Shard의 복사본. 장애 복구 및 검색 성능 향상 역할 |

- **Primary Shard 개수는 인덱스 생성 시점에만 결정되며, 이후 변경 불가**
- **Replica Set 개수는 언제든지 변경 가능** (단, 늘어날수록 저장 공간 소모는 증가)

> 카프카의 파티션과 유사한 점이 있지만, 샤드/레플리카 샤드는 **검색 요청(읽기)**에 대해 분산 처리가 가능하다는 점이 특징이다.

---

## 5. Replication(복제)

- 데이터를 복제하여 중복성을 확보하고, 고가용성 및 장애 대응을 보장
- **Primary-Replica 관계**: Primary Shard는 0개 이상의 Replica Shard를 가질 수 있음
- **쓰기(Write) 연산**: Primary Shard에서 발생한 변경 사항이 모든 Replica Shard에 복제됨
- **읽기(Read) 연산**: Primary와 Replica Shard가 함께 검색 부하를 분산 처리 → 성능 향상

### Replication의 장점
- **고가용성(HA)**: Primary가 포함된 노드가 다운되면 Replica가 Primary로 승격되어 데이터 접근에 문제없음
- **부하 분산**: 검색 요청을 Primary/Replica 어디로든 분산 처리 가능 → 성능 향상
- **데이터 중복 저장**: 여러 노드에 데이터를 복사해 장애 시 데이터 손실 방지

### Replication 고려 사항
- **노드 개수**: 동일한 샤드의 Primary와 Replica는 같은 노드에 저장할 수 없으므로, Replica 개수만큼 충분한 노드가 필요
- **네트워크·저장소 부담**: 복제본 유지에 따른 네트워크 트래픽 증가, 저장 공간 추가 소모
- **트레이드오프**: 복제본이 많을수록 데이터 안정성은 높아지지만 디스크·네트워크 자원 소모도 커짐

### 인덱스별 Primary Shard·Replica 설정 예시

```json
PUT books
{
  "settings": {
    "index": {
      "number_of_shards": 5,
      "number_of_replicas": 1
    }
  }
}
```

Python 클라이언트 기준:

```python
es.indices.create(
    index="book",
    body={
        "settings": {
            "index": {
                "number_of_shards": 5,
                "number_of_replicas": 1
            }
        }
    }
)
```

위와 같이 설정하면 `books` 인덱스는 5개의 샤드(0~4)로 나뉘어 여러 노드에 분산 배치되고, 각 샤드의 Replica는 자신의 Primary와 다른 노드에 위치하도록 Elasticsearch가 자동으로 최적 분산 배치를 수행한다. Replica를 선언하지 않으면 해당 인덱스는 복제 없이 각 샤드만 분산된 상태로 생성된다.
