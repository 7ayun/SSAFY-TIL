## 2. 웹폰트

### 2-1. 웹폰트란

폰트(글씨체)를 사용자 컴퓨터에 별도 설치하지 않고, 웹에서 직접 다운로드 받아 제공하는 폰트를 **웹폰트**라고 한다.

### 2-2. 웹폰트를 사용하는 이유

| 이유 | 설명 |
|------|------|
| 심미적 이유 | 예쁜 글씨체로 서비스 퀄리티 향상 |
| OS/브라우저 간 통일 | Windows, macOS, Linux, Safari, Chrome 등 기본 폰트가 각기 달라 디자인 일관성이 깨짐 → 웹폰트로 통일 |

### 2-3. 장단점

**장점**
* 사용자가 별도 설치 불필요
* 원하는 폰트를 자유롭게 선택 가능(유연성 증가)
* 링크 한 줄로 적용

**단점**
* 웹 서버에서 폰트를 실시간 로드하므로 **로딩 시간 증가**
* 인터넷 연결 필수
* 브라우저 호환성 문제 (`.woff`, `.ttf` 등 지원 형식이 브라우저마다 상이)
* **라이선스 반드시 확인** 필요 (상업적 이용 여부 등)

### 2-4. 폰트 라이선스 종류

| 라이선스 | 특징 |
|----------|------|
| OFL (SIL Open Font License) | 자유 사용·수정·재배포·상업적 이용 가능. 단, 수정 재배포 시 ① 원본 함께 배포 ② OFL 텍스트 파일 포함 ③ 원본 저작권자 명시 조건 있음 |
| MIT | 상업적 이용 포함 자유 사용 가능. 단, 저작권자 명시 필요. React, Vue 등 오픈소스 프레임워크가 채택 |
| Apache | 폰트와 함께 라이선스 명시 조건 |
| 유료 라이선스 | 구매 후 사용. 상업용 배포 전 반드시 계약서 확인 |

### 2-5. 폰트 제공 사이트

**① Google Fonts** (`fonts.google.com`)
* Language 필터 → Korean 선택
* 원하는 폰트 클릭 → `Get Font` → `@import` 코드 복사

**② 눈누** (`noonnu.cc`)
* 국내 무료 폰트 모음 사이트
* 폰트 클릭 → 하단 "웹폰트로 사용" 코드 복사

### 2-6. 웹폰트 적용 방법

**방법 A — CSS `@import` 방식 (권장)**

CSS 파일 최상단에 아래 코드를 붙여넣는다.

```css
@import url('https://fonts.googleapis.com/css2?family=Nanum+Pen+Script&display=swap');

.nanum-pen-script-regular {
  font-family: "Nanum Pen Script", cursive;
  font-weight: 400;
  font-style: normal;
}
```

HTML 태그에 클래스 적용:

```html
<p class="nanum-pen-script-regular">안녕하세요</p>
```

**방법 B — HTML `<link>` 태그 방식**

```html
<head>
  <link rel="preconnect" href="https://fonts.googleapis.com">
  <link href="https://fonts.googleapis.com/css2?family=Nanum+Pen+Script&display=swap" rel="stylesheet">
</head>
```

**눈누 폰트 적용 예시 (G마켓 산스)**

```css
@font-face {
    font-family: 'GmarketSansMedium';
    src: url('https://cdn.jsdelivr.net/gh/projectnoonnu/noonfonts_2001@1.1/GmarketSansMedium.woff') format('woff');
    font-weight: normal;
    font-style: normal;
}

.gmarket-font {
  font-family: 'GmarketSansMedium';
}
```

## 3. Figma와 생성형 AI를 활용한 웹페이지 구현

### 3-1. Figma란

기획자·디자이너가 UI/화면 시안을 만드는 **웹 기반 디자인 툴**이다.

* 사각형·버튼 등 UI 요소를 배치하면 가로·세로·픽셀 정보가 자동으로 계산됨
* 프론트엔드 개발자는 이 수치를 보고 CSS를 작성
* **콜라보레이터** 기능: 여러 명이 동시 접근·편집 가능 (권한 설정 지원)
* 기획자/디자이너가 주로 다루며, 개발자는 참고용으로 활용

### 3-2. Figma 주요 특징

* **클라우드 기반**: 별도 설치 없이 브라우저에서 바로 실행. 팀원 이메일 추가로 협업 가능
* **프로토타입(Prototype)**: 실제 개발 전에 임시로 UI 흐름을 구현해보는 화면 목업
* **Bootstrap UI Kit**: Figma 내 검색창에 "Bootstrap 5 UI Kit" 검색 시 버튼·카드 등 컴포넌트가 미리 제작된 키트를 가져와 활용 가능
* **Export 기능**: 완성된 디자인을 PNG/JPG 이미지로 추출 → GPT에 첨부해 코드 생성에 사용
* **Figma 가입**: `figma.com` → 구글 계정으로 가입 → Starter(무료) 요금제 선택

```
Figma 작업 흐름
① 새 페이지 생성 (예: "메인 페이지")
② Bootstrap UI Kit에서 필요한 컴포넌트 복사·붙여넣기
③ 요소 클릭 시 우측 패널에서 가로·세로·픽셀 확인
④ 우측 Export 버튼 클릭 → PNG로 추출
⑤ 추출한 이미지를 GPT에 첨부해 HTML/CSS 생성 요청
```

### 3-3. Figma 이미지 → GPT로 HTML/CSS 자동 생성

Figma 화면을 캡처한 이미지를 GPT에 직접 첨부하고 요구사항 프롬프트를 함께 입력하면 HTML/CSS 코드를 자동으로 생성해 준다.

**프롬프트 예시 (XML 태그 구조화 방식 권장):**

```
<요구사항>
- HTML, CSS 그리고 Bootstrap 5를 사용해서 첨부된 이미지와 동일한 디자인으로 구현
- 반응형: 화면 크기가 줄어들면 햄버거 메뉴로 전환
- 첨부한 이미지를 참고해서 스타일이 일치되도록 구현
- 코드를 간결하게 최적화
</요구사항>
```

GPT에 이미지만 던지는 것보다 XML 태그로 요구사항 범위를 명확히 지정하면 결과 퀄리티가 확연히 올라간다. 알고리즘 문제 풀이 시에도 `<문제>`, `<입력>`, `<출력>` 태그를 구분해 넣으면 효과적이다.

GPT 웹서비스에서는 이미지 업로드 횟수 제한이 있다 (무료·유료 모두 해당). 이를 극복하기 위해 OpenAI API를 코드로 직접 호출한다.

## 4. OpenAI API를 활용한 이미지 분석 코드

### 4-1. 코드 흐름 개요

```
이미지 파일 (PNG/JPG)
  → 바이너리(binary)로 읽기
  → Base64 인코딩 (문자열 형태로 변환)
  → OpenAI API에 문자열로 전송
  → GPT가 Base64 문자열 → 이미지 복원 후 분석
  → HTML/CSS 코드 응답 반환
```

이미지는 바이너리 형태(0과 1)로 저장되어 있으므로, API로 전송하려면 Base64 인코딩을 통해 텍스트 형태로 변환해야 한다. Base64는 해시와 달리 **복원(디코딩)이 가능**하다.

### 4-2. 실습 코드 구조

```python
import openai
from dotenv import load_dotenv
import os
import base64

# 환경 변수 로드
load_dotenv()
client = openai.OpenAI(api_key=os.getenv("OPENAI_API_KEY"))


def encode_image(image_path):
    """이미지를 Base64 문자열로 인코딩"""
    with open(image_path, "rb") as image_file:   # rb: read binary
        return base64.b64encode(image_file.read()).decode("utf-8")


def analyze_image(prompt, image_path):
    """Base64 이미지를 GPT API에 전송하고 응답 반환"""
    base64_image = encode_image(image_path)

    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[
            {
                "role": "user",
                "content": [
                    {"type": "text", "text": prompt},
                    {
                        "type": "image_url",
                        "image_url": {
                            "url": f"data:image/png;base64,{base64_image}"
                        },
                    },
                ],
            }
        ],
    )
    return response.choices[0].message.content


if __name__ == "__main__":
    target_image_path = "images/login.png"
    prompt = "이 이미지를 HTML과 CSS로 작성해서 Bootstrap 5를 함께 사용해서 만들어 달라"
    result = analyze_image(prompt, target_image_path)
    print(result)
```

### 4-3. `.env` 파일 설정

```bash
# .env
OPENAI_API_KEY=sk-xxxxxxxxxxxxxxxxxxxxxxxx
```

### 4-4. GPT 활용 팁

* 특정 코드 부분을 **드래그로 선택한 후 질문**하면 해당 부분만 수정 요청 가능
* GPT는 할루시네이션(hallucination)을 만들 수 있으므로 무지성 복사·붙여넣기는 주의
* 스스로 **디버깅**하는 연습이 중요 — 프롬프트를 잘 쓰는 능력이 곧 개발 능력

## 5. UI 용어 정리

Bootstrap 문서(`getbootstrap.com/docs`)의 Components 섹션에서 아래 용어들의 실제 구현 예시를 확인할 수 있다.

### 5-1. 주요 UI 컴포넌트 용어

| 용어 | 설명 | 예시 |
|------|------|------|
| **스피너 (Spinner)** | 로딩 중 빙글빙글 돌아가는 인디케이터 | 버퍼링 시 원형 로딩 아이콘 |
| **캐러셀 (Carousel)** | 화살표를 눌러 화면이 옆으로 넘어가는 슬라이드 | 배너 이미지 슬라이더 |
| **모달 (Modal)** | 버튼/화면 클릭 시 화면 위에 뜨는 독립적인 창 | "정말 탈퇴하시겠습니까?" 확인창 |
| **내비게이션 바 (Navbar)** | 화면 최상단에 위치한 메뉴 바 | Bootstrap, 각종 사이트 상단 메뉴 |
| **페이지네이션 (Pagination)** | 많은 데이터를 페이지 단위로 나누는 기능 | 게시글 100개를 10개씩 10페이지로 분리 |
| **토스트 (Toast)** | 특정 이벤트 발생 시 화면 모서리에 슥 올라오는 알림창 | 카카오톡 데스크탑 알림, 우측 상단 팝업 |
| **햄버거 메뉴 (Hamburger Menu)** | 반응형에서 Navbar를 대체하는 ≡ 아이콘 | 모바일에서 Navbar 대신 나타나는 줄 3개 버튼 |
| **아코디언 (Accordion)** | 클릭하면 내용이 펼쳐지고 다시 누르면 닫히는 UI | FAQ 섹션 |
| **브레드크럼 (Breadcrumb)** | 현재 위치의 경로를 표시하는 내비게이션 | `홈 > 카테고리 > 상품명` |
| **플레이스홀더 (Placeholder)** | 입력창 내부에 표시되는 안내 텍스트 | 검색창의 "검색어를 입력하세요" |
| **팝오버 (Popover)** | 클릭 시 요소 주변에 뜨는 설명창 | 버튼 클릭 시 추가 정보 표시 |
| **툴팁 (Tooltip)** | 마우스를 올렸을 때 나타나는 짧은 설명 | 아이콘에 마우스 올리면 설명 표시 |

Tailwind CSS도 Bootstrap과 유사하게 이런 컴포넌트들을 제공한다. Tailwind CSS는 CSS 프레임워크이며, **스펙이 아니다** — 활용하는 것 자체가 개인 역량이 아니므로 직접 만들어보는 도전을 권장한다.

## 6. UI/UX 개론

### 6-1. UI vs UX

| 구분 | 풀네임 | 의미 |
|------|--------|------|
| **UI** (User Interface) | 사용자 인터페이스 | 사용자가 서비스와 상호작용하는 **시각적 요소** |
| **UX** (User Experience) | 사용자 경험 | 사용자가 제품을 사용하면서 느끼는 **전반적인 경험** (유용성, 사용성, 감성) |

UI와 UX는 세트로 불리며, 시각적으로 예쁜 것이 하나의 사용자 경험으로 연결된다.

### 6-2. UX가 중요한 이유

* 기능이 아무리 좋아도 UX가 나쁘면 **사용자 이탈**로 직결
* 나쁜 UX의 결과: 이탈률 증가, 신뢰도 하락, 사용자 학습 비용 발생

**카카오톡 첫 화면 변경 사례**

기존 첫 화면(친구 탭) → 피드 형태로 변경. 사용자 입장에서 익숙한 UX가 바뀌자 신뢰도 하락 및 이탈이 발생했다. 코드 한 줄 변경이 서비스 전체 신뢰도에 영향을 준 대표적 사례다.

**개발자 입장에서 UX를 알아야 하는 이유**

* 자연스러운 UI 플로우 = Django의 URL 설계, 라우팅 구조, DB 테이블 설계와 직결
* 잘 설계된 UX 기획안 = 잘못된 의사결정 방지
* 기술적 한계를 UX로 극복 가능

## 7. UX 설계 원칙

### 7-1. 명확한 시각적 가이드

나쁜 예: 결제하기 버튼과 취소하기 버튼의 색상이 동일 → 사용자 실수 유발, 불필요한 사고 정지.

좋은 예: 더 중요한 행동(결제)에 강조 색상 부여, 버튼 텍스트를 동사 중심으로 작성.

글은 최대한 줄이고 직관적으로 본능을 따라갈 수 있도록 설계해야 한다.

### 7-2. 실시간 피드백 (제출 후 즉각 가이드)

나쁜 예: 모든 항목 입력 완료 후 제출하자 "오류가 있습니다"만 표시 → 어디가 틀렸는지 모름.

좋은 예: 비밀번호 입력 중 조건 충족 시 즉시 색상 변화, 조건 안내 표시. 폼 데이터는 새로고침 또는 세션 만료 후에도 유지.

### 7-3. 숨겨진 기능 vs 눈에 보이는 기능

**사용자는 자신에게 보이는 기능만 존재한다고 믿는다.**

자주 쓰이는 핵심 기능(홈, 검색, 마이페이지 등)은 반드시 화면에 노출해야 한다. 깔끔해 보인다고 숨기면 사용자는 그 기능이 없다고 판단하고 이탈한다. 하단 탭바(엄지존)를 적극 활용한다.

### 7-4. 멈춘 것 같은 화면 — 심리적 속도 개선

버튼을 눌렀는데 아무 반응이 없으면 사용자는 앱이 멈췄다고 판단하고 불안감을 느끼며 무한 클릭을 하게 된다.

나쁜 예: 티켓팅 시 버튼 누른 후 화면 변화 없음.

좋은 예: "현재 6만 명이 대기 중입니다" 실시간 카운트다운 표시. 실제로 처리 속도를 올릴 수 없더라도 **심리적 대기 시간을 줄이는** 것만으로 사용자 이탈을 막을 수 있다.

### 7-5. 힉스의 법칙 (Hick's Law)

선택지가 많을수록 결정 시간이 길어진다. 화면에 정보와 버튼을 과도하게 배치하면 사용자는 인지적 과부하를 느낀다. 꼭 필요한 것만 보여줄 것.

### 7-6. 프로그레시브 디스클로저 (Progressive Disclosure)

단계적으로 정보를 제공하는 방식. 한 번에 모든 정보를 제공하지 않고, 단계를 나눠 진행 상황을 보여주면 사용자에게 성취감을 주고 완주율이 높아진다.

회원가입 시 모든 항목을 한 화면에 나열하면 뇌정지가 온다. 토스처럼 "아이디·비밀번호 먼저 → 다음 단계"로 나누는 것이 좋은 예다.

### 7-7. 시스템 경고 및 친절한 안내

나쁜 예: 에러 발생 시 `500 Internal Server Error`만 노출 → 사용자 불안감.

좋은 예 (네이버): "잠시 숨을 고르고 있습니다." + "다시 시도" / "홈으로 이동" 버튼 제공.

에러는 사용자가 무료로 QA(버그 탐색)를 해주는 기회다. 외면하지 않고 로그를 남겨 개선에 활용해야 한다.

### 7-8. 피츠의 법칙 (Fitts' Law)

대상이 크고 가까울수록 도달 시간이 짧아진다. 중요한 버튼(장바구니 담기, 결제 등)은 **크게, 누르기 쉬운 위치**에 배치한다. 모바일에서는 사용자의 손가락(엄지)이 마우스보다 크다는 점을 반드시 고려한다.

### 7-9. 무한 스크롤 vs 페이지네이션

| 방식 | 적합한 상황 |
|------|-------------|
| **무한 스크롤** | 인스타그램, 틱톡, 쇼츠 등 연속적 콘텐츠 소비 |
| **페이지네이션** | 검색 결과, 메일함, 게시글 목록 등 탐색·재방문이 필요한 콘텐츠 |

옳고 그름이 정확히 없다. **사용자의 목적에 부합하는 기능만 있을 뿐이다.**

## 8. 기업 UI/UX 사례

### 8-1. 삼성 One UI

* 핵심 철학: **한손 조작 최적화**, 인체공학적 설계
* 갤럭시 폴드·플립 등 다양한 폼팩터에 대응하는 UI
* 폰, 태블릿, 워치 간 디자인 일관성 유지
* 다크 모드 전 제품 지원
* 점점 커지는 화면을 소프트웨어로 극복하는 교과서적 사례

### 8-2. 애플

* 핵심 철학: **학습하지 않아도 자연스럽게 사용**
* 단순함 추구 — 복잡함을 정리하는 것이 디자인
* 전 제품(아이폰, 맥, 애플워치) 통일된 디자인 언어 (동일 곡률, 동일 진동 피드백)
* 인간 중심 설계: 시각 장애, 청각 장애 사용자를 위한 접근성 기능 내재화

### 8-3. 토스 (Toss)

* 핵심 철학: **One Thing Per Page (한 화면에 하나의 기능)**
* 기술 혁신이 아닌 **UX 혁신**으로 성공한 핀테크 사례
* 기존 복잡한 은행 송금 과정 → 화면의 버튼 하나씩만 누르면 완료
* 계좌번호 복사 시 자동 입력, 수취인 은행 자동 감지
* 사람 중심의 언어 사용: "보내러 가기", "다음 게임을 노려보세요" 등
* Toss 공식 개발자 센터(`toss.im`)에서 UI/UX 가이드 및 보이스톤 지침 공개

### 8-4. 쿠팡 — 성공한 나쁜 디자인

쿠팡은 미적 기준으로는 나쁜 디자인이지만 **비즈니스 목적에 최적화된 UX**로 성공했다.

| 문제점 | 내용 |
|--------|------|
| 시각적 노이즈 | 수많은 팝업, 배너, 텍스트로 어수선 |
| 힉스의 법칙 위반 | 상품이 미친 듯이 쏟아지는 레이아웃 |
| 다크 패턴 | 멤버십 해지 버튼을 찾기 어렵게 설계, 해지 페이지에서 "유지하기"를 강조 색상으로 배치 |

비즈니스 관점: 정보 투명성(선택지 노출)으로 "내가 고른 게 제일 싸다"는 심리를 만들고, 해지를 어렵게 해 유저를 머물게 한다.

## 9. 관통 PJT 실습 안내

### 9-1. 프로젝트 목표

스켈레톤 코드에서 완성 코드로 발전시키기.

* **스켈레톤 코드**: 내비게이션 바 없음, 베스트셀러 섹션 비어 있음
* **완성 목표**: 내비게이션 바 구현 + 베스트셀러 섹션 카드 목록 구현

### 9-2. 진행 방법

```bash
# 1. 강사가 올린 스켈레톤 코드 클론 또는 다운로드
# 2. 명세서 확인
# 3. 2인 1조로 구현
# 4. 완성 후 강사 GitHub에 초대
```

* 2인 1조, GPT 적극 활용 권장
* 완료 후 개인 공부 시간 활용 가능
