# [관통 PJT] TDD 함정과 극복 방법

---

## 1. 안티 패턴이란?

- **디자인 패턴**: 선배 개발자들이 먼저 문제를 경험하고, 이런 방식으로 짜면 문제가 안 생긴다고 제시하는 패턴
- **안티 패턴**: 이렇게 짜면 **터진다** — 나쁜 테스트를 짜지 않는 법

TDD가 독이 되지 않으려면 나쁜 테스트를 짜지 않아야 한다.  
대표적인 **안티 패턴 5가지**를 알아두어야 한다.

---

## 2. 안티 패턴 5가지

### 1. 구현 세부 사항 테스트

테스트 코드의 존재 이유 자체를 흔들어버리는 **가장 파괴적인 안티 패턴**

- **현상**: 함수의 내부 변수 값, 특정 내부 함수가 몇 번 호출됐는지, 내부 동작 과정 등을 테스트하면서 발생
- **문제점**: 코드의 결과물이 동일하게 내부 로직을 잘 리팩토링하더라도, **구현 방식을 테스트하기 때문에 테스트를 통과하지 못함**
- **해결책**: **입력값과 출력값에만 집중**하기

```
비유: 부산 → 서울 도착을 검증하는 테스트인데
     강원도 경유 여부까지 테스트하면 안 된다.
     KTX를 뚫어서(리팩토링) 서울에 잘 도착해도
     강원도를 안 거쳤다고 테스트가 실패하게 된다.
```

> 어차피 안에 로직이 잘 안 돌아가면 출력값이 틀리게 된다.  
> 출력값이 틀렸을 때 거기를 보면 된다.

### 2. 리팩토링 생략

- **현상**: 테스트를 통과(Pass)하면 다음 기능으로 바로 넘어가는 습관
- **문제점**: 테스트는 통과하지만 점점 **스파게티 코드**가 됨
- **해결책**: Pass는 리팩토링을 위한 안전책일 뿐, **리팩토링이 핵심**임을 인식하기

```
TDD 사이클: 문제 정의 → 문제 해결 → 코드 개선(리팩토링)
많은 개발자들이 코드 개선 단계를 생략한다.
```

> "패스됐네, 넘어가야지" → "패스됐네, 이 코드를 막 작성해도 안정적이겠네!"  
> 마인드를 바꿔야 한다.

### 3. 모킹 지옥

- **현상**: 외부 API나 DB 의존성을 끊기 위해 사용하는 모킹을 **남용**하는 경우 — 테스트 코드의 대부분이 `mock.patch`나 가짜 객체 설정으로 도배된 경우
- **문제점**: 실제 시스템이 고장나도 가짜 데이터끼리 응답하며 테스트가 통과됨 → **실제 연동 로직이 검증되지 않는 문제** 발생
- **해결책**: **통제 불가능한 영역**(네트워크 통신, 외부 서비스)에만 최소한으로 사용하기

> 배포 직후나 최종 테스트 단계에서는 모킹을 빼고 실제 연동 로직을 검증해야 한다.

### 4. 테스트 간 의존성

- **현상**: 테스트끼리 데이터를 공유하거나 실행 순서에 영향을 받는 경우 (예: Test_A가 실행된 후 남긴 DB 데이터가 있어야 Test_B가 통과됨)
- **문제점**: 하나가 실패하면 모든 테스트가 실패하고, **어떤 테스트가 문제인지 찾기 어려움**
- **해결책**: 각 테스트를 **완전히 고립된 상태**로 개발하고, 테스트가 끝나면 데이터가 롤백되어 초기 상태로 돌아오도록 설정

> Django pytest에서 `@pytest.mark.django_db`를 사용하면 각 테스트마다 DB가 자동으로 롤백된다.

### 5. 지나친 검증

- **현상**: 하나의 테스트 함수 안에서 수십 개의 assert를 사용하는 경우 (제목, 내용, 작성일, 조회수 등 모든 것을 한 함수에서 검증)
- **문제점**: 테스트가 실패했을 때, **무엇 때문에 실패했는지 한 눈에 파악하기 어려움**
- **해결책**: 하나의 테스트는 하나의 논리적 단위만 검증; **검증할 게 많다면 테스트 함수를 쪼개기**

```
하나의 함수가 하나의 기능만 하는 것처럼
하나의 테스트는 하나의 논리적 단위만 검증해라.
```

## 3. TDD 도입 시 겪는 현실적인 어려움

### 1. 시간 부족

- 일반적으로 TDD 도입 시 개발 시간이 **1.5 ~ 2배** 늘어남
- 개발자는 유닛 테스트의 필요성을 인정하지만, 경영진 레벨에서는 "기능이 돌아가는데 왜 테스트까지?"라는 반응이 있음
- **대처법**: 처음부터 모든 것을 TDD로 하려 하지 말고, **"버그 발생 시 치명적인 코드", "복잡한 코드"** 위주로 작성

### 2. 코드가 복잡해서 테스트 코드를 작성할 엄두가 안 남

- 코드가 이미 스파게티거나, 의존성이 너무 강한 코드라면 테스트 코드 짜기가 매우 어려움
- **대처법**: 이러한 경험을 **내 코드의 문제점을 파악하는 계기**로 삼고, 천천히 개선해 나가야 함

### 3. 작성할 테스트가 너무 많음

- 이미 코드가 완성되어 있다면 한 번에 다 작성하기에는 양이 너무 많음
- **대처법**: 한 번에 다 하지 말고, **조금씩/부분적인 테스트라도 추가**해 나가는 것이 중요

### 4. 기획이 자주 바뀜

- 스타트업에서는 기획이 자주 바뀌고, 그로 인해 테스트 코드 작성하는 시간이 코드 고치는 시간보다 오래 걸림
- **대처법**: 기획이 틀어지지 않을 것 같은 **중요한 비즈니스 로직**에 집중해서 테스트 코드를 작성; 자주 바뀌는 파트는 힘을 빼서 테스트 코드를 작성

## 4. 지속 가능한 TDD

TDD를 배우면 두 가지 부류로 나뉜다:
- "코드의 안정성을 확보할 수 있는 혁명이다"
- "현실적인 개발 시간을 고려하지 못한 이상론이다"

**두 주장 모두 맞다.** 결국 흑백 논리 없이 **실용적인 타협점**을 찾아 나가야 한다.

### TDD를 끝까지 지속하는 방법

1. **테스트 코드를 중요한 업무로 인식하기**  
   귀찮다고 안 해도 되는 레벨이 아니다. API 작성이나 DB 설계처럼 필수 업무로 인식해야 한다.

2. **완벽하게 짜야 한다는 생각을 버리기**  
   조금씩 부분적인 테스트라도 추가해 나가는 것이 중요하다.

3. **리팩토링을 예쁜 코드로 바꾸는 즐거운 과정이라 생각하기**  
   유닛 테스트를 잘 짜 놓으면 리팩토링해도 코드가 망가지지 않는다. 그 안에서 내 철학대로 코드를 예쁘게 짜는 즐거움을 찾아야 한다.

4. **나의 의지만을 믿지 말고, 자동화(CI/CD)를 연구하기**  
   인간의 의지는 길어야 3일이다. 테스트 코드를 자동으로 검증해 주는 CI/CD 사이클을 구축하면 지속 가능성이 높아진다.

## 5. TDD/유닛 테스트에 대한 현실적 관점 정리

| 구분 | 내용 |
|------|------|
| TDD (방법론) | 도입 여부는 상황에 따라 선택적; 기획 변경이 잦은 스타트업에선 특히 신중하게 판단 |
| 유닛 테스트 | 요즘 시대에는 **필수**에 가까움; 기업 채용 요구사항에도 충분히 들어가는 내용 |
| 핵심 교훈 | 흑백 논리 X, **트레이드 오프**를 인식하고 적절한 상황에 적절하게 사용하는 것이 최고 |
