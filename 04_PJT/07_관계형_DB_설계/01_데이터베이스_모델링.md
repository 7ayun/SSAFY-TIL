# [관통 PJT] 데이터베이스 모델링

---

## 1. 데이터베이스 모델링이란

현실 세계의 관계와 데이터를 데이터베이스 구조로 정의하고 설계하는 과정이다. 수강신청 앱을 예로 들면, 학생 정보와 수강 정보를 어떤 테이블로 설계할지 결정하는 것이 모델링이다.

> AI가 모델링을 잘해주는 건 맞지만, **비즈니스 맥락**은 AI가 알 수 없다. 여행사나 은행처럼 회사마다 고유한 관계 규칙이 있고, 그걸 AI에게 제대로 먹이려면 본인이 먼저 알아야 한다. 또한 AI가 만들어준 모델에서 빠진 케이스를 잡아내려면 직접 이해하고 있어야 한다.

---

## 2. 모델링이 중요한 이유

| 이유 | 설명 |
|------|------|
| **효율성** | 쿼리 성능과 저장 효율 향상 → 결국 **돈과 속도** 문제. 잘못 설계하면 데이터를 찾을 때 전체 테이블을 순회해야 함 |
| **일관성** | 중복 데이터를 방지해 갱신 시 데이터 모순이 생기지 않도록 함. 예) 과목명 "언어"를 "국어"로 바꿀 때 일부만 바뀌는 문제 |
| **무결성** | 제약 조건을 설계 단계에서 미리 설정해 부적절한 데이터가 들어가지 못하도록 함 |

---

## 3. 무결성 제약조건

데이터베이스에 잘못된 데이터가 삽입·수정·삭제되는 걸 막아 일관성과 신뢰성을 유지하는 조건들이다.

### 1) 개체 무결성 (Entity Integrity)
- 기본키(PK)는 **고유**해야 하고 **NULL을 허용하지 않는다**
- 주민등록번호처럼 나라에서 한 사람을 유일하게 구별하는 값과 같다

```sql
CREATE TABLE Student (
    student_id INT PRIMARY KEY,   -- NULL 불가, 중복 불가
    name VARCHAR(50) NOT NULL
);
```

### 2) 참조 무결성 (Referential Integrity)
- 외래키(FK)는 **참조 대상 테이블의 기본키에 존재하는 값**이어야 한다
- 존재하지 않는 기본키를 참조하면 안 된다 (외래키는 NULL은 허용)
- 부모 레코드 삭제 시 처리 방법:
  - **CASCADE**: 참조하는 자식 레코드도 함께 삭제
  - **PROTECT**: 참조값이 하나라도 있으면 삭제 자체를 막음

```sql
CREATE TABLE Department (dept_id INT PRIMARY KEY, dept_name VARCHAR(50));
CREATE TABLE Employee (
    emp_id INT PRIMARY KEY,
    dept_id INT,
    FOREIGN KEY (dept_id) REFERENCES Department(dept_id)
);
```

> **주의** — CASCADE는 데이터 손실 위험이 크므로 신중하게 사용해야 한다. 참조 무결성 위반은 현업 신입들이 자주 겪는 실수 중 하나다.

### 3) 도메인 무결성 (Domain Integrity)
- 각 속성(컬럼)이 정의된 **타입·범위·형식**에 맞는 값만 가져야 한다
- 예) 가격은 0 초과, 생년월일은 현재 날짜 이전, 카테고리는 정해진 값만

```sql
CREATE TABLE Product (
    product_id INT PRIMARY KEY,
    price DECIMAL(10, 2) CHECK (price > 0),
    category VARCHAR(20) CHECK (category IN ('전자제품', '의류', '도서'))
);
```

### 4) 고유 무결성 (Unique Integrity)
- 특정 컬럼의 값이 테이블 내에서 **중복되지 않도록** 제한
- 예) 이메일 주소, 닉네임 등 비즈니스에 따라 유일해야 할 필드
- 고유 여부는 비즈니스 로직에 따라 결정된다 (닉네임이 유일해야 할 수도, 아닐 수도 있음)

### 5) NULL 무결성 (NOT NULL)
- 특정 컬럼이 **NULL 값을 가질 수 없도록** 제한
- 예) 여행사의 예약번호, 여행 날짜처럼 반드시 있어야 하는 값

### 6) 일반 무결성 (Business Rule)
- 위의 제약조건 외에 **비즈니스 로직에 따라 추가 정의**하는 규칙
- 예) 은행 잔고가 0 미만이 되지 않도록, 재고 수량이 음수가 되지 않도록
- 마이너스 통장처럼 회사의 정책에 따라 달라질 수 있음

## 4. 모델링 과정 4단계

```
요구사항 수집 및 분석 → 개념적 설계 → 논리적 설계 → 물리적 설계
```

### 1단계: 요구사항 수집 및 분석
어떤 데이터가 필요하고, 어떤 작업을 수행해야 하는지 파악하는 단계다. 실무에서는 대표·기획자가 담당한다.

- **개체 (Entity)**: 저장할 중요한 데이터 집합 → 테이블에 대응. 예) 고객, 상품
- **속성 (Attribute)**: 더 이상 쪼갤 수 없는 데이터 단위. 예) 고객명, 상품 가격
- **관계 (Relationship)**: 개체 사이의 논리적 연관성. 예) 고객은 상품을 N:M으로 주문

### 2단계: 개념적 설계 (ERD 작성)
요구사항을 기반으로 개체와 관계를 **가시적으로 그려내는** 단계. 대충 큰 그림을 잡는 과정이다.

- ERD 표기법: **Chen 표기법**, **IE 표기법 (까마귀발 표기)** 등이 사용됨
- 고객 ↔ 상품을 N:M 관계로 그리고, 각 개체의 속성을 나열

### 3단계: 논리적 설계
개념적 설계를 기반으로 **디테일한 DB 구조**를 확정하는 단계. 실질적인 개발자의 역할이다.

- N:M 관계는 중개 테이블로 분해 (예: 고객 ↔ 주문 ↔ 상품)
- 컬럼 타입, 제약조건 등 구체적 스펙 결정
- **정규화(Normalization)** 를 적용하는 단계

```
Customer
  PK  customer_id
      name        VARCHAR(20) NOT NULL
      age         INT NOT NULL
      address     VARCHAR(50)
      phone       VARCHAR(20) NOT NULL
      shopping_point INT NOT NULL DEFAULT 0
```

### 4단계: 물리적 설계
실제 저장·운영 환경에 맞게 최적화하는 단계. AWS RDS 등 클라우드를 쓰면 대부분 자동으로 처리된다.

- **인덱스**: 책의 목차처럼 조회를 빠르게 하는 구조 (B-Tree, AVL Tree 등). 조회 속도 향상 vs 삽입·삭제 비용 증가의 트레이드오프 존재
- **파티션**: 데이터를 연도별·범위별로 물리적으로 분리해 특정 범위 쿼리 속도 향상
- **클러스터링**: 함께 조회되는 데이터를 물리적으로 가깝게 저장해 범위 검색 최적화
- 보안, 백업, 복구 등도 이 단계에서 고려

> **큰 회사들이 자체 데이터센터를 갖는 이유** — AWS 같은 클라우드 서비스는 편리하지만, 서버 장애 시 서비스도 함께 다운되는 의존성이 생긴다. 쿠키런킹덤 사례처럼 1년에 한두 번 AWS 장애로 게임이 멈추는 일이 발생하기도 한다.

## 💡 한 줄 요약
> DB 모델링은 무결성 제약조건과 4단계 설계 과정을 통해 **일관성 있고 이상현상 없는 데이터베이스**를 만드는 핵심 작업이다.
