# [관통 PJT] 데이터베이스 정규화

---

## 1. 정규화란

데이터 **중복을 최소화**하고 **이상현상을 방지**하기 위해 테이블 구조를 체계적으로 분해하는 설계 기법이다. 논리적 설계 단계의 핵심이며, 테이블을 점점 잘게 쪼개는 과정이다.

**정규화의 목적**
- **중복 최소화**: 동일한 데이터를 여러 곳에 저장하지 않음
- **이상현상 방지**: 삽입·갱신·삭제 작업 시 발생하는 불일치 예방
- **유연성 (유지보수성)**: 비즈니스 모델 변경 시 재작업 범위를 최소화

실무에서는 일반적으로 **3NF까지** 적용한다. 그 이상은 테이블이 너무 많아져 조인 비용이 커지기 때문이다.

---

## 2. 이상현상 (Anomaly)

정규화 없이 설계했을 때 삽입·갱신·삭제 과정에서 발생하는 비일관성 문제다.

아래 예시처럼 레시피 정보와 재료 정보가 하나의 테이블에 섞여 있을 때 문제가 발생한다.

| id | name | description | ingredients |
|---|---|---|---|
| 1 | 뽀모도로 | 토마토 베이스의 기본 파스타 | 토마토, 파스타 |
| 2 | 알리오올리오 | 마늘과 올리브 | 올리브, 파스타, 마늘 |
| 3 | 명란파스타 | 명란젓이 들어간 특별한 파스타 | 올리브, 스파게티, 명란젓 |

### 삽입 이상 (Insertion Anomaly)
새로운 식재료 "마늘"만 등록하고 싶어도, 테이블 구조상 요리 이름(name)과 설명(description)이 없으면 삽입이 불가능하다. 결국 가짜 데이터를 억지로 입력해야 한다.

### 갱신 이상 (Update Anomaly)
"파스타"를 "스파게티"로 바꾸려면 ingredients 컬럼에 문자열로 흩어진 모든 파스타를 찾아서 일일이 바꿔야 한다. 하나라도 놓치면 데이터 불일치가 발생한다.

> 이 문제는 발생해도 바로 알아채기 어렵다. 몇 달이 지나서야 조회가 안 된다는 걸 깨닫고, 그 사이 쌓인 데이터를 복구해야 하는 상황이 생긴다.

### 삭제 이상 (Deletion Anomaly)
"명란파스타" 레시피를 삭제하면, 그 행에만 존재하던 "명란젓"이라는 재료 정보까지 같이 사라진다.

### 근본 원인
레시피(1:N)와 재료(N:M)가 단일 테이블에 뒤섞여 있기 때문이다. 해결책은 **테이블 분리 + N:M 중개 테이블 생성**이다.

## 3. 함수 종속성과 결정자

정규화를 이해하려면 이 개념이 먼저 필요하다.

- **함수 종속성 (Functional Dependency)**: A의 값이 정해지면 B의 값이 유일하게 결정될 때, "B는 A에 함수적으로 종속된다" (A → B)
  - 예) 학번 → 이름 (학번을 알면 이름을 알 수 있다)
- **결정자 (Determinant)**: 다른 속성을 결정하는 속성 집합 (화살표 왼쪽, 즉 A)

---

## 4. 정규화 단계

### 1NF (제1정규형) — 원자값 보장

**각 컬럼은 하나의 값(원자값)만 가져야 한다.** 콤마로 구분된 문자열이나 리스트 형태로 저장하면 안 된다.

**위반 예시**
| 고객번호 | 이름 | 전화번호 |
|---|---|---|
| 123 | 파이썬 | 010-1111-2222, 010-3333-4444 |

**해결**: 전화번호를 별도 테이블로 분리

| 고객번호 | 이름 |     | 고객번호 | 전화번호 |
|---|---|---|---|---|
| 123 | 파이썬 |     | 123 | 010-1111-2222 |
| 234 | 자바 |     | 234 | 010-3333-4444 |
|  |  |     | 234 | 010-1234-5678 |

> **주의** — 같은 고객번호를 한 테이블에 여러 행으로 나눠 저장하면 기본키가 중복되는 문제가 생긴다.

---

### 2NF (제2정규형) — 부분 함수 종속 제거

**복합키(여러 컬럼으로 구성된 기본키)를 사용하는 테이블에서**, 비기본키 속성이 복합키 전체가 아닌 **일부 컬럼에 의해서만 결정**되면(= 부분 함수 종속) 해당 속성을 별도 테이블로 분리한다.

> 복합키가 없는 테이블이라면 2NF를 적용할 필요가 없다.

**복합키란?** 단일 컬럼으로 행을 유일하게 식별할 수 없어 **2개 이상의 컬럼을 합쳐서** 기본키로 사용하는 것. 예) 수강신청 테이블에서 {학생번호 + 과목번호}가 복합키.

**위반 예시** — 복합키: {상품명, 생산자}

| 상품명 | 생산자 | 상품가격 | 생산지 |
|---|---|---|---|
| 사과 | 박씨농가 | 1000 | 대구 |
| 바나나 | 박씨농가 | 1500 | 대구 |
| 사과 | 청년사과 | 1200 | 경북 |

- 상품가격 → {상품명 + 생산자}에 의해 결정 ✅ (완전 함수 종속)
- 생산지 → **생산자**에 의해서만 결정 ❌ (부분 함수 종속 → 위반!)

**해결**: 부분 종속 컬럼을 별도 테이블로 분리

| 생산자 | 생산지 |     | 상품명 | 생산자 | 상품가격 |
|---|---|---|---|---|---|
| 박씨농가 | 대구 |     | 사과 | 박씨농가 | 1000 |
| 청년사과 | 경북 |     | 바나나 | 박씨농가 | 1500 |
| 혼저옵서예 | 제주도 |     | 사과 | 청년사과 | 1200 |

이렇게 하면 "대구 → 대구시" 변경 시 생산자 테이블에서 한 번만 수정하면 된다.

---

### 3NF (제3정규형) — 이행적 함수 종속 제거

**비기본키 컬럼이 다른 비기본키 컬럼을 결정하면 안 된다.** A → B이고 B → C이면, A → C가 성립하는 이행 종속이 생기는데, 이때 {B, C}를 별도 테이블로 분리한다.

쉽게 표현하면: **기본키 외의 값들끼리 "대장 역할"을 하면 따로 빼라.**

**위반 예시** — 기본키: 학생번호

| 학생번호 | 학생이름 | 학과 | 학과장 |
|---|---|---|---|
| 1 | 장원영 | 국어국문학과 | 이효리 |
| 2 | 김채원 | 경제학과 | 바다 |
| 3 | 안유진 | 국어국문학과 | 이효리 |

- 학생번호 → 학과 ✅
- 학과 → 학과장 ❌ (비기본키인 학과가 비기본키인 학과장을 결정 → 이행 종속!)

**해결**: {학과, 학과장}을 별도 테이블로 분리

| 학생번호 | 학생이름 | 학과 |     | 학과 | 학과장 |
|---|---|---|---|---|---|
| 1 | 장원영 | 국어국문학과 |     | 국어국문학과 | 이효리 |
| 2 | 김채원 | 경제학과 |     | 경제학과 | 바다 |
| 3 | 안유진 | 국어국문학과 |     | | |

---

### BCNF (Boyce-Codd Normal Form) — 모든 결정자는 후보키

**3NF보다 엄격한 규칙**: 모든 결정자(화살표 왼쪽)는 반드시 후보키여야 한다.

**후보키란?** 테이블의 각 행을 유일하게 식별할 수 있는 속성(또는 조합) 중 **최소성을 만족하는 것**. 즉, PK가 될 수 있는 후보들이다.

> **롤(LoL) 사례** — 초기에는 닉네임이 후보키(유일)였으나, 이용자 급증으로 중복 닉네임을 허용하면서 닉네임+태그(#1234)의 복합키로 변경됐다. 이 변경 과정에서 기존 로직을 대거 수정해야 했다. 초반 설계가 얼마나 중요한지 보여주는 사례다.

**핵심 판단 방법**: 남을 결정하는 역할을 하려면 (결정자가 되려면), 그 컬럼 자체가 유일해야 한다.

실무에서 BCNF까지 적용하는 경우는 드물다. 3NF까지 하는 것이 일반적이다.

---

## 5. 역정규화 (Denormalization)

정규화로 잘게 쪼갠 테이블을 **의도적으로 다시 합치는** 것. 나쁜 설계가 아니라 **의도된 선택**이다.

- 테이블이 많아질수록 조인(JOIN)이 늘어나고, 조인은 비용이다
- 이상현상 위험을 감수하더라도 조인 비용 절감이 더 이득인 경우 역정규화를 선택
- 경험을 바탕으로 판단하는 고급 영역이다

---

## 💡 한 줄 요약
> 정규화는 이상현상을 막기 위해 테이블을 체계적으로 쪼개는 과정으로, 1NF(원자값) → 2NF(부분 종속 제거) → 3NF(이행 종속 제거)가 실무 필수 단계다.
